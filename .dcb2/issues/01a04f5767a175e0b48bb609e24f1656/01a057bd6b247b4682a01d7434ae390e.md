# Design brief

## Problem

Json.parse<T> and Json.serialize<T> generate and recompile large RawJson-based codec graphs for each concrete call site. Reusable JSON mechanics are repeatedly lowered and emitted with type-specific construction code.

## Goals

- Keep compile-time validation and direct native construction for concrete Dark types.
- Replace generated RawJson traversal with reusable streaming parsing/writing plus thin compiled codecs.
- Preserve the pinned JSON parity contract exactly.
- Achieve at least 3.33× faster cumulative JSON E2E compilation without unacceptable decode regressions.

## Proposed solution

## Architecture

Keep the public API unchanged. `Json.parse<T>` type-checks and resolves `T`, then calls a compiler-derived private `decode_T`; `Json.serialize<T>` calls `encode_T`.

`decode_T` is ordinary compiled native code, not an interpreted descriptor. It owns concrete scalar policy, direct record/sum construction, tuple arity, static field/variant dispatch, and calls to child codecs. A reusable private runtime owns JSON lexing, comments/trivia, cursor advancement, spans, container framing, common scalar extraction, path extension, common errors, and writer escaping.

```text
Json.parse<Person>(source)
→ Reader.parseRoot(source)
→ Person.__jsonDecode(reader, rootView, [Root])
→ Result<Person, ParseError>
```

Typed parsing does not construct `InternalRawJson`; public `AltJson.parse` remains unchanged and continues to construct its public ordered tree.

## Reader and writer ABI

```text
JsonReader { Source: String; Cursor: Int64; Limit: Int64 }
JsonSpan { Start: Int64; EndExclusive: Int64 }
JsonValueView { Span: JsonSpan; Kind: Null|Bool|Number|String|Array|Object }

parseRoot : String -> Result<(JsonReader, JsonValueView), NotJson>
expectNull|Bool|String|NumberLexeme
beginArray / nextArray / finishArray
beginObject / nextObject / finishObject
skipValue
rawFragment : JsonReader * JsonSpan -> String
extendPathField / extendPathIndex
```

Reader values, cursors, spans, and views borrow the immutable source semantically; they do not allocate substrings or retain RawJson nodes. `rawFragment` slices the source only when an observable error needs it. Lexical operations return only complete syntactically valid views. Invalid literals, escapes, UTF-16 surrogate pairs, numbers, comments, separators, trailing commas, and non-trivia trailing input yield `NotJson` before type decoding.

`JsonWriter` owns compact JSON punctuation and canonical escaping. Thin codecs select scalar formatting and emit statically known record fields, enum cases, arrays, and child codecs; they no longer generate string-concatenation graphs.

## Concrete codec flow

For `type Person = { Name: String; Age: Int64 }`, `Person.__jsonDecode`:

1. Requires an object view or returns `CantMatchWithType(Person, rawFragment, path)`.
2. Scans source-ordered object fields through `ObjectCursor`, retaining compact state for declared fields only and skipping unknown fields.
3. Returns `RecordDuplicateField` immediately for a second declared field.
4. After syntactic object completion, checks required fields in declaration order and returns the first `RecordMissingField`.
5. Decodes present declared fields in declaration order using child codecs and extended paths.
6. Directly constructs `Person`.

For a sum, generated code requires exactly one object field, retains source-order names for `EnumTooManyCases`, dispatches directly on known case names, uses a reusable array cursor for payload framing, decodes the common payload prefix before reporting a later missing/extra argument, then directly constructs the known variant.

Encoding is symmetric: `Person.__jsonEncode` emits fields in ordinal name order through `JsonWriter`; enum codecs emit their existing one-field-object plus argument-array wire form.

## Codec ownership

- Named records and sums own private codec definitions in their declaration group.
- Structural types use small compiler-generated composition wrappers over child codecs.
- Generic named codecs are templates parameterized by child codecs and specialized only at concrete applications by existing monomorphization.
- Recursive and mutually recursive declaration groups reserve all codec identities before deriving any body; generated direct calls form the recursive graph.
- Locally declared types derive codecs in their local compilation unit.
- Codecs are private compiler identities, not a public custom-codec feature in this issue.

## Compiler boundaries

Type checking continues to validate supported JSON target types and resolve aliases. The JSON pass replaces current `ensureDecoder`/`ensureSerializer` graph expansion with private codec requests and thin declarations. AST→ANF, optimization, RC insertion, MIR/LIR lowering, register allocation, and code generation treat codecs as ordinary functions.

Generated code: static field/variant dispatch, direct constructors, child-codec calls, scalar-policy selection.

Reusable runtime code: lexical parser, streaming cursor operations, span/raw-fragment handling, list/dictionary traversal mechanics, path manipulation, standard failures, number/string helpers, and writer mechanics.

Reader/writer helpers must not be inlined into every codec. Existing session caches may remain generic optimizations but are not the JSON architecture.

## Required compatibility

The pinned `docs/features/json-parity.md` contract is authoritative:

- Preserve comments/trivia, strict grammar, Unicode/surrogate behavior, exact numeric lexemes, integer range/exponent rules, and Int128/UInt128 fallback behavior.
- Preserve `NotJson`, all public `ParseError` variants, exact rendered wording, raw fragments, and leaf-first paths.
- Preserve ordered/duplicate object input, record unknown-field ignoring, duplicate detection, declaration-order missing-field checks, declaration-order child conversion failure, enum common-prefix conversion before arity errors, and source-order enum names in multiple-case errors.
- Reader views borrow source. Materialized fragments, decoded values, paths, errors, lists/dictionaries, and constructed records/sums are ordinary owned values subject to existing RC insertion. No manual ownership protocol, global state, exceptions, or sentinels.

## Migration

A. Record a clean post-merge timing JSON, full-suite timing, representative decode throughput, binary-size samples, and compact parity fixtures.

B. Build reader/writer lexical equivalence behind test-only comparison with `AltJson.__parseRaw`; do not route production typed JSON yet.

C. Migrate scalar and structural codecs, proving the compiler no longer generates full RawJson graphs for those shapes.

D. Migrate declaration-owned records/sums, aliases, generic instantiation, recursion, and mutual recursion with exact precedence fixtures.

E. Cut all supported typed JSON conversion to the new path; then remove the old generated RawJson codec path, its generated accessors, and its JSON-specific AST cache.

F. Consider separately pre-emitted native JSON runtime code only in a follow-up if post-cutover profiling shows reader/writer code generation and emission still comprise at least 25% of cumulative JSON compile time.

A checkpoint is rejected and reverted during development if compatibility, RC/leak checks, or its performance gate fails. There is no shipped old/new runtime fallback.

## Validation and thresholds

Run existing JSON corpus unchanged plus focused E2E cases for comments/trivia, trailing input, Unicode/surrogates, exact fragments, record and enum precedence, generic/recursive/mutually recursive types, and ownership-sensitive failures. Use temporary differential tests against the old path only until cutover.

Establish a commit-identified baseline with `--timings-json`, then report cumulative JSON compile multiplier, full-suite multiplier, per-pass totals, runtime throughput multipliers, binary-size samples, full test result, routine benchmark result, and the canonical `RESULTS.md` performance ratio.

Acceptance: at least 3.33× faster cumulative JSON E2E compile time; at least 2.0× faster full suite unless timing evidence shows non-JSON work dominates; no more than 10% decode slowdown for scalar/1KiB flat-record/1KiB collection payloads and 15% for 64KiB nested payloads; zero JSON compatibility or leak failures; routine benchmark verification with no regression.

## Success criteria

- Fresh design approval occurs before an implementation plan is prepared.
- All current JSON parity cases pass with unchanged values and error text.
- Clean timing data shows at least 3.33× JSON compile improvement and 2.0× full-suite improvement, or explains a measured non-JSON limit.
- Runtime decode thresholds, leak checks, full tests, and routine benchmark verification pass.
- The old generated RawJson codec implementation is removed after successful cutover.

## Response to feedback

The prior broad plan was not reviewable because it did not define the runtime ABI, semantics, codec lifecycle, compiler boundaries, checkpoints, or measurable rollback criteria.

## What changed

- Returns the issue to design and discards the broad implementation plan.
- Resolves semantic questions from the repository’s pinned parity contract.
- Defines private reader/writer APIs and borrowed-span ownership.
- Defines direct record/sum codec behavior and type-ownership rules.
- Defines staged migration, final deletion of the old path, exact performance thresholds, and conditional scope for pre-emitted runtime code.

## Why

The current parity contract fixes the observable behavior that a streaming implementation could otherwise accidentally change. Separating reusable reader/writer mechanics from small ordinary generated codecs preserves specialization while making the performance target testable and the migration safe.

## Conversation response

The issue remains in design. This replacement makes the reader/writer ABI, semantic preservation, codec derivation, compiler boundaries, migration gates, and performance acceptance criteria explicit before any implementation plan is created.
