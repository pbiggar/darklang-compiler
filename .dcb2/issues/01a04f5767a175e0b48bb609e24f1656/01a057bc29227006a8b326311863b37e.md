# Design brief

## Problem

Typed JSON conversion is currently specialized by expanding every Json.parse<T> and Json.serialize<T> call into a complete recursive Dark program. Each E2E assertion then recompiles JSON syntax traversal, RawJson inspection, collection recursion, error-path construction, and type-specific constructors through every compiler pass. The recent session cache reduced repeated planning/code generation but does not remove the generated graph from AST→ANF, RC insertion, MIR/LIR lowering, register allocation, final emission, or the per-executable binary.

## Goals

- Retain compile-time JSON target validation, exact nominal record/sum knowledge, direct typed native construction, and current source-level diagnostics.
- Replace whole-tree typed decoding with a reusable streaming JSON reader and compiler-derived thin codecs; do not introduce a general descriptor interpreter.
- Move common parsing, spans, container traversal, scalar extraction, error construction, escaping, and writer mechanics into reusable runtime support.
- Generate named-type codecs with their declarations, and generate only small compositional wrappers for structural applications.
- Preserve the pinned JSON wire contract and all observable parse-error behavior exactly.
- Reduce cumulative JSON E2E compile time by at least 70% against an established clean post-merge baseline, without an unacceptable decode-throughput regression.

## Proposed solution

## 1. Chosen architecture

The completed system has one production specialization path:

```text
Json.parse<T>(source)
  → type checking validates and resolves T
  → compiler selects/derives a private typed codec for T
  → reusable JsonReader streams source tokens and spans
  → typed codec directs reader/container operations
  → codec constructs T directly and returns Result<T, ParseError>

Json.serialize<T>(value)
  → compiler selects/derives a private typed codec for T
  → typed codec directs reusable JsonWriter operations
  → writer produces canonical JSON text
```

A codec is compiled native code, not an interpreted decoder descriptor. It owns statically known decisions: concrete numeric policy, tuple arity, record-field and enum-variant names, nominal constructor selection, and child codec calls. The reusable reader/writer owns repeated mechanics: lexical JSON parsing, comments/trivia, cursor advancement, source spans, container framing, common scalar validation, path extension, standard failures, JSON escaping, and ordered output buffering.

The old path—`__parseRaw` followed by a generated RawJson decoder graph—will be removed after compatibility and performance gates pass. It is retained only as a development oracle during migration, never as a runtime fallback or permanent compatibility mode.

## 2. Internal streaming reader API

`JsonReader` is compiler/runtime-private. It is not a public reflective `JsonDecoder` API and has no user-visible dynamic-value escape hatch.

### 2.1 Reader state and ownership

```text
JsonReader = {
  Source: String,
  Cursor: Int64,
  Limit: Int64,
  RootValidated: Bool
}

JsonSpan = {
  Start: Int64,
  EndExclusive: Int64
}

JsonValueView = {
  Span: JsonSpan,
  Kind: Null | Bool | Number | String | Array | Object
}
```

`Source` is an ordinary immutable managed Dark string owned by the top-level parse call. Reader, cursor, span, and value-view records borrow it semantically: they retain no substring and allocate no `InternalRawJson` node. Every operation that returns a reader returns a new immutable reader state; no global mutable reader, hidden session state, or exception-based control flow is introduced.

A span is a pair of byte offsets into the original UTF-8 Dark string. It remains valid for precisely the lifetime of the owning source string. A raw fragment is materialized only at an observable error boundary using `String.__byteSlice(Source, Start, EndExclusive)`. This preserves the current original-fragment wording while preventing eager source-slice allocation for successful decoding.

The reader owns lexical validation. It never exposes a partially valid value to a codec: a returned `JsonValueView` is syntactically complete. `parseRoot` consumes leading trivia, one complete value, trailing trivia, and then requires end-of-input. Any malformed lexical form, bad escape/surrogate pair, invalid number, unterminated comment, trailing comma, or non-trivia trailing input becomes `NotJson` before a typed codec observes a value.

### 2.2 Primitive operations

The internal API is deliberately narrow:

```text
parseRoot(source) -> Result<(JsonReader, JsonValueView), NotJson>

expectNull(reader, view) -> Result<Unit, TypeMismatchView>
expectBool(reader, view) -> Result<Bool, TypeMismatchView>
expectString(reader, view) -> Result<String, TypeMismatchView>
expectNumberLexeme(reader, view) -> Result<JsonSpan, TypeMismatchView>

beginArray(reader, view) -> Result<ArrayCursor, TypeMismatchView>
nextArray(cursor) -> Result<ArrayStep, NotJson>
finishArray(cursor) -> Result<Unit, NotJson>

beginObject(reader, view) -> Result<ObjectCursor, TypeMismatchView>
nextObject(cursor) -> Result<ObjectStep, NotJson>
finishObject(cursor) -> Result<Unit, NotJson>

skipValue(reader, view) -> Result<JsonReader, NotJson>
rawFragment(reader, span) -> String
extendPathField(path, name) -> JsonPath
extendPathIndex(path, index) -> JsonPath
```

`ArrayStep` is either `End` or `Element(index, JsonValueView, nextCursor)`. `ObjectStep` is either `End` or `Field(name, keySpan, valueView, nextCursor)`. Both cursors retain the original source and current cursor offset by value, use no mutation, and enforce separators/end delimiters. Object fields are yielded in source order; duplicate and empty names are preserved.

`TypeMismatchView` carries only `JsonValueView`; the codec converts it to the existing `CantMatchWithType(typeReference, rawFragment, path)` using its compile-time concrete type metadata. Standard error constructors remain the existing public `Stdlib.Json.ParseError.ParseError` cases.

### 2.3 Reader versus parser tree

`AltJson.parse` and the public `AltJson.Json` tree remain unchanged and continue to build ordered trees, because that is public behavior. Only typed `Json.parse<T>` stops calling `AltJson.__parseRaw`. The reader shares lexical helpers with AltJson where possible, but successful typed parsing does not allocate `InternalRawJson`, list nodes for every array item, object-field tuples, or per-node raw slices.

## 3. Internal writer API

`JsonWriter` is likewise runtime-private and owns canonical JSON syntax and escaping.

```text
JsonWriter.empty() -> JsonWriter
writeNull / writeBool / writeNumberLexeme / writeString
beginArray / elementSeparator / endArray
beginObject / writeFieldName / fieldSeparator / endObject
finish(writer) -> String
```

The writer preserves the current contract: compact output, canonical string escaping, record fields in ordinal name order, dictionaries in ordinal key order, arrays/list order, and enum one-field-object shape. Number formatting policy remains exactly where it is today for float and integer helpers; thin codecs select the correct reusable writer primitive rather than concatenate JSON strings themselves.

## 4. Concrete end-to-end decode example

For:

```dark
type Person = { Name: String; Age: Int64 }
Json.parse<Person>(source)
```

the compiler associates a private declaration-owned entry point conceptually equivalent to:

```text
Person.__jsonDecode(reader, value, path)
```

The generated body remains ordinary typed code and has direct `Person` construction. Its work is:

1. Call `beginObject`. A non-object produces `CantMatchWithType(Person, raw(value), path)`.
2. Consume fields through `ObjectCursor` in source order into a compact generated record-field state: `Name = unseen | seen(valueView)` and `Age = unseen | seen(valueView)`. Unknown fields are `skipValue`d.
3. If a declared field is observed a second time, return `RecordDuplicateField(fieldName, path)` immediately.
4. After the object ends, check required fields in declaration order. The first absent declared field returns `RecordMissingField(fieldName, path)`.
5. Decode `Name` and `Age` through their child codecs with `path.Field("Name")` and `path.Field("Age")`, in declaration order; the first child error wins.
6. Construct `Person { Name = decodedName; Age = decodedAge }` directly.

This keeps the existing observable semantics while centralizing object scanning, cursor/separator validation, source spans, duplicate tracking mechanics, raw-fragment slicing, and standard errors.

For a sum:

```dark
type Choice = No | Yes of String * Int64
```

`Choice.__jsonDecode` calls `beginObject`, requires exactly one field, captures the source-order list of case names for `EnumTooManyCases`, dispatches directly on `"No"` or `"Yes"`, uses a reusable array cursor for the payload, calls `String.__jsonDecode` then `Int64.__jsonDecode`, and directly emits `Choice.Yes(text, number)`. It uses the existing rule that child conversion of the common payload prefix occurs before reporting a later missing/extra argument.

## 5. Codec ownership and derivation

### Named types

Named records and sums own private codec definitions in the same compiler declaration context that defines their fields, type parameters, aliases, constructor tags, and ownership shapes. Conceptually, the compiler adds private companions:

```text
TypeName.__jsonDecode
TypeName.__jsonEncode
```

They are not source-visible names and are not user-overridable in this migration. This is the selected option-5 placement: named-layout logic is derived once with the declaration, rather than regenerated per call site.

### Structural types

Primitive, tuple, list, dictionary, Option, Result, and other structural applications receive compiler-internal composition wrappers. A wrapper contains only the necessary framing and statically known child-codec calls. It does not replicate scalar scanning, object traversal, list-loop mechanics, raw-fragment construction, or JSON string escaping.

### Generic types

A generic named declaration derives a codec template parameterized by child codecs for each type argument. Standard compiler monomorphization specializes that template at concrete applications, exactly as it handles other generic functions. The compiler validates the concrete JSON target before derivation and keeps the current unsupported-type diagnostics.

### Recursive and mutually recursive types

Derivation first builds one codec declaration graph for the complete recursive declaration group. It reserves each codec identity before deriving any body, so self and mutual calls bind directly and no placeholder runtime error can survive into emitted code. The same group owns compatible encode/decode codec pairs. Cycle handling remains ordinary direct native recursion and uses the existing recursion/RC analysis; it does not allocate a runtime descriptor or use dynamic dispatch.

### Local declarations

A type declared inside the source unit being compiled owns codecs in that source unit. It cannot be hoisted into a prebuilt stdlib/preamble context because its declaration identity is intentionally local. This is expected and remains correct; the new codec is still small because generic reader/writer mechanics are not generated into it.

## 6. Compiler-pass integration

| Stage | New responsibility | Ordinary generated code | Reusable runtime code |
|---|---|---|---|
| Parser | No JSON semantic change. | None. | None. |
| Type checking | Keep `Json.parse<T>` / `Json.serialize<T>` validation and unsupported-shape rejection. Resolve aliases and canonical nominal identities. | Type-reference/codec request annotations. | None. |
| JSON derivation pass | Replace full `ensureDecoder`/`ensureSerializer` AST graph generation with a codec request graph and thin private codec declarations. | Field/variant dispatch, typed construction, child codec calls, scalar policy selection. | Reader/writer calls. |
| AST→ANF and monomorphization | Treat private codec declarations as ordinary typed functions with compiler-owned identities; specialize generic codec templates. | Codec control flow that remains type-specific. | Calls to reader/writer helpers. |
| ANF optimization/inlining | Optimize small codec bodies, but do not inline reader/writer implementation into every codec. | Local direct construction and static dispatch. | Mark reusable reader/writer helpers as non-inline at this boundary. |
| RC insertion | Infer ownership normally for values constructed by codecs. | Record/sum/list/dict ownership at typed construction boundaries. | Reader spans/cursors borrow source; writer buffers own their produced text. |
| MIR/LIR/codegen | Compile reachable thin codecs and helper runtime normally, then tree-shake. | Per-type compact functions. | Shared JSON reader/writer functions. |
| Emit | No object-file/linker architecture in the first delivery. | Normal program output. | Normal prebuilt-stdlib participation. |

The current `PlanningSession` AST cache and generated raw-list accessor functions are superseded. Session codegen reuse may remain as a generic compiler optimization, but JSON correctness and performance must not depend on it.

## 7. Exact compatibility contract

The repository’s pinned `docs/features/json-parity.md` resolves the previous behavior questions. The new system must preserve all of the following exactly:

- **Grammar:** JSON whitespace; skipped line and block comments; strict literals; strict decimal/exponent syntax; UTF-16 surrogate-pair decoding; no trailing commas; no trailing non-trivia input.
- **Malformed input:** lexical, escape, numeric-syntax, comment, separator, and trailing-input failures return `NotJson`, never a typed mismatch or partial value.
- **Raw fragments:** `CantMatchWithType` and `EnumExtraField` use the exact original source slice for that complete value. They retain input whitespace inside the value span only where the present parser retains it; framing trivia remains outside the span.
- **Paths:** paths remain leaf-first `Root | Field | Index` lists and render root-to-leaf with the current `JsonPath.toString` output.
- **Integers:** retain exact number lexemes; preserve arbitrary `Int`, fixed-width range checks, exponent/integrality behavior, and the documented Int128/UInt128 binary64 fallback boundary.
- **Unicode:** preserve current JSON string unescaping and surrogate rules, and preserve `Char`’s one-extended-grapheme-cluster validation.
- **Objects:** retain source order, duplicate names, and empty names internally. Typed records ignore unknown fields, require declared fields, reject duplicate declared fields, and report missing fields in declaration order after scanning the object.
- **Error precedence:** this is not open. Typed record decoding must retain the current behavior: detect duplicate declared fields while scanning; after a successful syntactic object scan, report the first missing declared field in declaration order; then decode present declared fields in declaration order, so the first declaration-order child conversion failure wins. For enums, require exactly one field; preserve source-order names in `EnumTooManyCases`; decode the common argument prefix before emitting a later missing/extra-arity failure.
- **Reference counting:** reader/cursor/view values borrow the source and must never release it. Materialized raw fragments, decoded strings, paths, list/dict accumulators, error values, and constructed records/sums are ordinary owned values and pass through existing RC insertion. Every abandoned cursor/view on an error path must be structurally unreachable; no manual RC protocol or special sentinel is permitted.

## 8. Incremental delivery and safe migration

### Checkpoint A — semantics inventory and measurement baseline

Before changing behavior, capture a clean post-merge baseline using the existing JSON timing output and a dedicated decode-throughput harness. Add missing compact parity fixtures only where the pinned contract lacks an executable assertion: comments/trivia, source-order versus declaration-order failures, duplicate/missing precedence, raw fragments, Unicode surrogate pairs, and recursive/mutually recursive types.

### Checkpoint B — reader/writer lexical equivalence

Implement the reader/writer internals behind dedicated direct tests and E2E probes, without routing `Json.parse<T>` through them. Compare reader outcomes against `AltJson.__parseRaw` for valid syntax and against `NotJson` cases for malformed syntax. Keep this temporary comparison test-only; no production dual path.

### Checkpoint C — scalar and structural thin codecs

Route primitives, tuples, lists, dictionaries, Option, and Result through thin codecs and the reader/writer. Retain declaration-owned record/sum codecs on the old path only until their specific compatibility matrix passes. Confirm the compiler no longer generates raw-list accessor functions or complete decoder graphs for migrated shapes.

### Checkpoint D — records, sums, aliases, generic and recursive groups

Migrate declaration-owned codecs, then generic instantiation and recursive/mutually recursive groups. Require the exact object/sum error-precedence fixtures before each category is enabled.

### Checkpoint E — complete cutover

Route all supported `Json.parse<T>` and `Json.serialize<T>` through the new path. Delete generated RawJson decoder/encoder construction from `1.7_JsonPlanning.fs`, its AST cache contract, and raw-list accessor special cases. Preserve public AltJson tree parsing independently.

### Checkpoint F — optional option-6 decision

Do not pre-emit a separate native JSON object in this issue. After cutover, inspect pass timing. Create a separate design only if reusable JSON reader/writer code generation plus emission remains at least 25% of cumulative JSON compile time after thin-codec migration. The initial result should use normal prebuilt stdlib/runtime integration; object-format/linker work is not justified before that evidence.

At each checkpoint, a regression in output, error type/text/path/raw fragment, RC/leak behavior, or target parity blocks progression. The safe rollback during development is to revert the incomplete checkpoint; it is not a shipped runtime fallback.

## 9. Validation and performance contract

### Focused tests

- Existing `src/Tests/e2e/json-parity.e2e` and upstream `stdlib/json.dark` unchanged.
- New compact E2E cases for lexical comments/trivia, trailing input, escaped Unicode/surrogates, exact raw fragments, record order/duplicate/missing precedence, enum prefix/arity precedence, generic record/sum, self recursion, mutual recursion, and ownership-sensitive nested values.
- Compiler-pass tests for codec identity/ownership, generic codec specialization, recursive codec-group reservation, and rejection of unsupported types.
- Leak-check E2E coverage for nested string/list/dict/record/sum success and failure paths.
- Differential test-only oracle cases compare the new reader/codec output to the legacy generated path until cutover; remove the legacy oracle after its production path is removed.

### Established baselines and reports

Create the exact clean baseline before implementation with:

```bash
./run-tests --ai --build-only
bin/Tests/Debug/net10.0/Tests --ai --filter=json --timings-json=/tmp/json-before.json
./run-tests --ai
./benchmarks/run_benchmarks.sh --verify routine
```

The baseline report records test count, wall time, cumulative JSON compile time, cumulative JSON runtime time, pass totals, binary-size samples, and the slowest JSON tests. It must identify the exact commit and contain the timing JSON artifact. The historical anchors remain context only: pre-cache full suite 1,236.8s; post-merge full suite 858.4s for 8,504 tests; representative `json-parity` compile total 26,462ms → 15,621ms.

After every checkpoint, compare sums from timing JSON rather than contended wall-clock alone. At final validation report:

- JSON compile-speed multiplier: `baseline cumulative JSON compile ms / candidate cumulative JSON compile ms`;
- full-suite speed multiplier: `baseline full-suite elapsed / candidate full-suite elapsed`;
- JSON runtime multiplier for each representative payload class;
- routine benchmark verification decision and the `RESULTS.md` table-header performance ratio, as required by repository policy.

### Acceptance thresholds

- Cumulative JSON E2E compile time: at least **3.33× faster** (at least 70% lower) than the clean post-merge baseline.
- Full-suite elapsed: at least **2.0× faster** than the same clean baseline, unless timing JSON shows non-JSON work has become the dominant limiter; if so, report the causal breakdown rather than claiming success from the JSON-only target.
- Decode throughput: no more than **10% slower** for scalar, 1KiB flat-record, and 1KiB collection payloads; no more than **15% slower** for 64KiB nested record/sum payloads. Any regression beyond these thresholds rejects the checkpoint unless explicitly redesigned and re-approved.
- Semantics: zero JSON parity failures; no changed expected error strings; no RC/leak-check failures.
- Compiler performance: routine benchmark verification passes with no regression; report the canonical performance ratio.

## 10. Explicit exclusions

- No general runtime descriptor interpreter.
- No retention of the old generated RawJson codec path after complete migration.
- No weakening, batching, skipping, or reclassifying JSON E2E cases to manufacture a speed result.
- No public user-authored codec API in this issue; custom codec design is a separate product decision.
- No pre-emitted native object/linker format work without the post-cutover 25% timing trigger.

## Success criteria

- A fresh review accepts this replacement design before any implementation plan is created.
- The final implementation preserves the entire pinned JSON parity contract, including exact error text, paths, raw fragments, comments/trivia, numeric behavior, Unicode behavior, object semantics, and ownership behavior.
- Clean timing JSON demonstrates at least 3.33× JSON compile speedup and at least 2.0× full-suite speedup against the recorded post-merge baseline, or provides an evidence-backed explanation if non-JSON work becomes dominant.
- Representative decode benchmarks remain within the defined 10%/15% runtime thresholds.
- All tests, leak checks, routine benchmark verification, and canonical performance-ratio reporting pass.
- The old generated RawJson JSON codec path is deleted after cutover; only the new typed streaming codec path remains in production.

## Open questions

- None for this issue. The public custom-codec API and a separately pre-emitted native JSON runtime object are explicitly deferred, with the latter gated by post-cutover profiling rather than an unresolved design choice.

## Response to feedback

The previous plan collapsed a high-risk compiler/runtime migration into one work item. The requested replacement must be a reviewable design that specifies interfaces, lifetimes, compiler boundaries, observable semantics, migration checkpoints, measurement thresholds, and rollback decisions before implementation is reconsidered.

## What changed

- Atomically returns the issue from implementation planning to fresh design review and discards the broad implementation plan.
- Resolves error-precedence, runtime-threshold, and public-codec questions from repository evidence or explicit scope decisions.
- Defines concrete internal reader/writer, cursor, span, raw-fragment, and ownership models.
- Adds concrete record and sum decode flows, plus named/structural/generic/recursive codec ownership rules.
- Separates reusable runtime work from ordinary generated code at every compiler pass.
- Adds staged cutover gates, differential test-only oracle use, exact baseline commands, acceptance multipliers, benchmark reporting, and a conditional trigger for option 6.

## Why

The repository already has a pinned JSON parity contract that fixes most semantic questions. Making that contract, rather than an aspirational architecture, the migration boundary prevents a streaming implementation from silently changing errors or ownership behavior. The detailed runtime ABI and compiler-pass placement make code review possible before implementation, while staged checkpoints contain risk and make the performance claim falsifiable.

## Conversation response

I have withdrawn the accepted design and discarded the single broad implementation plan. This replacement is a complete technical design for fresh review; it does not request implementation approval.

The material change is that the design no longer treats “streaming reader plus thin codecs” as a broad direction. It defines the internal ABI, observable compatibility contract, codec ownership, compiler-pass boundaries, staged migration, test gates, and measured exit criteria. It also resolves the previously open behavior questions from the pinned JSON parity contract: existing error precedence and error text are compatibility requirements, not product choices.
