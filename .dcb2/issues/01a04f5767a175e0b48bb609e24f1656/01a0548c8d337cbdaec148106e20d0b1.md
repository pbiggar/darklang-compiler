# Design brief

## Problem

Every Json.parse<T> and Json.serialize<T> currently expands into a large, type-directed ordinary Dark program. The compiler repeatedly lowers and emits JSON syntax traversal, raw-tree matching, path/error propagation, and type-specific construction for hundreds of independent E2E executables, even though most of that logic is reusable.

## Goals

- Massively reduce JSON-related compile time while preserving compiled, type-specific native codecs rather than a general descriptor interpreter.
- Retain compile-time validation, nominal record/sum construction, exact JSON error behavior, and strong runtime performance.
- Eliminate whole-raw-tree allocation for successful typed decoding where compatibility permits.
- Make named type codec ownership explicit and compile codecs with the declarations that define their layouts.

## Proposed solution

Use compiler-derived thin codecs over a reusable streaming reader/writer runtime. Generate direct type-specific code only for statically known fields, variants, scalar policies, and Dark value construction; centralize syntax parsing, container traversal, source spans, paths, standard errors, and common collection mechanics in reusable runtime support.

## Success criteria

- All existing JSON E2E behavior passes unchanged, including error text/path/raw-fragment compatibility and user-defined record/sum cases.
- A clean timing comparison shows at least a 70% reduction in cumulative JSON E2E compile time against the current post-merge baseline, with results grouped by compiler pass.
- The full test suite passes without disabled or weakened JSON cases.
- Representative scalar, nested collection, record, and sum decode throughput is measured; no material regression is accepted without an explicit follow-up decision.
- The completed implementation has one JSON specialization path; the old full generated-decoder path is removed.

## Open questions

- Should exact current record-error precedence be preserved when malformed/duplicate/missing fields occur in different source orders, or is a documented behavior change acceptable?
- What runtime-performance threshold is acceptable for representative deeply nested JSON payloads relative to the present fully specialized decoder?
- Should declaration-owned codecs become a purely internal compiler representation first, or should Dark eventually expose an explicit user-authored codec API?

## Conversation response

Design: replace per-call JSON decoder expansion with compiler-derived, type-specific codecs driven by a reusable streaming JSON runtime.

This adopts options 2 and 3 together, incorporates declaration-owned codecs from option 5, and defers option 6 until profiling proves native runtime pre-emission is needed. It explicitly excludes the rejected fully interpreted descriptor approach and excludes caching fully lowered current decoder functions.

## Core model

Keep the public surface unchanged:

```dark
Json.parse<T>(text) : Result<T, Json.ParseError>
Json.serialize<T>(value) : String
```

Keep compile-time validation of `T`, alias resolution, nominal record/sum knowledge, integer-width semantics, and source-level diagnostics.

Replace the current expansion:

```text
Json.parse<T>
→ parse complete InternalRawJson tree
→ generate a complete recursive decoder graph for T
→ compile that graph as ordinary Dark code
```

with:

```text
Json.parse<T>
→ create streaming JsonReader over source text
→ call compiler-derived decode_T(reader, path)
→ generated codec drives reusable reader/container operations
→ construct T directly
```

The codec remains compiled native code and remains specific to `T`. It is not a generic runtime interpreter. The reusable runtime owns JSON syntax scanning, cursor movement, object/array framing, source spans, common scalar extraction, path construction, and standard error creation. The generated codec owns type-specific decisions and direct Dark value construction.

## Runtime boundary

Introduce an internal JSON decoding runtime, initially as compiler/runtime support rather than a public reflective API.

Its conceptual operations are:

```text
Reader.create(source)
Reader.expectNull / expectBool / expectString / expectNumberLexeme
Reader.beginArray / ArrayCursor.next / ArrayCursor.finish
Reader.beginObject / ObjectCursor.next / ObjectCursor.finish
Reader.skipValue
Reader.rawSliceAtCurrentValue
Reader.failNotJson / failTypeMismatch / failMissing / failDuplicate / failArity
Path.root / Path.field / Path.index
```

The reader is streaming and retains the original source plus token spans. It does not construct `InternalRawJson` for successful typed decoding. When an error requires the original JSON fragment, it creates that fragment lazily from the stored source span. This preserves the present `ParseError` contract without requiring a whole raw JSON tree.

The runtime must be able to distinguish malformed JSON from valid JSON with the wrong target type, preserve comment/trivia behavior currently accepted by `AltJson`, and retain exact integer lexemes for arbitrary-precision and fixed-width integer conversion.

## Generated codec shape

`JsonPlanning` becomes a derivation pass rather than a full decoder-program generator. For every concrete type it produces a private codec entry point with a typed result.

```text
decode_T(reader, path) -> Result<T, Json.ParseError>
encode_T(writer, value) -> Unit
```

Generated code is deliberately thin.

- Scalars select the correct reusable scalar operation and retain only compile-time-known conversion policy, such as `Int64` range validation or `Char` grapheme validation.
- Lists and dictionaries call reusable array/object iteration mechanics; generated child-codec references remain statically known.
- Tuples retain direct positional construction but use reusable array-length/cursor operations.
- Records retain direct named-field and record construction logic. The generated codec owns the statically known field table and calls reusable object traversal/duplicate/missing-field helpers.
- Sums retain a direct compiler-generated dispatch over known variants and direct constructor calls. The runtime owns object framing, tag extraction, payload cursor framing, and common wrong-shape/arity errors.
- Serialization is migrated symmetrically to a reusable `JsonWriter` plus derived type-specific encode functions, so `Json.serialize<T>` stops generating large concatenation/match graphs as well.

This preserves native direct construction of records and tagged sums, avoids runtime reflection, and leaves a small amount of specialization exactly where it provides useful performance and feedback.

## Declaration ownership

For named records and sums, generate the private codec alongside the declaration, following the placement used by OCaml JSON PPX tools. A `Person` declaration owns `Person.__jsonDecode` and `Person.__jsonEncode`; its field layout and variant tags are therefore resolved once in the declaration’s authoritative context.

Structural compositions such as `List<Person>`, tuples, `Option<Person>`, `Result<A, B>`, and dictionaries receive small compiler-generated composition wrappers. Generic declarations receive codec bodies parameterized by their child codecs and are specialized only at concrete type application boundaries. This avoids re-emitting a named record/sum’s field or variant logic at every `Json.parse<T>` call.

## Compiler pipeline changes

1. Type checking continues to validate JSON target types and resolve aliases exactly as now.
2. Replace `rewriteProgramWithSession`’s generated recursive AST decoder graph with private codec declarations/calls.
3. Teach AST→ANF and monomorphization about internal codec declarations and child-codec references.
4. Add the reusable reader/writer support to the ordinary base runtime/stdlib compilation context.
5. Tree shaking retains only runtime operations and derived codecs reachable from a program’s JSON calls.
6. Remove the superseded generated-decoder path once behavior and performance validation are complete.

The first implementation should decode directly from a reader. Do not keep a production fallback that chooses between `InternalRawJson` plus old generated decoders and the new system; the test suite may compare implementations during development, but the completed migration has one authoritative path.

## Compatibility constraints

The migration is correct only if it preserves all existing observable JSON behavior:

- public API and compile-time unsupported-type errors;
- `ParseError` variants and rendered text, including `NotJson`, original raw fragments, and JSON paths;
- duplicate/missing record-field behavior;
- sum tag and payload arity behavior;
- aliases, records, user sums, nested collections, `Option`/`Result`, arbitrary integers, fixed-width integer limits, floats, Unicode strings, and comments/trivia;
- native ownership/reference-count correctness for strings, raw slices, lists, dictionaries, records, sums, and errors.

A streaming decoder has one subtle compatibility risk: the current record decoder checks declared fields in declaration order after parsing the full object. A one-pass reader naturally sees JSON source order. The design must specify and test the existing error-precedence behavior before implementation; the reader may need a compact per-object field index/spans rather than a wholly one-pass record decoder to preserve it exactly.

## Option 6 decision

Do not make a pre-emitted native JSON runtime object part of the initial design. The derived codecs and streaming runtime remove the large repeated generated-code graphs; existing stdlib precompilation and the recent session cache should then make backend emission much smaller. Only introduce separately pre-emitted/linkable runtime code if a post-migration timing profile shows the shared reader/writer itself remains a meaningful repeated codegen cost. That keeps object-format, relocation, and cross-target complexity out of the primary semantic migration.
