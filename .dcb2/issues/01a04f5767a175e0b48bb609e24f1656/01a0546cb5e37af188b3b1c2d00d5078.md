Yes. The useful middle ground is **not** a generic descriptor interpreter, and it is **not** the current “generate the whole decoder as bespoke Dark code on every use.” It is to compile a small, type-specific codec once, while moving repeated JSON mechanics into reusable runtime operations.

Other ecosystems split the work this way:

- Rust Serde derives a `Deserialize` implementation per data type, but the implementation is driven by a reusable `Deserializer` and visitor/container interfaces. The generated code supplies type-specific construction and validation; the format library supplies tokenization and traversal. [Serde’s `Deserialize` model](https://serde.rs/impl-deserialize.html), [derive overview](https://serde.rs/derive.html)
- OCaml `ppx_deriving_yojson` generates two conversion functions per declared type (`*_of_yojson` and `*_to_yojson`) over a reusable `Yojson.Safe.t` representation. It does not regenerate those functions at every call site. [ppx_deriving_yojson](https://github.com/ocaml-ppx/ppx_deriving_yojson)
- Swift synthesizes type-specific decoding initializers, but they operate through reusable keyed/unkeyed/single-value decoding containers rather than parsing and matching JSON directly. [Swift keyed decoding container](https://developer.apple.com/documentation/swift/keyeddecodingcontainer?changes=_4)
- Kotlin serialization generates a serializer per class. That serializer has a structural descriptor and calls reusable `Decoder`/`CompositeDecoder` operations to decode fields; custom serializers can replace or wrap the generated one. [Kotlin serialization documentation](https://kotlinlang.org/docs/serialization-create-and-use-serializers.html)

Dark currently combines all three layers into every `Json.parse<T>` expansion:

```text
JSON syntax parsing + raw-tree traversal + field/variant matching
+ path/error construction + type-specific value construction
```

The repeated compile cost comes mainly from re-lowering the enormous expanded control flow, not from the fact that the compiler knows `T`. The best options preserve compile-time knowledge of `T` while changing what is specialized and when.

| Option | What remains specialized | What becomes reusable | Expected compile impact | Runtime trade-off |
|---|---|---|---|---|
| 1. Hoist and fully compile codecs once per type/context | The current direct decoder functions | Nothing semantic; reuse already-allocated LIR/native-function artifacts | High for the test corpus; lowest semantic risk | None or negligible |
| 2. Derived per-type codecs over runtime containers | Record fields, sum variants, tuple arity, concrete constructors | Raw JSON traversal, field lookup, list/dict iteration, path/error plumbing, numeric conversion | Very high; much smaller generated functions | Small dispatch/call overhead |
| 3. Serde-style generated visitors | Type-specific visitor callbacks and constructors | Streaming JSON parser drives the visitor | Very high, plus removes raw-tree allocation | More invasive; must preserve error behavior |
| 4. Hybrid staged decoder IR | Static construction and known shape decisions | Generic operations selected by a compact internal decoder IR | High and tunable | Can specialize hot/simple cases |
| 5. Derive codecs at declarations, not calls | One codec per named type, generic composition at instantiation | Codec bodies compiled with their declaring module/preamble | High for named records/sums | Minimal |
| 6. Pre-emitted reusable JSON runtime object | None of the decoder shape alone | Native JSON support code is emitted once, linked/referenced repeatedly | Complementary, not sufficient alone | None |

## 1. Hoist current codecs to a compiled artifact cache

This is the most direct continuation of the recent merge.

Today `PlanningSession` caches generated decoder **AST** and `CompilationSession` sometimes caches final ARM64 instructions for equal non-entry LIR functions. The decoder still undergoes AST→ANF, optimization, RC insertion, MIR, LIR, and register allocation for each test executable before the ARM64 cache is consulted.

Instead, build each JSON codec once per `(resolved type graph, declaration-context fingerprint, target, compiler-options)` and retain its fully lowered, register-allocated LIR functions in the suite/preamble compilation context. A later `Json.parse<T>` would add only a call to those functions; it would not recompile their bodies.

This preserves every current semantic property: direct native control flow, exact existing path/error text, direct record/sum construction, and no runtime decoder abstraction. It is especially suited to the test corpus because `buildSuiteContexts` already scans all tests and collects type specializations before compiling them.

The limitation is scope: a codec for a type declared locally inside an individual executable cannot be prebuilt from the shared context. Those cases fall back to local compilation. It also does not reduce the code emitted into each final binary; it removes repeated compiler work.

## 2. Generate thin codecs over reusable JSON operations

This is the strongest non-interpreter middle ground, and the closest match to Swift/Kotlin/Serde.

Keep a generated function per concrete Dark type, but change its shape. For example, instead of generating a record decoder containing raw-object inspection, `__matchingFields` calls, duplicate/missing checks, path-list construction, result propagation, and nested decoder matching, generate a thin codec that asks reusable runtime operations for fields and invokes child codecs:

```text
Person.decode(raw, path):
  fields = JsonRuntime.expectObject(raw, path)
  name = JsonRuntime.requiredField(fields, "name", path) |> String.decode
  age  = JsonRuntime.requiredField(fields, "age", path)  |> Int64.decode
  Person(name, age)
```

For sums, the generated codec selects the known constructor table and calls a reusable tagged-union helper. Lists and dictionaries use reusable loops instead of generating recursive functions. Numeric lexeme normalization and standard errors already have natural homes in the JSON runtime.

The compiler still provides excellent feedback because it validates supported `T`, resolves aliases and nominal declarations, generates direct typed constructors, and can point errors at the `Json.parse<T>` call. It just stops compiling generic mechanics into every decoder body.

This reduces code size much more than option 1 and should improve application compile time too. Runtime performance remains largely static: fields/variants are known by generated code, while only common mechanics are indirect.

## 3. Serde-style streaming visitors

Avoid building `InternalRawJson` for typed parsing. The reusable parser reads tokens and calls a generated, type-specific visitor: record visitors request named fields, list visitors request repeated elements, sum visitors request a tag/payload, and scalar visitors validate concrete numeric/string rules.

This has the best potential runtime profile for large inputs because it avoids the raw JSON tree and can short-circuit early. It also substantially reduces generated code because the parser owns syntax traversal and most failure handling.

It is higher risk than option 2. Dark’s current public behavior deliberately retains source slices and exact JSON paths in `ParseError`; a streaming design must preserve those semantics, including duplicate fields, malformed JSON versus type mismatches, fixed-width integer behavior, and detailed nested errors. It is a worthwhile long-term architecture, but not the first test-speed change.

## 4. Introduce an internal staged `JsonCodec<T>` IR

This is a compiler-internal representation, not a general user-visible interpreter. `JsonPlanning` would produce typed codec nodes such as `Int64`, `List child`, `Record(fields, constructor)`, and `Sum(variants, constructors)`. The backend then chooses a lowering strategy:

- emit a direct specialized codec for small/simple shapes;
- emit a thin codec calling reusable helpers for wide records, collections, and deeply nested sums;
- reuse a fully lowered codec artifact whenever the key matches.

That gives a controlled code-size/runtime-performance policy instead of one all-or-nothing implementation. It also creates a stable boundary for options 1 and 2: the current generator becomes one lowering of the codec IR, rather than the authoritative representation.

## 5. Derive codecs with type declarations

Borrow the OCaml PPX placement rule: generate codecs when a record/sum is declared, rather than independently at each `Json.parse<T>` call.

For a named `Person`, the compiler creates private `Person.__jsonDecode` and `Person.__jsonEncode` once as part of its declaration/preamble compilation. Generic containers compose those existing codecs. This makes ownership, invalidation, and diagnostics clear, and it aligns perfectly with the fact that a record’s field and sum’s variant structure are declaration-owned.

It does not fully solve arbitrary structural types such as `Result<List<Dict<String, Option<Int64>>>, String>`; those need small composition wrappers or a codec IR. It is therefore best paired with option 2 or 4.

## 6. Pre-emit the reusable runtime separately

The compiler already reuses preallocated stdlib LIR but still emits native instructions and assembles a complete executable for every test. Pre-emitting the JSON runtime into a reusable object/code blob would reduce repeated backend work for the common JSON parser/helpers.

This helps only after options 1–4 shrink the user-specific code. On its own, it leaves the current giant generated decoders untouched, so it should be treated as a later complementary backend improvement.

## Recommended path

1. Implement **option 1** first: promote JSON artifacts from AST/codegen caches to suite-context, fully lowered codecs. It is a bounded extension of the merged cache, keeps runtime performance and semantics unchanged, and should remove nearly all repeated codec lowering from the 420 parse tests.
2. In parallel, define the internal codec representation in **option 4**, but initially lower it to the current direct functions. This makes the cache key and ownership model explicit.
3. Replace repeated list/dictionary/raw-object/path/error mechanics with reusable helpers (**option 2**), retaining generated direct construction for records, sums, and scalar conversion selection.
4. Evaluate streaming visitors (**option 3**) only after the compile-time gain is measured and only if JSON runtime throughput/allocation is also important.

This avoids the unwanted full interpreter while preserving static specialization where it matters: construction of Dark nominal values, field/variant knowledge, integer-width rules, compile-time unsupported-type feedback, and direct calls for small/hot codecs.
