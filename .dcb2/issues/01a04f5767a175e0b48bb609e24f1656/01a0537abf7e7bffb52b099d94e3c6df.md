The recent merge fixed a real part of the problem, but the remaining bottleneck is still the test model for typed JSON—not test-host overhead or slow program execution.

The merged session cache reduced the representative `json-parity` compilation total from **26,462 ms to 15,621 ms (-41.0%)**, primarily by reducing Code Generation from **21,280 ms to 13,368 ms (-37.2%)**. The full post-merge suite nevertheless still took **858.4s** for 8,504 tests, so it remains far too slow for routine iteration.

The source is `src/Tests/e2e/upstream/stdlib/json.dark`: its large typed-JSON parsing corpus contains roughly 420 independently compiled parse assertions. Each assertion creates a distinct native program. Even after session-scoped reuse, each one still performs per-case parsing/type checking, AST→ANF, MIR/regalloc for the entry program, final layout/encoding, writes a binary, starts it, and validates it. The cache can reuse generated decoder planning and non-entry ARM64 symbolic functions, but it cannot remove that per-executable work.

Earlier full timing evidence isolated the same mechanism: 420 `Stdlib.Json.parse` cases consumed 811s of a 1,237s run, while all test runtime was only 13.5s. Code generation was 798s. This is therefore not an individual pathological test, a sleep/timeout, or build time.

The next material improvement is to change execution granularity for compatible JSON assertions: compile groups of same-context success/error assertions into one native test program with an assertion harness that preserves source-line/case diagnostics. Keep isolated E2E programs for compile-error behavior, process/stdio boundaries, and cases that require executable isolation. This preserves coverage while eliminating repeated compiler and executable-startup work; the prior profile suggests a multi-minute reduction is available, whereas further cache tuning alone is unlikely to be comparable.

Before implementation, establish a clean full-suite `--timings-json` artifact and report totals grouped by source file, compile/runtime, and compiler pass. That becomes the acceptance baseline; wall-clock-only comparisons are unreliable under concurrent worktree load. No files were changed.
