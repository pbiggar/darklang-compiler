`Json.parse<T>` is not a call to one generic runtime parser in the compiled program. It is a compile-time specialization system that turns `T` into a bespoke, monomorphic Dark decoder graph. That is the core reason the work is expensive.

For a source assertion such as:

```dark
Stdlib.Json.parse<Result<Result<Option<Result<Int64, String>>, String>, String>> json
```

the compiler first type-checks the call and obtains its concrete `T`. Then [`1.7_JsonPlanning.fs`](src/DarkCompiler/passes/1.7_JsonPlanning.fs) replaces the generic intrinsic with two things:

1. A call to `Stdlib.AltJson.__parseRaw`, which parses text into the internal `RawJson` tree.
2. Generated ordinary Dark functions that recursively convert that tree into exactly `T` and produce a typed `Result<T, Json.ParseError>`.

The generated decoder is structural and monomorphic:

- A numeric leaf checks `RawNumber`, normalizes integer lexemes, parses an arbitrary `Int`, performs the requested fixed-width conversion, and constructs an error with the original JSON and JSON path on every failing branch.
- A list creates a recursive list decoder, increments an index path at every element, decodes each element, and propagates the first structured error.
- A dictionary creates a recursive field decoder, updates the persistent dictionary, and constructs field-path errors.
- A tuple emits a fixed-arity raw-array pattern plus one nested decode and error-propagation chain per element.
- A record emits, for every declared field, a lookup for matching raw fields, missing/duplicate-field handling, a nested decoder invocation, and construction of the typed record.
- A sum emits code for **every variant**. For every payload field of every variant it emits missing/exact/extra arity paths, nested decoding, variant construction, invalid-case handling, and too-many-case handling.

So the nested `Result<Result<Option<Result<Int64, String>>, String>, String>` example does not become one short generic call. It produces individual decoders for the outer and inner `Result`s, `Option`, `Int64`, and `String`, plus explicit match/error-control-flow for all of their variants. A wide record or sum grows with every field/variant; nesting composes those graphs. This is deliberately how the compiler obtains type-directed JSON semantics and precise errors without runtime reflection.

After planning, the generated functions take the normal compiler path for each E2E assertion:

| Stage | Work repeated for the generated JSON graph |
|---|---|
| Parse and type checking | Parse the synthesized assertion program and type-check it against the prebuilt stdlib/preamble context. |
| JSON planning | Scan the typed AST for JSON intrinsics; resolve aliases, records, and sums; form a declaration-context fingerprint; retrieve or build generated decoder AST. |
| AST → ANF | Convert generated decoders and the assertion into ANF; monomorphize/rewrite calls and construct the entry function. |
| ANF work | Optimize, inline, specialize direct/higher-order calls, then insert retain/release operations for all managed raw JSON, strings, lists, dictionaries, results, and error-path values. |
| MIR/LIR work | Build CFGs, convert to SSA, optimize MIR, lower to LIR, peephole-optimize, and allocate registers. |
| Link-like assembly | Tree-shake reachable stdlib functions, combine them with the generated/user functions, form type/variant metadata, and generate the whole executable. |
| Native output | Select ARM64 instructions, resolve labels/literal pools/layout, encode Mach-O/ELF bytes, write and execute a fresh binary. |

The recent 40% merge only reuses two layers:

- `PlanningSession` stores the generated JSON **AST** by resolved type set plus declaration-context fingerprint. On a hit it avoids regenerating that AST, but the retrieved functions still go through AST→ANF, optimization, RC insertion, MIR, LIR, register allocation, and binary construction for the next executable.
- `CompilationSession` can reuse ARM64 symbolic instruction output for structurally identical non-entry allocated LIR functions. It does not reuse the entry function, whole-program tree shaking/layout, binary encoding, or process execution. It also does not apply to the x86-64 backend.

This explains both results at once: the representative JSON workload improved 41% because large decoder codegen is reusable, yet the full suite remains slow because every one of roughly 420 parse assertions still drives a complete native-compilation pipeline and emits/runs a distinct executable.

The expensive residual work is therefore not JSON *runtime parsing*. It is repeated ahead-of-time compilation of mostly the same type-directed decoder graphs and their reachable support code. The pre-merge full profile measured only 13.5s of runtime across the suite, versus 798s in code generation; after the merge, the unreused lowering, entry-program, final-emission, and process-per-case work remains the limiting factor.

A massive improvement requires reducing this compilation multiplicity: compile many assertions that share a declaration context into one generated test program, while retaining an assertion identifier/line number and independently reporting failures. That would compile each decoder shape and shared support graph once per batch rather than once per source assertion. The existing caches remain useful within that design, but cannot by themselves remove the repeated pipeline work because their current reuse boundary is below and after much of it.
