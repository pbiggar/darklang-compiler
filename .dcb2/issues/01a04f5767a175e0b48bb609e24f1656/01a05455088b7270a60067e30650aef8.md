Yes—an Elm-like decoder architecture could remove most of the remaining JSON compile cost. But the benefit comes only if it replaces generated decoder *code* with a reusable runtime decoder interpreter plus compact per-type decoder descriptions. Simply moving today’s generated functions into the stdlib would not materially help.

Today the public API is effectively a compiler intrinsic:

```dark
Json.parse<T>(text) -> Result<T, Json.ParseError>
```

`Json.dark` deliberately defines `Json.parse` and `Json.serialize` as functions that fail if they are not specialized. The type checker recognizes those two names, validates `T`, and `JsonPlanning.rewriteProgramWithSession` replaces the call. The current runtime already handles the first half—`AltJson.__parseRaw` parses JSON text into `InternalRawJson`—but the second half, conversion of `RawJson` to `T`, is emitted as a new program-specific decoder graph.

Elm’s model is different. A decoder is an ordinary runtime value assembled from reusable combinators such as `int`, `string`, `list`, `field`, `oneOf`, `map`, and `andThen`; a generic runtime engine interprets that value against JSON. The type parameter is checked by Elm’s compiler, but it does not cause a bespoke native function graph to be emitted for every use.

Applied here, the equivalent internal representation would be conceptually like this:

```text
Decoder<Int64>
  = integer(Int64 conversion rules)

Decoder<Result<Int64, String>>
  = taggedSum(
      "Result",
      [ "Ok" -> positional [integer(Int64 rules)]
      , "Error" -> positional [string]
      ])
```

The native runtime would contain one reusable evaluator:

```text
runDecoder(descriptor, rawJson, path) -> Result<runtime value, ParseError>
```

It would recursively inspect the descriptor and `InternalRawJson`, keep the exact existing error-path rules, and construct the requested result, tuple, list, dictionary, record, or sum value. A given type would contribute a small immutable descriptor, rather than several generated Dark functions containing all success, failure, missing-field, duplicate-field, wrong-arity, and nested-propagation branches.

This directly attacks the expensive work:

| Current model | Descriptor-runtime model |
|---|---|
| Every `T` emits one decoder function per reachable structural node, plus recursive list/dictionary helpers. | One shared decoder engine; each `T` emits or references compact descriptor data. |
| Every generated branch passes through ANF optimization, inlining, RC insertion, CFG construction, SSA, MIR optimization, LIR lowering, register allocation, and code generation. | The engine is compiled once as reusable runtime/stdlib support; per-type work is descriptor construction and a call. |
| A sum compiles all variants and their missing/exact/extra payload cases into native control flow. | The engine loops over descriptor entries at runtime. |
| Nested types increase generated function/control-flow size before every test executable is built. | Nested types increase descriptor size, but not native code size proportionally. |

The expected compile-time impact is large because the old full profile was dominated by generated decoder code generation (798s of 1,237s pre-cache). The recent cache helps after lowering has already happened; a descriptor architecture removes the generated functions from AST→ANF, RC, MIR, LIR, allocation, and most code generation in the first place. It would also reduce binary size and final encoding/layout work. For the JSON E2E corpus, it is a much more fundamental reduction than the 40% cache win.

There are two important caveats.

First, moving the current generated decoder bodies into `Stdlib.Json` without changing their shape does not solve the problem. They remain monomorphic functions whose source must be instantiated for `T`; the compiler would still lower and emit them. The essential change is from **specialized executable code** to **data interpreted by shared executable code**.

Second, Dark does not currently have the runtime reflection machinery this needs. `T` may be a nominal record or sum defined by the user. The current compiler knows field order/types, variant tags, payload layout, aliases, and how to generate allocation code; the runtime does not have a general facility to dynamically construct an arbitrary typed record/sum from a descriptor. A real implementation must therefore introduce a controlled internal decoder ABI:

- a runtime descriptor format for scalar conversions, list/dictionary/tuple children, record fields, sum variants, and error semantics;
- runtime type/constructor metadata sufficient to allocate Dark records and tagged sums correctly, including managed-pointer ownership and reference counting;
- compiler emission of descriptor constants for each concrete `T`, resolving aliases and nominal declarations exactly as `JsonPlanning` does today;
- an opaque boundary that restores the statically known `T` only after the runtime decoder has constructed a valid value; and
- an equivalent serialization story if `Json.serialize<T>` is also migrated, since it currently uses the same compile-time specialization model.

There is a middle ground that is likely lower risk: keep compile-time type resolution, but have it emit a compact, typed internal descriptor and call a runtime interpreter. This retains the existing API and compile-time rejection of unsupported types, avoids public reflection, and preserves precise error messages. It is closer to Elm’s underlying idea while fitting this compiler’s AOT, nominal-type, and reference-counting model.

The trade-off is runtime performance. Generated decoders use direct native calls and pattern matches; an interpreter adds descriptor dispatch, indirect construction, and likely more allocations. For normal applications that may be slower, especially for deeply nested or large JSON payloads. However, the test workload is overwhelmingly compile-bound—the earlier profile measured only 13.5 seconds of total runtime—so this is strongly favorable for test speed. The right evaluation is not just “does the suite get faster?” but: preserve JSON semantics and error text, measure JSON decode runtime on representative large/nested payloads, and decide whether the compiler should retain an opt-in specialized fast path for production-critical decoding.

In short: **yes, an Elm-style runtime decoder is likely the highest-leverage way to massively reduce the JSON compilation work.** It replaces per-`T` generated control flow with data. It is a runtime/ABI feature, not a simple cache or stdlib relocation, and needs careful ownership/layout design to preserve Dark’s typed record/sum semantics.
