# Design brief

## Problem

At compiler HEAD b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, primitive literal syntax and observable scalar semantics are not governed by one interpreter-compatible contract against darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d.

## Goals

- Match interpreter behavior for unit, Boolean, integer, float, character, and string values end to end.
- Define consistent behavior for malformed tokens, numeric boundaries, negative literals, Unicode scalars, escapes, and exposed floating-point special values.
- Classify intentional divergences and compiler-only extensions while removing superseded spellings from maintained sources and fixtures.

## Proposed solution

Treat the pinned interpreter’s public behavior as the normative literal contract and align tokenization, escape decoding, parsing, typing, constant lowering, runtime representation, and rendering as one coherent change. Revalidate retained DCB1 findings at the pinned revisions, preserve only explicitly documented extensions or divergences, and migrate all maintained literal-bearing material to the resulting canonical syntax.

## Success criteria

- Equivalent source has the same acceptance, type, runtime value, and observable rendering in the compiler and interpreter.
- Boundary, malformed-input, Unicode, escape, negative-literal, and floating-point-special-value behavior agrees with the pinned interpreter.
- Superseded spellings are absent from maintained tests, library code, examples, and executable fixtures.
- Parity evidence records both exact revisions and distinguishes parity behavior from every retained extension or intentional divergence.

## Open questions

- Should any existing compiler-only literal spelling remain as a documented extension, or should all such spellings be removed?
