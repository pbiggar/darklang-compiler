# Design brief

## Problem

The compiler lacks the interpreter’s structural JSON model and type-directed behavior, producing capability gaps and incompatible values or errors.

## Goals

- Match current interpreter behavior for structural JSON construction, traversal, parsing, and formatting
- Provide type-directed serialization and parsing with canonical record, enum, type, and path-bearing failures
- Record exact compiler and interpreter revisions and explicitly classify extensions or intentional divergences

## Proposed solution

Introduce a first-class structural JSON runtime representation and the type metadata needed for generic conversion, then reuse the interpreter’s portable JSON implementation for parsing, formatting, traversal, building, and error rendering. Keep the representation, generic conversion, and compatibility behavior as one integrated parity boundary, with compiler-specific behavior documented separately.

## Success criteria

- The same-source JSON behavior produces equivalent values, formatting, and rendered failures in the compiler and interpreter at recorded revisions
- Typed round trips preserve supported records, enums, collections, primitives, and nested values
- Typed failures retain canonical type context and precise JSON paths
- Every retained difference is documented as an extension or intentional divergence
- Existing compiler behavior outside JSON remains unchanged

## Open questions

- Which existing compiler-only JSON behaviors, if any, must remain as compatibility extensions instead of converging?
- Should interpreter-unsupported runtime types be rejected identically or exposed as explicitly documented compiler extensions?
