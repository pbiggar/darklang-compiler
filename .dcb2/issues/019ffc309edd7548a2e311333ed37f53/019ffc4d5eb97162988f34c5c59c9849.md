# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, conditional and sequential expressions can differ observably from darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d in accepted syntax, typing, evaluation order, and failure timing.

## Goals

- Make the interpreter’s current public behavior the parity contract.
- Align condition typing, branch unification, nested conditionals, sequence result typing, branch selection, and left-to-right execution.
- Remove compiler-only conditional and sequencing forms, migrate affected expressions, and explicitly document any intentional divergence.

## Proposed solution

Treat the pinned interpreter revision as the canonical language contract and align the compiler’s parsing, typing, and control-flow lowering with it as one coherent change. Preserve lazy branch selection and strict left-to-right sequencing so skipped work, observable effects, termination, and failures occur at the same points. Replace compiler-only forms with interpreter-supported equivalents and retain revision-linked source and same-source behavioral evidence for each resolved difference.

## Success criteria

- The same supported source has matching parse acceptance, inferred or rejected types, results, execution order, and failure timing at the two pinned revisions.
- Untaken conditional branches are never evaluated, and sequential expressions execute left to right with the interpreter-defined result type.
- Compiler-only forms are no longer accepted, all repository uses are migrated, and every remaining divergence is explicitly classified.
- Current parity documentation records the exact compared revisions and revalidated evidence rather than relying on the earlier report.
