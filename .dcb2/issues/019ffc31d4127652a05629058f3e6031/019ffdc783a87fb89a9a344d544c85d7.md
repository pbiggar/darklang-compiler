# Design brief

## Problem

Using C@3514213a33a0a67562d33f9aa16478863ad9c11c versus current I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d, focused same-source probes confirm that compiled programs lack canonical HTML and HTTP values. The historical DCB1 report was only an inventory; current sources additionally show that the requested struck-text constructor and executable cookie encoding are not interpreter-parity behavior.

## Goals

- Provide the complete interpreter-declared HTML and HTTP value surfaces and observable behavior.
- Reuse portable interpreter definitions while limiting runtime work to canonical value representation and shared binary, date, dictionary, and JSON dependencies.
- Classify the additional HTML constructor and any cookie encoding capability as compiler-only extensions, and document AOT-specific divergences.

## Proposed solution

Port the interpreter’s structural HTML model, rendering behavior, HTTP records, parsers, and response helpers as pure standard-library values, preserving signatures and observable serialization, parsing, aggregation, status, body, and header semantics. Build on canonical shared value dependencies rather than introducing HTTP-specific runtime behavior. Keep the requested extra HTML constructor as a contained extension; define cookie encoding only against an explicit contract because the parity baseline exposes a cookie value shape but no executable encoder.

## Success criteria

- Equivalent same-source programs produce identical HTML documents, request-derived values, parsed query and header values, and HTTP responses at the recorded revisions.
- Canonical response bodies and headers use the expected binary and textual encodings, including the interpreter’s already-encoded JSON contract.
- The current upstream execution contracts pass on supported native targets.
- Every retained extension or intentional AOT divergence is explicitly separated from interpreter parity.

## Open questions

- What executable cookie encoding and header contract should be canonical: the non-executable legacy examples, a new typed specification, or value-shape parity only?
