# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, compared with darklang/dark revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, compiled programs lack the interpreter’s canonical Html and Http value APIs. DCB1 report 8a402797 is treated only as prior evidence; the retained finding is that this surface is absent from the compiler baseline.

## Goals

- Provide the complete interpreter-declared HTML construction and serialization surface.
- Provide canonical HTTP request, response, query, header, redirect, and cookie values and behavior.
- Match observable interpreter behavior at the recorded revisions, explicitly identifying any compiler-only extension or intentional divergence.
- Keep portable logic in the value modules and limit runtime additions to representation and unavoidable dependencies such as JSON serialization.

## Proposed solution

Port the interpreter’s pure value definitions and behavior as one coherent compatibility slice. Model HTML structurally and render it with the same escaping, void-element, attribute, comment, and document semantics. Model HTTP data structurally and preserve the interpreter’s parsing, response construction, content-header, redirect, JSON, and cookie encoding behavior. The frozen interpreter behavior is authoritative; the compiler baseline has no extension in this surface, and divergences should exist only when explicitly documented.

## Success criteria

- The full declared Html and Http public surfaces are available to compiled programs.
- Equivalent same-source programs produce matching HTML, query, header, response, redirect, JSON, and cookie results at the recorded revisions.
- All behavior differences are classified as parity, compiler-only extension, or intentional divergence, with no unclassified gaps.
- Existing compiler behavior remains intact and no performance work is introduced unless required for observable compatibility.
