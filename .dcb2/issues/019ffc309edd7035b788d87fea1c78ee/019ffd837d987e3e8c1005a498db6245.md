# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, competing parser paths and fragmented function representations produce syntax, evaluation-order, partial-application, arity, and closure differences from current interpreter behavior.

## Goals

- Use the interpreter-native parser and canonical function syntax as the sole public source boundary.
- Match interpreter behavior for parameter patterns, Unit-modeled zero parameters, multiple parameters, higher-order calls, lexical capture, and nested or returned closures.
- Evaluate arguments left-to-right before the callee, and preserve already-evaluated arguments across partial application.
- Retain only documented ahead-of-time typing divergences; keep recursive binding availability separate.
- Migrate compiler-authored functions and calls before removing legacy syntax, automatic nullary calls, compatibility adapters, and call fallbacks.

## Proposed solution

Replace both the compiler-specific parser and compatibility parsing path with the pinned interpreter-native parser and its canonical representation. Lower flat parameter lists and patterns into a statically typed compiler representation, then use one applicable function-value model for named functions and lambdas that carries lexical captures and evaluated partial arguments. Exact application invokes the function, under-application returns an applicable value, and over-application produces the corresponding observable failure. Preserve earlier compile-time rejection where arity or type errors are statically provable, documenting that timing difference as an intentional ahead-of-time divergence.

## Success criteria

- The same canonical source produces equivalent values, failures, and side-effect order on both pinned revisions for zero and multiple parameters, patterns, annotations, under- and over-application, higher-order calls, and nested, returned, or shadow-capturing closures.
- Partial application evaluates each supplied argument once and retains its value until invocation.
- Public compiler input and compiler-authored Dark code use the interpreter-native syntax without legacy parser or call fallbacks.
- Every remaining behavioral difference is revision-pinned and explicitly classified as an ahead-of-time requirement or intentional divergence.
