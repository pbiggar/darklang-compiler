## Work item 01a02421d9867b3cbf4dcee8238fb3e7

Title: Replace partial-application rewrites with interpreter-shaped applicable values

Category: behavior

Evidence: Pinned interpreter RuntimeTypes.fs:895-935 defines AppNamedFn and AppLambda as Applicable variants, each with argsSoFar; RuntimeTypes.fs:1821-1837 preserves both lambda captures and partial arguments during value traversal. Interpreter.fs:143-194 combines Prior evaluated arguments with current registers; 1194-1223 reports excess package arguments and materializes argsSoFar only for partial application; 1480 onward performs the same combined-argument logic for lambdas. In contrast, compiler TypeChecking.fs:3357-3384 and 5542-5578 builds a deferred lambda containing supplied argument expressions, and AST_to_ANF.fs:2057-2183 retains LambdaEnv reinterpretation before separate ClosureAlloc/ClosureCall lowering.

Outcome:

Represent named functions and lambdas uniformly through typing, ANF, closure allocation, invocation, and both backends, carrying lexical captures and already-evaluated arguments. Combine prior arguments with newly evaluated arguments in left-to-right source order; invoke at exact arity, return an applicable value at under-arity, and preserve compiler-time rejection only when arity or type failure is statically provable. Remove LambdaEnv call reinterpretation and generated-lambda partial-application fallbacks.

## Conversation response

Pinned interpreter evidence now confirms the target representation: named functions and lambdas are both `Applicable` values with `argsSoFar`; application combines prior evaluated values with new arguments, returns an applicable value when under-applied, and raises the interpreter’s arity failure when over-applied. The compiler plan should mirror that model rather than preserve its lambda-rewrite approximation.
