# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 versus interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, internal equality and output capabilities are not exposed through a parity-compatible public prelude.

## Goals

- Match the interpreter’s public, same-typed polymorphic equality behavior for values supported by both systems.
- Match explicit string-output ordering, return values, currying, and newline behavior.
- Classify compiler-only extensions and intentional divergences explicitly.

## Proposed solution

Expose a coherent public prelude over the compiler’s existing type-directed structural equality and output effects. Equality remains statically restricted to matching types, inequality is its complement, and explicit output remains distinct from automatic result rendering.

## Success criteria

- Equivalent same-source programs produce matching equality results for shared supported values.
- Explicit output produces matching bytes and ordering, including newline and empty-input behavior, returns Unit, and causes no duplicate rendering.
- Parity evidence pins both revisions and clearly separates shared behavior, compiler extensions, and intentional divergences.
