# Design brief

## Problem

At compiler d65ad3daf594422bd93664cc16758bc43ae29297 versus interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, equivalent equality and output machinery exists internally but is absent from the callable public prelude.

## Goals

- Match the interpreter’s polymorphic equality and explicit string-output contracts for shared supported values.
- Preserve evaluation order, return values, currying, and exact newline behavior.
- Explicitly classify compiler-only value support, static checking, boundary rendering, and unsupported interpreter capabilities or types.

## Proposed solution

Expose one coherent public prelude backed by the compiler’s existing type-directed structural equality and output effects. Equality should retain operator semantics, inequality should be its complement, and output should sequence strings predictably without altering automatic result rendering.

## Success criteria

- Public equality matches interpreter behavior across value forms supported by both implementations.
- Explicit output matches interpreter bytes, ordering, newline, empty-list, and Unit-return behavior without duplicate output.
- Parity evidence pins both revisions and distinguishes shared parity from compiler extensions and intentional or separately owned divergences.
