The repository already uses the right *kind* of deterministic signal for generated-program performance: Cachegrind instruction counts. Its benchmark runner explicitly excludes F#/.NET because the runtime does not work reliably under Valgrind, while the compiler’s existing `PassTimingRecorder` uses `Stopwatch` and is therefore wall-clock noisy. The CLI currently does not enable that recorder.

The best approach is a two-level compiler-performance system:

1. **Make Native AOT + Cachegrind instruction count the deterministic regression metric.** Publish a dedicated release compiler benchmark runner as Native AOT, then run it under Cachegrind. Native AOT removes the JIT at execution time, yielding a normal native executable; Cachegrind reports the exact executed instruction count, rather than elapsed time. [Native AOT overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [Cachegrind manual](https://valgrind.org/docs/manual/valgrind_manual.pdf).
2. **Measure each pass in isolation.** Give the runner a fixed corpus of realistic, versioned pass inputs (AST/ANF/MIR/LIR as appropriate), load/setup outside the measured region, and run one pass repeatedly or in its own process. Record `Ir`/executed instructions as the primary result, plus allocations and output-size/work counters as diagnostics. This avoids trying to infer an individual pass from a whole-compilation total.
3. **First do a feasibility spike.** The key unknown is whether this compiler and its dependencies publish/run correctly as Native AOT under this container’s Valgrind. If it does, require several identical trial runs before treating the count as a gate. If it does not, retain the same harness and use Linux `perf stat` retired-instruction counts as a less-deterministic fallback.

`perf` is valuable for explaining a regression in the real JIT build, but not as the deterministic gate: hardware counters can be interrupted, multiplexed, or affected by other activity. With .NET it can resolve JIT code through perf maps, but enabling those maps can itself add JIT-time overhead. [Runtime perf-map guidance](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/debugging-profiling), [Linux .NET tracing guidance](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-highcpu).

BenchmarkDotNet is also useful, but for a different job: it gives statistically sound elapsed-time and allocation comparisons, not deterministic results. Its hardware-counter support is platform-dependent, and its own documentation positions it as a benchmarking framework rather than an instruction-count simulator. Use it as the final, real-production confirmation after the deterministic gate—not as the gate itself. [BenchmarkDotNet diagnosers](https://benchmarkdotnet.org/articles/configs/diagnosers.html).

A few controls matter for the secondary wall-clock benchmark: fixed SDK/runtime image, release build, one pinned CPU, no competing workload, process isolation, warmup, and explicit .NET runtime settings. Tiered compilation and dynamic PGO are enabled/configurable in modern .NET and otherwise change startup/steady-state behavior between runs. [Runtime compilation settings](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation).

I would not use EventPipe, `dotnet-trace`, PerfView, or PerfCollect as the regression metric. They are excellent attribution tools—EventPipe is the supported base for .NET tracing—but sampled/traced data remains observational and adds overhead. [EventPipe overview](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe).

So the concrete recommendation is: **add a Native-AOT Cachegrind compiler-pass benchmark harness as the deterministic CI signal, retain the current generated-program Cachegrind benchmark separately, and use BenchmarkDotNet/perf only to validate that instruction-count improvements translate to real JIT compiler elapsed-time improvements.** Native AOT is a measurement vehicle, not a claim that its timings equal the shipping JIT compiler.
