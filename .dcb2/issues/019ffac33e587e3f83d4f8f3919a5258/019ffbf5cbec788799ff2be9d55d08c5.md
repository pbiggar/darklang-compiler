# Design brief

## Problem

At compiler 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, the typed database model, query representation, and SQLite surface present in darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d are absent, preventing same-source data-access parity.

## Goals

- Support the complete requested typed DB and SQLite surface.
- Match the interpreter’s public typing, results, ordering, cardinality, conversion, and error behavior.
- Record both exact revisions for every parity comparison and explicitly classify any compiler-only extension or intentional divergence.
- Treat DCB1 report 8a402797 and parity documents only as leads, with retained findings revalidated against current source and focused same-source probes.

## Proposed solution

Add a first-class typed database capability spanning declarations, values, schema-aware storage, and a dedicated typed query representation, backed by native runtime operations that preserve interpreter-visible behavior. Add SQLite values and operations with equivalent parameter binding, execution, row and column decoding, scalar handling, cardinality, and failure semantics. Deliver both as contained parts of one coherent data-access solution; no compiler-only extensions or intentional divergences are currently established, and any introduced during delivery must be documented against the recorded baseline revisions.

## Success criteria

- Every operation in the requested DB and SQLite scope is accepted with interpreter-equivalent types and produces equivalent observable results for focused same-source probes.
- Typed values round-trip safely, database queries and key operations preserve baseline semantics, and SQLite conversions, null/type mismatches, cardinality, and errors behave consistently.
- Parity evidence identifies the exact compiler and interpreter revisions for each comparison and distinguishes confirmed parity, extensions, and intentional divergences.
- Existing observable compiler behavior remains unchanged outside this capability.

## Open questions

- What native persistence, database identity, isolation, and lifecycle should represent the interpreter’s host-provided database context?
- How should SQLite availability and resource ownership be packaged across supported native platforms without changing public behavior?
