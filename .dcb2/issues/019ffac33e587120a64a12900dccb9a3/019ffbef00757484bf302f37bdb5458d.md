# Design brief

## Problem

The compiler’s List API does not yet match the interpreter’s current public surface, Int-based contracts, calling conventions, and observable sorting behavior.

## Goals

- Achieve behavioral and type parity with the interpreter’s public List API.
- Standardize indexing, sizing, repetition, and sorting around Int and canonical argument application.
- Explicitly classify compiler-only additions and any intentional divergences.

## Proposed solution

Treat compiler 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 and darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d as the recorded comparison revisions. Revalidate earlier findings from report 8a402797 and current parity documents against source and focused same-source probes, then close the API and behavioral gaps as one cohesive compatibility change. Use interpreter behavior as authoritative, preserve compiler-only additions as labeled extensions, and document any deliberate deviation without treating performance differences as gaps.

## Success criteria

- Equivalent programs observe matching types, argument order, currying, results, ordering, and error behavior across the shared collection surface.
- The interpreter’s currently public collection capabilities are present in the compiler.
- Every retained parity finding is backed by revision-specific source evidence and, where practical, a focused same-source comparison.
- Compiler-only extensions and intentional divergences are explicitly distinguished from parity behavior.
