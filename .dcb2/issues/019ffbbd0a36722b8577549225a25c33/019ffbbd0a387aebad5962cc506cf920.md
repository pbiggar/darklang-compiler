# Outline cold ARM64 decrement lowering

Reduce scalar-program ARM64 Code Generation time by avoiding JIT compilation of unused general decrement lowering.

## Constraints

- Limit changes to ARM64 pass 6 RefCountDec dispatch and retain one extraction only.
- Trial alternatives in an isolated worktree; establish a profiling threshold first and discard neutral, noisy, regressive, or invalid results.
- Collect 10 paired, alternating before/after -vv runs for every routine program; report raw Code Generation and total-compilation results, medians, and absolute and percentage deltas.
- Compare 10 paired before/after ./run-tests --ai wall-clock runs with raw results, medians, and deltas.
- Require identical symbolic ARM64 streams, binaries, benchmark outputs, and instruction counts; pass ./run-tests --ai and ./benchmarks/run_benchmarks.sh --verify routine and report the RESULTS.md performance ratio.
- Remove all exploratory profiling and instrumentation from retained code.

## Trial work

### Trial item 019ffbbd0a367eb4a1a9491a0d44c75e

Title: Measure unused decrement-lowering cost

Category: ARM64 code generation profiling

Evidence: Current ackermann timing assigns 25.5 ms of 54.4 ms total to Code Generation, while its allocated LIR contains string decrements but no general RefCountDec; the general branch spans roughly lines 4780-5170 of 6_CodeGen.fs.

Outcome:

Quantify JIT time and allocations attributable to the general RefCountDec branch on scalar/string-only programs.

### Trial item 019ffbbd0a367ec793f690da366eacf7

Title: Extract general decrement lowering

Category: ARM64 cold-path outlining

Evidence: A separate method can remain un-JITted for programs that never dispatch the general decrement case while preserving emitted instructions exactly.

Outcome:

Move the unchanged general managed-heap decrement branch into a private function invoked only by LIR.RefCountDec.
