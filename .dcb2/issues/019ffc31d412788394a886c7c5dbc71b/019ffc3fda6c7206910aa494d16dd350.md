# Design brief

## Problem

The compiler’s list surface diverges from the interpreter in available operations, Int contracts, calling conventions, bounds and error behavior, and validated sorting semantics.

## Goals

- Match the interpreter’s observable collection behavior using compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 and interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d as the comparison pair.
- Complete the collection and sorting surface, including dedicated chunk-size errors and required randomness support.
- Explicitly preserve compiler-only extensions and document any intentional divergences.

## Proposed solution

Adopt the interpreter’s current list and merge-sort algorithms and their public contracts, using Int consistently and matching canonical currying, argument order, bounds, errors, and comparator validation. Add only the primitive runtime capability needed by those algorithms, retain existing compiler extensions as separately classified behavior, and tie each parity conclusion to the pinned revisions plus current source or focused same-source evidence.

## Success criteria

- Equivalent programs produce matching values or matching structured errors across the covered collection operations.
- Invalid indices, sizes, ranges, and comparator behavior follow the interpreter baseline.
- Sorting is canonical, deterministic apart from explicitly random operations, and validates comparators before accepting results.
- Every retained finding records the exact comparison revisions and supporting current evidence.
- Compiler-only extensions and intentional divergences are clearly distinguished from parity behavior.
