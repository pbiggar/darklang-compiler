# Design brief

## Problem

The audit records current compiler HEAD 5134f85379dac51b1543902c2a68abc277fc53db; all parity findings compare compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 with interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d. The compiler differs observably in list syntax, supported values, evaluation behavior, failure behavior, and its public List contract.

## Goals

- Make the pinned interpreter’s public list behavior the canonical source and API contract.
- Preserve contextual empty-list inference and AOT static rejection of heterogeneous lists while matching observable interpreter results.
- Remove compiler-only list syntax and public aliases, explicitly classifying retained implementation divergences.

## Proposed solution

Deliver one vertical parity change covering list literals, canonical separators, right-associative cons patterns, append syntax, inference, construction, matching, equality, and the complete public List contract. Classify spread-style construction and patterns plus public aliases as compiler extensions to remove. Classify earlier compile-time rejection and the native list representation as intentional divergences; retain native implementations and internal helpers wherever behavior remains equivalent. Use revision-stamped, same-source evidence to align signatures, supported element categories, callback order and count, short-circuiting, results, and language-visible failures.

## Success criteria

- Canonical list source has equivalent acceptance, typing, associativity, construction order, matching, equality, and results under both revisions.
- Empty lists infer from context; heterogeneous lists are rejected before execution by the compiler as a documented AOT divergence.
- The public List surface matches interpreter names, types, arities, return and error shapes, element support, and observable callback behavior.
- Compiler-only list syntax and public aliases are absent, affected sources use the canonical contract, and every retained divergence is documented with the exact compared revisions.

## Open questions

- Must failure parity include exact diagnostic wording and source context, or only equivalent failure classification with the compiler’s earlier AOT phase documented?
