Findings: the benchmark system has accumulated three overlapping gates, but only the full routine gate is currently part of normal agent verification and integration.

- `--fast` exists only in `benchmarks/quick_check.sh`, `benchmark_baseline.py`, `profiles/quick-fast.txt`, and the benchmark README. It has no agent, playbook, or integration caller. It runs a five-benchmark projection that cannot establish or advance a baseline, so it provides neither the canonical full-suite guarantee nor a uniquely used workflow role.
- There is no `--quick` option on `run_benchmarks.sh`; the corresponding command is `quick_check.sh`. It runs all 21 reduced workloads, including the two intentionally non-canonical workloads excluded from the 19-workload `routine` profile.
- `quick_check.sh` does rebuild Rust only when its source or binary is stale, but it executes every Rust quick binary and runs Cachegrind on each on every invocation. Those Rust counts are printed only as diagnostics: the quick snapshot and pass/fail decision contain Dark counts alone. The Rust source and expected output are already hash-checked by `PARITY.json` before work begins. Re-running Rust is therefore redundant for the normal Dark regression decision; it is useful only as an explicit reference audit.
- The full runner already follows the desired Dark-only model: ordinary Cachegrind runs use cached audited Rust rows, and Rust runs only with `--refresh-baseline=rust`.

Actual workflow:

- Repository policy, AGENTS guidance, and retained optimization workflow all prescribe `./benchmarks/run_benchmarks.sh --verify routine` for final validation.
- `scripts/land-on-main.sh` runs `./run-tests --ai`, then `./benchmarks/run_benchmarks.sh --verify-fresh --jobs 3 routine`. This enforces both non-regression and that an unrecorded full-suite improvement is recorded before integration.
- Specialist agents generally leave the full gate to the integration owner; the benchmark-fixer agent runs only its selected workload. No current workflow invokes `quick_check.sh`.

The history explains the churn: quick checking was added in January as a fast pre-merge substitute for a roughly three-minute full run; the current routine/freshness/snapshot system was added in August and integration moved back to the full routine profile. The old quick and fast machinery remained, creating a second baseline, third profile, duplicated policy, and documentation burden without an active integration role.

Recommendation: remove fast mode. Then make the reduced suite the standard agent/developer preflight, but make it Dark-only by default; retain Rust build/output/Cachegrind as an explicit audited-reference refresh command. Keep the full 19-workload `--verify-fresh routine` gate at integration, because quick has different workloads and cannot prove or record the canonical full-suite result. This yields a clear two-tier workflow instead of three modes:

1. Agent/developer: complete Dark-only quick gate.
2. Integration: full Dark-only routine freshness gate.
3. Maintainer-only: explicit Rust reference audit/refresh.

One product decision remains before implementation: whether the quick suite should remain its current 21-workload correctness superset, or be projected from the canonical 19 workloads. The former preserves broader quick coverage; the latter further reduces conceptual duplication.
