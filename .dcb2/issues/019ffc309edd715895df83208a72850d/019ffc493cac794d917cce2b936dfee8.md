# Design brief

## Problem

At compiler HEAD b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, identifier, keyword, capitalization, and qualified-name parsing can diverge from interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, producing inconsistent acceptance or parse structure and preserving legacy forms in repository-authored source.

## Goals

- Make the pinned interpreter’s public lexical behavior the baseline across value names, bindings, parameters, types, constructors, fields, modules, packages, qualification segments, reserved words, and ambiguous token boundaries.
- Limit scope to lexical acceptance and parse structure, leaving semantic name and namespace resolution unchanged.
- Explicitly classify every revalidated compiler-only extension or intentional divergence and remove keyword aliases, capitalization exceptions, and legacy identifier forms from repository-authored source.

## Proposed solution

Align the compiler’s naming grammar and token-boundary behavior with the pinned interpreter revision, applying the same keyword, capitalization, identifier, and qualification rules consistently in every parser context. Revalidate prior-report and parity-document findings against both pinned revisions, retain only source-backed gaps with focused same-source evidence, and treat any necessary divergence as an explicit part of the lexical contract.

## Success criteria

- The exact compiler and interpreter revisions are recorded for every comparison.
- Focused same-source probes produce matching acceptance, rejection, and parse structure across all covered naming contexts and ambiguous boundaries, except for explicitly documented intentional divergences.
- Every claimed gap is supported by current source evidence and, where practical, a focused probe or parser-facing test.
- Repository-authored source contains no removed keyword aliases, capitalization exceptions, or legacy identifier forms.
- Callable and namespace lookup behavior remains outside the change boundary.

## Open questions

- Which revalidated compiler-only extensions, if any, must remain intentional divergences from the interpreter’s public grammar?
