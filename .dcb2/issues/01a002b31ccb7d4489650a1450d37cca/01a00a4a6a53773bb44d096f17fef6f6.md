I audited both benchmarks and tests for internal-function calls and split findings into actionable vs intentionally internal.

### Summary
- Found **54 internal-call matches in 12 benchmark source files** (all under `benchmarks/problems/*/dark/*.dark`).
- Found **275 internal-call matches in tests** (across `.e2e`, `.fs`, and compiler-pass tests).
- No broad accidental pattern of user-facing internal calls turned up.

### Benchmark findings
- Internal calls are concentrated in these files:
  - `benchmarks/problems/edigits/dark/{main,quick}.dark` (7 each)
  - `benchmarks/problems/matmul/dark/{main,quick}.dark` (6 each)
  - `benchmarks/problems/nsieve/dark/{main,quick}.dark` (4 each)
  - `benchmarks/problems/spectral_norm/dark/{main,quick}.dark` (4 each)
  - `benchmarks/problems/fasta/dark/{main,quick}.dark` (3 each)
  - `benchmarks/problems/fannkuch/dark/{main,quick}.dark` (1 each)
  - `benchmarks/problems/quicksort/dark/{main,quick}.dark` (2 each)
- These are compiled with explicit `--allow-internal` in benchmark build/test scripts (for example `benchmarks/infrastructure/build_all.sh` and `benchmarks/quick_check.sh`), so this is currently an intentional benchmark policy rather than accidental user-code usage.

### Test findings
- Intentional internal suites:
  - `src/Tests/e2e/stdlib-internal/*` (multiple files)
  - `src/Tests/verification/*` (e.g. `dict-verification.e2e`, `stdlib-internal/skew-list-verification.e2e`)
- The end-to-end runner only enables internal names for those paths via `isInternalTestFile` (`/stdlib-internal/` and `/verification/`).
- Compiler-pass tests also mention internal helper names (e.g. `src/Tests/compiler-passes/ASTToANFTests.fs`, `RefCountInsertionTests.fs`, `X86_64CodeGenTests.fs`) as expected fixtures for internal-symbol behavior.
- Outside those intentional zones, only **non-executable comments** and one deliberate rejection test remain:
  - `src/Tests/e2e/pattern_matching.e2e` comments (`// ... Stdlib.String.__compareBytes`)
  - `src/Tests/e2e/tailcall.e2e` comments (`// ... Stdlib.String.__compareBytes`)
  - `src/Tests/e2e/stdlib_internals.e2e` intentionally asserts internal identifiers are rejected.

### Why this matters
Most internal usage is either:
1) part of internal verification coverage, or
2) benchmark code paths compiled with explicit internal allowance, often touching APIs that have no direct public equivalent (e.g., internal HAMT keying semantics and list mutation-like helpers such as internal `SkewList.setAt`/`List.__repeatInt64`).

If the objective is strict removal of internal calls from benchmarks/tests, this will likely require either:
- API exposure work (public wrappers for currently internal functionality), or
- benchmark rewrite to public-only semantics where possible.
Both options should be treated as behavior/performance-impacting changes and measured before/after.
