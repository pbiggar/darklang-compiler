# Design brief

## Problem

At C@9195f26d0f1d32b5345bc6020cf569674951d8f6, binary representation, codecs, cryptography, and certificate handling differ from I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d in API coverage, signatures, bounds, and failure behavior.

## Goals

- Establish Blob as the single distinct immutable binary runtime value.
- Match interpreter-observable results and failures across the scoped binary capabilities.
- Preserve and document the specified compiler-only extensions while recording exact comparison revisions and any intentional divergences.

## Proposed solution

Replace the compiler’s current binary type with Blob and align the complete scoped codec, cryptographic, and certificate surface to the pinned interpreter behavior. Retain the specified Bytes, decoding, digest, hexadecimal, and diagnostic capabilities as explicitly separated extensions operating on Blob. Deliver runtime representation, behavior alignment, extension classification, and revision-pinned parity evidence as one compatibility change.

## Success criteria

- Pinned same-source comparisons produce equivalent values and observable failures throughout the parity surface.
- Blob is immutable, distinct from other runtime values, and the former Bytes runtime type no longer exists.
- All retained compiler-only capabilities are clearly classified as extensions, with intentional divergences explicitly recorded.
- Every comparison identifies the exact compiler and interpreter revisions used.
