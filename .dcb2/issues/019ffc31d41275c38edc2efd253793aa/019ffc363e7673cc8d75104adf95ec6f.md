# Design brief

## Problem

At C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, binary-data, codec, cryptographic, and certificate behavior differs from the interpreter baseline I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d in types, coverage, and failure semantics.

## Goals

- Provide an immutable Blob API matching interpreter-observable values, bounds, signatures, and decoding failures.
- Align dependent codec, hashing, HMAC, and certificate operations around Blob.
- Retain and explicitly document existing non-parity APIs as compiler extensions; propose no intentional parity divergences.
- Keep revision-pinned comparison evidence reproducible.

## Proposed solution

Introduce a distinct immutable Blob runtime value and make the parity surface use it consistently across conversion, encoding, cryptography, and certificate extraction. Reproduce interpreter behavior for malformed input and boundary cases instead of normalizing errors or adding defaults. Preserve the existing byte-oriented and extra cryptographic capabilities as clearly separated compiler extensions. Deliver the type, related operations, behavior alignment, and parity documentation as one coherent compatibility change.

## Success criteria

- At the recorded revisions, focused same-source comparisons produce equivalent successful values and equivalent observable failures across the parity surface.
- Blob values cannot be mutated or confused with the compiler’s existing byte representation.
- Codec, hash, HMAC, and certificate operations expose interpreter-compatible Blob signatures.
- Existing compiler-only capabilities remain available and are classified as extensions rather than parity behavior.
- Current parity documentation records the comparison revisions, resolved gaps, extension boundary, and absence of intentional divergences.
