# Design brief

## Problem

At C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, binary-data behavior differs from the interpreter baseline I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d in representation, API coverage, signatures, and failure semantics.

## Goals

- Replace the Bytes type with one distinct immutable Blob representation.
- Match current interpreter-observable codec, cryptographic, certificate, bounds, and failure behavior.
- Record exact comparison revisions and explicitly classify compiler extensions and intentional divergences.

## Proposed solution

Adopt Blob as the compiler’s sole binary-data type and align the parity surface around interpreter-compatible behavior. Retain applicable compiler-only capabilities as documented extensions operating on Blob, without preserving a separate Bytes type. Treat the related type, codec, cryptographic, certificate, and parity-documentation changes as one compatibility effort, with no proposed intentional divergences.

## Success criteria

- Equivalent inputs produce interpreter-equivalent Blob values and observable failures across the parity surface.
- No Bytes runtime type remains, and Blob values are immutable and distinct from other runtime values.
- Retained compiler-only behavior is clearly identified as extension behavior over Blob.
- Parity evidence records the exact compiler and interpreter revisions used for each comparison.
