# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 versus interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, temporal behavior lacks parity: dates remain publicly interchangeable with integers, canonical duration parsing is absent, and related signatures and semantics differ.

## Goals

- Make dates distinct runtime values while matching the interpreter’s observable integer-based temporal API.
- Match the interpreter’s duration units, numeric and whitespace handling, integer results, and exact error contract.
- Classify compiler-only extensions explicitly and introduce no intentional semantic divergences.

## Proposed solution

Copy and adapt as much of the interpreter’s temporal behavior as possible, sharing its portable wrappers and parsing logic while supplying native, timezone-independent primitives for clocks, epochs, calendar conversion, and arithmetic. Use an opaque date representation throughout the runtime boundary and keep the parity work as one coherent temporal design.

## Success criteria

- Dates are observably distinct from integers while conversions, arithmetic, calendar fields, clock behavior, and millisecond operations match the recorded interpreter revision.
- Duration inputs yield the same integer values or exact errors as the interpreter across valid, malformed, whitespace, numeric, and boundary cases.
- Same-source comparisons at the recorded revisions demonstrate value parity and type separation.
- Every remaining behavioral difference is documented as a compiler-only extension, with no unclassified divergence.
