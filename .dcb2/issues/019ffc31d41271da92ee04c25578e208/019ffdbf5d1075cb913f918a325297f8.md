# Design brief

## Problem

At compiler HEAD a177b36cfcb27ab6793e054d12015e83e1d805dc versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, DateTime remains interchangeable with Int64, its integer contracts use the wrong type, and canonical Duration parsing is absent.

## Goals

- Make DateTime a distinct UTC runtime value with canonical Int-facing behavior.
- Match interpreter-observable DateTime arithmetic, conversion, calendar, clock, rounding, range, and error semantics.
- Match Duration units, arbitrary-precision signed numeric handling, accepted whitespace, and exact errors.
- Classify retained compiler extensions and AOT-specific divergences explicitly.

## Proposed solution

Introduce a dedicated DateTime value throughout the compiler and runtime, then reuse the interpreter’s portable public wrappers over native, timezone-independent clock, epoch, calendar, conversion, and arithmetic primitives. Reuse the portable Duration wrapper and align its numeric parsing dependency with the interpreter. Static rejection timing is an intentional AOT divergence; legacy aliases and internal entry points are compiler-only extensions outside the parity contract and must be documented if retained.

## Success criteria

- DateTime and integer values are not interchangeable, while the canonical DateTime surface accepts and returns Int where specified.
- Pinned same-source cases produce matching UTC values, component values, negative-epoch behavior, rounding, range failures, and error text.
- Duration parsing recognizes only the canonical units, returns arbitrary-precision Int results, preserves interpreter sign and whitespace behavior, and reproduces exact error categories and messages.
- Clock-derived and converted values behave consistently across supported targets without host-timezone dependence.
