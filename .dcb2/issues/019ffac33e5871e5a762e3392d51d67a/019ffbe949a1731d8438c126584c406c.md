# Design brief

## Problem

At compiler HEAD 5a69ef3202b6b8ddef3c4246abe6af9f7e11de3e versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, text behavior is partly byte- or codepoint-based, Unicode coverage is incomplete, canonical surface area is missing, and Regex is absent, producing observable parity failures.

## Goals

- Match the interpreter’s public character, string, and regex contracts, including values, types, errors, normalization, and index units.
- Treat characters as extended grapheme clusters and strings as NFC text throughout canonical operations.
- Expose the complete in-scope canonical surface while explicitly separating compiler extensions and intentional divergences.
- Keep behavior consistent across native targets without treating performance differences as parity gaps.

## Proposed solution

Establish one shared, versioned Unicode text layer providing normalization, grapheme segmentation, classification, casing, comparison, and indexing semantics. Build canonical character and string behavior on that layer, preserving the interpreter’s operation-specific contracts and result shapes. Add a regex compatibility layer matching the interpreter’s dialect and observable matching, replacement, splitting, and error behavior. Layer conversions, encoding, digest, and randomness behavior over canonical runtime types and capabilities, while retaining noncanonical compiler facilities only as documented extensions. Pin both implementation revisions in all conformance evidence.

## Success criteria

- Same-source coverage produces interpreter-equivalent values and errors across ASCII, composed and decomposed text, combining sequences, emoji clusters, Unicode whitespace, and casing expansions.
- Canonical text construction and transformation preserve NFC and never split an EGC where the interpreter treats it atomically.
- Every in-scope public operation is available with matching types, argument order, index units, boundary behavior, and failure shape.
- Regex behavior matches the interpreter for ordinary, empty, Unicode, zero-width, replacement, split, and invalid-pattern cases on both native targets.
- Compiler-only facilities and intentional divergences are clearly classified and cannot be mistaken for parity behavior.

## Open questions

- Which Unicode version should be pinned so native behavior remains deterministic as the interpreter runtime evolves?
- Which native regex engine can reproduce the interpreter dialect and error semantics consistently across supported platforms?
- Should canonical blob, cryptographic, and randomness prerequisites be consumed from their family alignment or included as dependencies of this delivery?
