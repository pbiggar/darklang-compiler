The repository already has a strong deterministic microbenchmark gate: 19 audited Dark/Rust full-workload pairs in `routine`, parity-hashed sources/output, Cachegrind instruction counts, and a geometric-mean regression decision. But its workloads are predominantly small kernels; the largest Dark source is `nbody` at 201 lines, and the suite has no application-profile category.

Recommendation: retain `routine` as the compiler-optimization gate and add one separate, fixed-input **application benchmark**—preferably a `request_render` vertical slice:

`request string → query/header parsing → JSON decode → routing/model transformation → HTML rendering → response/checksum`

This is a good fit for the language as it exists: the repository has JSON parsing/serialization plus pure `Http` request parsing and `Html` rendering modules. It exercises strings, lists, Dict/HAMT operations, records/ADTs, pattern matching, recursive library code, allocation, and formatting together—rather than rewarding one narrow optimization. Keep input embedded and deterministic, repeat the operation enough to amortize startup, and validate a compact checksum/length rather than emitting every rendered response. Implement an audited Rust counterpart with the same request corpus, semantics, and observable result, using the existing parity contract.

Other viable candidates, in order:

- **JSON corpus transform**: parse a representative fixed JSON document, normalize/filter/group it, then serialize. Lowest implementation risk, but less application-shaped.
- **Small interpreter/query engine**: tokenize, parse, evaluate a compact expression/query corpus. Strong compiler-language coverage, but it overlaps compiler-parser concerns more than Dark application usage.
- **Ray tracer or minilight port**: established whole-program benchmark, but mostly repeats the suite’s numerical focus and is less representative of Dark’s web/data-oriented stdlib.
- **Port a real Dark application**: highest realism, but only worthwhile once a dependency-free, stable program and corpus can be frozen; otherwise parity, fixture licensing, and maintenance dominate the benchmark.

This two-tier approach matches mature projects. Go deliberately runs both Sweet end-to-end workloads and bent microbenchmarks, and describes Sweet as real-world applications for CPU and memory comparisons; it also treats the suite as curated and changeable over time. [Go performance monitoring](https://go.dev/wiki/PerformanceMonitoring), [Sweet suite](https://pkg.go.dev/golang.org/x/benchmarks/sweet). Rust’s `rustc-perf` separately tests a large collection of popular crates across clean and incremental build scenarios. [Rust performance testing](https://rustc-dev-guide.rust-lang.org/tests/perf.html). OCaml’s Sandmark combines sequential/parallel application benchmarks with configurable compiler variants and nightly reporting. [Sandmark](https://github.com/ocaml-bench/sandmark). LLVM likewise keeps whole applications, multi-source programs, and microbenchmarks as distinct suite categories with reference-output validation. [LLVM Test Suite Guide](https://llvm.org/docs/TestSuiteGuide.html).

A practical policy would be: application benchmarks are a separately reported profile at first, must be deterministic and parity-audited, and are reviewed individually rather than allowed to overwhelm the existing equal-weight micro-suite score. Once it proves stable and useful for optimization decisions, decide explicitly whether it becomes one equal-weight member of `routine` or remains a required companion profile. This avoids losing the current gate’s precise diagnostic value while adding a workload that exposes cross-cutting regressions.
