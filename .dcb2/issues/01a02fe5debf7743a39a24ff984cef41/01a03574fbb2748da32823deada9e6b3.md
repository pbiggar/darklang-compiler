A much better-sized candidate is **[TinyTemplate](https://github.com/bheisler/TinyTemplate)**: an established Rust text/HTML template engine, originally created for Criterion reports and intended for HTML reports and simple web-server output.

At frozen release **1.2.1**, its implementation is **2,417 physical Rust lines across six source files**—almost exactly the requested scale. It includes a real template compiler and bytecode interpreter, rather than being merely a string-replacement helper:

- escaped and unescaped value rendering;
- nested field/index lookup over dynamic JSON-like values;
- `if`/`else` branches;
- loops with index/first/last state;
- named contexts;
- custom formatters; and
- calls between named templates.

This is a more suitable translation target than MiniJinja. The source is compact enough to understand and preserve as a single benchmark/application, yet it has enough parser, compiler, interpreter, context-stack, and rendering behavior to exercise Dark meaningfully. [TinyTemplate source at 1.2.1](https://github.com/bheisler/TinyTemplate/tree/1.2.1)

One important distinction: TinyTemplate’s **source** meets the 3k target, but its Cargo closure does not. It directly depends on `serde` and `serde_json`, so counting every transitive Rust dependency would put even this small engine well above 3k lines. That is not a useful portability boundary: Dark already has an in-tree structural JSON representation and parser, just as Rust treats its standard library as ambient. The fair unit to port is TinyTemplate’s 2,417-line domain implementation, with a small explicit JSON/value model at the boundary—not `serde` itself.

A literal line-for-line port is unlikely to stay under 3k Dark lines because the Rust implementation relies on mutation, `HashMap`, lifetimes, and panics. A faithful **frozen semantic profile** should fit the intent:

- static named templates;
- JSON-like values represented by Dark’s existing `AltJson.Json` type;
- field/index lookup;
- escaping;
- loops, branches, and template calls;
- no user-defined Rust callbacks or arbitrary `serde::Serialize` conversion.

That would be a genuine TinyTemplate-derived application benchmark, not a toy renderer. A fixed set of realistic report/catalog templates plus structured input could then run both parse-and-compile and compile-once/render-many modes, with exact rendered-output validation.

Caveat: release 1.2.1 declares itself **passively maintained**. That is acceptable for a frozen benchmark source—the target will not drift—but it means we should pin the source and independently retain the relevant behavior tests, rather than depend on ongoing upstream support. [Release manifest](https://github.com/bheisler/TinyTemplate/blob/1.2.1/Cargo.toml)

My recommendation is therefore to evaluate **TinyTemplate 1.2.1 as the source program**, with the benchmark explicitly limited to the frozen feature profile above. It is the first candidate that simultaneously gives us an established Rust implementation, an application-like execution pipeline, and a credible ~3k-LOC scope.
