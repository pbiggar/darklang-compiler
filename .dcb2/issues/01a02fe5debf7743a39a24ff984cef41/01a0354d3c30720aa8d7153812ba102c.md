The best Rust application candidate is **[ripgrep](https://github.com/BurntSushi/ripgrep)**, frozen at a release tag with a checked-in text corpus and a fixed set of searches.

It is a real, mature Rust CLI application—not a synthetic benchmark—and is approximately 46k lines across ten crates. Its core workload is highly relevant here: traverse a corpus, apply ignore/path rules, search lines, aggregate matches, and format deterministic results. It exercises strings, parsing, recursive data structures, lists/maps, pattern matching, allocation, and output construction. Rust itself uses ripgrep as a real-world crate in its compiler-performance corpus. [rustc-perf](https://perf.rust-lang.org/)

However, the **full ripgrep program is not an appropriate direct Dark/Rust parity pair today**. Its default Rust regex engine has linear-time DFA-style guarantees, whereas Dark’s stdlib `Regex` implementation is a pure backtracking matcher. A whole-program port would therefore violate this repository’s same-algorithm parity rule and add filesystem traversal, ignore-file behavior, encodings, binary detection, CLI parsing, and optional PCRE2 concerns that would obscure compiler performance. [ripgrep’s architecture and behavior](https://github.com/BurntSushi/ripgrep), [regex-engine distinction](https://ripgrep.dev/docs/regex/)

The appropriate benchmark is consequently a **ripgrep-derived, application-scale search workload**, not ripgrep wholesale:

- Include a versioned, embedded corpus: several source-like documents plus ignore rules and a small query set.
- Implement the same restricted search semantics in Rust and Dark: UTF-8 text, fixed query grammar, line-oriented matching, path filtering, match counting, and a stable result checksum.
- Initially restrict matching to literals, anchors, character classes, alternation, and bounded repetition only if both implementations share the same algorithm. Otherwise use literal search first and broaden only after a parity audit.
- Run the complete query corpus repeatedly inside the measured executable; prepare immutable corpus data outside the hot loop where appropriate.
- Keep Rust as the original audited reference and lock its source, Dark source, corpus, expected output, and workload parameters through the existing `PARITY.json` mechanism.

This gives the requested substantially larger application shape while preserving meaningful instruction-count comparison. It also matches Rust’s own runtime-suite guidance: prefer useful real-world code over microbenchmarks, keep workloads at least tens or hundreds of milliseconds, and embed reasonably sized input data for self-contained runs. [Rust runtime-benchmark guidance](https://raw.githubusercontent.com/rust-lang/rustc-perf/master/collector/runtime-benchmarks/README.md)

A template/static-site-generator benchmark is the runner-up. Rust has a maintained template benchmark whose `big_table` workload renders a 100×100 HTML table, but it mostly measures rendering and escaping; a ripgrep-derived search workload covers a broader application pipeline and better complements Dark’s existing numerical microbenchmarks. [Rust template benchmark](https://github.com/askama-rs/template-benchmark)
