Yes—but only **MiniJinja** is a sensible candidate for a direct Dark reimplementation. Askama and the other compile-time engines are not: their defining behavior is Rust procedural-macro code generation, while Dark has no corresponding macro-expansion model. Porting them would create a new template compiler rather than compare equivalent generated programs.

MiniJinja is different: it is a runtime Jinja/Jinja2-compatible interpreter, with parsing, an AST, dynamic values, scopes, expressions, loops, conditions, filters, escaping, inheritance, macros, and template lookup. Its upstream project explicitly aims for minimal dependencies and uses only `serde` as its principal public dependency. [MiniJinja](https://github.com/mitsuhiko/minijinja)

For the current `v2.22.0` default feature set, I counted physical Rust source lines from the frozen sources:

| Component | Rust lines | Role |
|---|---:|---|
| `minijinja/src` | 24,524 | Parser, AST, evaluator/VM, dynamic values, escaping, template management |
| `serde/src` v1.0.228 | 5,200 | Rust serialization integration |
| `memo-map/src` v0.3.1 | 401 | Internal memoization map |
| **Default closure** | **30,125** | Excludes Rust standard library, tests, examples, build tooling, and optional features |

That is roughly **150× the size of the repository’s current largest Dark benchmark source**. The exact number is deliberately stated as physical Rust lines, including blank lines and comments; a code-only metric would need to be defined before it becomes an acceptance target. Optional MiniJinja features add further dependencies: `aho-corasick` for custom syntax, `v_htmlescape` for speedups, `serde_json`, `indexmap`, Unicode helpers, and others. [MiniJinja manifest at v2.22.0](https://github.com/mitsuhiko/minijinja/blob/2.22.0/minijinja/Cargo.toml)

Feasibility assessment:

- **Full MiniJinja compatibility:** technically possible, but inappropriate as a benchmark-only change. It is a substantial language-runtime project—likely tens of thousands of Dark lines plus a large compatibility test corpus. Dark would also need an explicit substitute for MiniJinja’s dynamic `serde` value conversion and memoization behavior.
- **A frozen MiniJinja-compatible subset:** feasible and potentially excellent. Implement only the syntax used by a checked-in application template corpus: variables, escaped output, `if`, `for`, property/index access, and a small fixed filter set. Use immutable Dark records/ADTs and Dicts for the input model. Call it **MiniJinja-derived**, not MiniJinja-compatible generally.
- **Benchmark value:** high if it contains both `cold` (parse + render) and `warm` (preparsed template + render) workloads. The existing Rust template suite intentionally excludes setup and measures rendering only; that is correct for template-engine comparison, but insufficient alone for the desired application benchmark.

I would not choose Tera, Handlebars, Liquid, or the SSR engines for this effort. They have broader dependency and feature surfaces without giving a better benchmark shape. Askama is especially unsuitable because it renders generated Rust code after compile-time template processing; its architecture is precisely what the Dark reference could not reproduce fairly. [Askama architecture](https://github.com/askama-rs/askama)

So the practical option is: take MiniJinja’s template syntax and its `big_table`/`teams`-style rendering workload as inspiration, define a small frozen feature profile, implement that profile independently and equivalently in Rust and Dark, then use a larger catalog-page corpus. That produces an application-scale benchmark without covertly turning this issue into a full template-engine implementation project.
