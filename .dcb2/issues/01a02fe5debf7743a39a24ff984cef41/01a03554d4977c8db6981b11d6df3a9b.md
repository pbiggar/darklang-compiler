Rust’s maintained [template-benchmark](https://github.com/askama-rs/template-benchmark) is a **renderer comparison suite**, not a complete web-application benchmark. It compares 17 mature Rust template engines across three implementation styles: precompiled templates, interpreted templates, and server-side-rendering frameworks.

It has two canonical workloads:

- **`big_table`** creates a 100×100 HTML table from a prebuilt `Vec<Vec<usize>>`: 10,000 cells, repeated loops, integer formatting, HTML output allocation, and a large result.
- **`teams`** renders four scored teams for a year. It is small, but intentionally includes dynamic strings requiring HTML escaping and conditional rendering.

The harness is thoughtfully designed: it prepares the input and engine instance outside the measured iteration, times rendering only, validates every output with a fixed-seed hash, then clears the output buffer for reuse. It uses Criterion with 500 samples, a five-second warm-up, and a 60-second measurement period. The suite’s own description confirms both workload shapes and the distinction between precompiled and dynamic engines. [Benchmark README](https://github.com/askama-rs/template-benchmark)

For Dark, this has two important implications:

- It is a good source for a **large deterministic HTML-rendering workload**. `big_table` can translate directly into equivalent Rust and Dark programs that construct the same element structure and render the same HTML. Dark’s `Html` stdlib makes this unusually feasible.
- It is not fair to use Askama, Tera, or another engine as the Rust reference. Those engines compile or interpret a template language that Dark does not implement, so the comparison would measure template-engine architecture rather than Dark code generation. The Rust reference should instead be a direct Rust DOM/builder implementation matching the Dark program.

It is also not large enough on its own to meet the original “full application” goal: the inputs are deliberately narrow, and `big_table` is principally a rendering/allocation stress test. I would use it as the **rendering stage** of a larger benchmark, for example:

`fixed JSON catalog → typed records/filtering/grouping → conditional HTML catalog page → checksum`

That composite keeps the benchmark self-contained and deterministic while adding parsing, records, lists, Dict operations, filtering, formatting, escaping, and large output construction. It would be inspired by the Rust template benchmark’s tested rendering shape, but represent a small server-rendered application rather than a template-engine shootout.

Of the two supplied workloads, `big_table` is the better base for throughput and allocation behavior; `teams` should be incorporated as a feature requirement—escaped user text plus conditional sections—rather than retained as a standalone benchmark.
