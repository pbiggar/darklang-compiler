# Design brief

## Problem

Revalidation of DCB1@8a402797 against compiler C@0252155caa311db8fc33f6607c7ebefc3ee6a1f7 and interpreter I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d confirms that the compiler lacks the interpreter’s canonical immutable Blob, exposes incompatible binary signatures and encoding behavior, and has no certificate public-key extraction.

## Goals

- Make immutable Blob the canonical binary value across conversion, encoding, hashing, HMAC, and certificate operations.
- Match the interpreter’s observable values, accepted inputs, formatting, and error results.
- Preserve already-correct cryptographic results while explicitly separating compiler-only byte, decoding, digest, hexadecimal, and diagnostic extensions.

## Proposed solution

Introduce a first-class immutable Blob boundary and route the complete scoped binary family through it. Align public types and observable edge behavior with the pinned interpreter, reuse conforming cryptographic logic behind the new boundary, add the missing certificate capability, and retain the identified compiler-only surface solely as explicit extensions.

## Success criteria

- Pinned same-source Blob, Base64, cryptography, and certificate examples compile without adapters and produce interpreter-equivalent values and errors.
- Every scoped binary input and output uses Blob rather than the compiler-specific byte type.
- Invalid encoding, text-decoding, and certificate inputs are accepted or rejected with interpreter-compatible results.
- Parity evidence records both exact revisions and clearly distinguishes extensions, intentional divergences, and out-of-scope performance differences.

## Open questions

- Should Blob identity, persistence, and equality semantics be included here or handled as a separate value-semantics boundary?
- Should existing binary and cryptography extensions remain in the default compiler dialect or require an explicit extension/internal surface?
