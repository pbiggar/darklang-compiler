Yes—the installed interpreter is outdated: it reports `alpha-a70f30d` (2026-05-26) and itself says `latest: alpha-d5076d6`. The latest published release is [v0.0.34 / `d5076d6`](https://github.com/darklang/dark/releases/tag/v0.0.34), published 2026-08-09.

We can update it: the image already uses `scripts/install-darklang-interpreter.sh`, which selects the newest matching GitHub-release binary. Rebuilding the container would install v0.0.34; running that script in an existing container would also replace the interpreter.

However, updating is not required to correct the compiler target. The compiler’s parity work is pinned to upstream `04fbe9d` (2026-08-10), which is **one commit newer than** the v0.0.34 release artifact. In other words, the installed binary is stale, but the compiler has been targeting a slightly newer unreleased upstream revision already. Updating from `a70f30d` to `d5076d6` should therefore improve validation-tool consistency without requiring compiler source changes.

Upstream `main` has since advanced to [`7fc6d80`](https://github.com/darklang/dark/commit/7fc6d805950f89cb1945045b9bf8cdfd3e64cfc7), 191 commits beyond the compiler’s pin, but there is no newer published CLI release. Those unreleased changes include package-root parsing rules, bare `Some`/`None` and `Ok`/`Error` constructor resolution, at-rest package type checking, and more accurate type-error naming. A future move of the compiler target from `04fbe9d` to current `main` would need a deliberate compatibility pass and E2E coverage for those behaviors; it should not be bundled with the safe interpreter-binary refresh.
