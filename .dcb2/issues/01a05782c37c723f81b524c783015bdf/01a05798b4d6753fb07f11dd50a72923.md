Recommend two deliberately separate updates:

1. Refresh the container interpreter to released v0.0.34 (`d5076d6`). This is low risk: the repository already has an installer that selects that release, and the compiler’s existing reference pin (`04fbe9d`) is one commit newer. Rebuild the container, confirm `darklang-interpreter --version`, then run the existing full test suite and interpreter-validation workflow. No compiler behavior change should be expected.

2. Treat alignment with current upstream `main` (`7fc6d80`, 191 commits past the pin) as a compatibility project, not a container-maintenance task. First lock a target upstream SHA and capture an upstream test/stdlib diff. Then add failing E2E tests for observable language changes before adapting the compiler: package-root declaration parsing, bare `Some`/`None` and `Ok`/`Error`, and any changed type-error presentation. The at-rest package type checker is upstream authoring/package infrastructure, so it should be evaluated for relevance rather than copied into the native compiler by default.

This sequencing avoids using an unreleased moving branch as the validation target, while preserving a clear path to adopt its language-level changes once they are verified. I would make the release refresh one small issue and the upstream-SHA compatibility audit a follow-up issue.
