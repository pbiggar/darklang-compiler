Understood—the subject is **Dark Compiler’s own compilation of Dark source**, not `dotnet build`/F# compilation of this repository, and not execution of the emitted Dark binary.

That narrows the useful options considerably:

- `./dark -vv program.dark -o /tmp/program.out` already measures the compiler pipeline itself: parse, type check, AST→ANF, SSA/optimization, register allocation, code generation, and emit. This is the most directly relevant attribution data.
- The test suite’s E2E `compile_ms` is also relevant, but it is not a clean compiler-build benchmark: it compiles many small expressions with shared stdlib/preamble contexts and also performs test-host work. It is useful for finding slow fixtures, not as the primary build-time metric.
- Cachegrind can measure the F#/.NET Dark Compiler process while it compiles a fixed Dark program. That excludes runtime of the generated program if the command only compiles, but includes process startup, .NET runtime/JIT initialization, reading sources/stdlib, and writing the ELF/Mach-O output. This is a stable measure of total compiler *work*, rather than build latency.
- `perf stat` would provide the same general idea with hardware retired-instruction counts and much lower overhead, if enabled on a dedicated benchmark host.

The important distinction is between two valid metrics:

1. **End-to-end Dark compilation:** invoke `./dark` on a source file and measure until its output is written. This is the user-visible build time; startup, stdlib loading, and emit belong in it.

2. **Pipeline-only compilation:** invoke `CompilerLibrary` with a prepared stdlib/preamble context and measure `CompileReport.CompileTime` or its pass timings. This isolates optimization work, but deliberately excludes setup that a CLI user pays.

For this issue, I would measure both but gate primarily on the first. Use Cachegrind/perf instruction counts to make its regression signal stable, and retain existing `-vv` timings to determine which compiler pass caused any count increase. Do not use the generated program’s runtime benchmarks or F# project-build tools for this purpose.
