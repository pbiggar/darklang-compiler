Yes. Native AOT plus Cachegrind is the sensible deterministic approach here; my prior recommendation overcorrected.

Publish Dark Compiler as a Linux Native AOT executable, then run that executable under Cachegrind to compile a fixed Dark source file. Native AOT removes runtime JIT compilation: the executable contains ahead-of-time-compiled application and required runtime code. Linux Arm64 is a supported Native AOT target. [Native AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

Cachegrind’s `I refs` is its count of executed instructions. For one fixed, single-threaded compiler invocation, it provides an exact user-space dynamic-instruction count—covering Dark Compiler, its AOT runtime support, source/stdlib processing, and output emission, but excluding kernel syscall execution. [Cachegrind manual](https://valgrind.org/docs/manual/valgrind_manual.pdf)

That gives the desired metric:

```text
fixed AOT Dark Compiler + fixed Dark input + fixed flags
→ exact executed-instruction count
```

It is a much better deterministic proxy for compilation cost than wall-clock time. It also avoids measuring Dark program runtime, provided the invocation only compiles and does not use `--run`.

Two caveats:

- Native AOT must successfully publish this F# compiler. It forbids runtime code generation and dynamic assembly loading, so this needs a one-time compatibility trial; the AOT analyzers/publish output are the authority, not an assumption.
- “Deterministic” should be verified empirically before making it a gate: run the identical AOT executable and input under Cachegrind several times and require identical `I refs`. If they differ, investigate runtime randomness or nondeterministic compiler traversal before relying on the metric.

Cachegrind will be slow, which is acceptable for a focused compile-time benchmark suite. Use instruction references as the primary exact baseline; optionally retain its branch and data-reference counters as diagnostic detail, not as the initial gate.
