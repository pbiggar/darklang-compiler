Yes—there is a better fit if the goal is a stable regression gate: count work rather than elapsed time.

The closest option is **Valgrind Cachegrind instruction counts**. The repository already uses this model for generated-program performance: `benchmarks/run_benchmarks.sh` defaults to Cachegrind and makes Hyperfine opt-in. Cachegrind reports deterministic simulated instruction references for a deterministic execution path, plus optional data-cache and branch statistics. A compiler gate could run a fixed corpus through `./dark` under Cachegrind and compare instruction counts by compiler pass workload/program.

That answers “did this compiler change do more or less computational work?” much more reliably than wall time. It does not answer exact real-machine latency: Cachegrind is very slow, simulates caches rather than observing this CPU, and a .NET run includes managed runtime/JIT work. Those are acceptable trade-offs for a regression signal, especially if the same runtime, input corpus, and invocation are fixed.

Other options, by purpose:

| Option | Signal | Stability | Best use |
|---|---|---|---|
| Cachegrind | Simulated instruction/data-cache/branch counts | High | Default compile-work regression gate |
| `perf stat` | Hardware retired instructions, cycles, cache misses | High for instructions; cycles vary | Validate Cachegrind findings on real hardware |
| In-process benchmark harness / BenchmarkDotNet | Timed repeated calls to `CompilerLibrary` | Statistical, not deterministic | User-visible warm compile latency |
| `/usr/bin/time` | Wall, user CPU, system CPU, memory | Moderate | Quick whole-command sanity check |
| Existing `-vv` / test JSON | Per-pass and per-test elapsed time | Diagnostic only | Locate a regression |
| `dotnet-trace` / counters | CPU samples, allocations, GC/JIT events | Diagnostic only | Explain a known regression |

`perf stat -e instructions,cycles,task-clock,branches,branch-misses -- ./dark ...` is the lower-overhead real-hardware alternative. Retired instruction counts are usually a strong signal; cycles and cache misses are inherently machine-state-sensitive. It is currently unavailable in this workspace because `perf` is not installed and the container blocks unprivileged performance counters, but it would be attractive on a dedicated benchmark machine.

For F# project-build performance, `fsc --times` and MSBuild binlogs remain useful, but they measure building Dark Compiler itself—not the performance of Dark Compiler compiling Dark code.

My revised recommendation: use a small representative compiler-input corpus with Cachegrind instruction counts as the correctness-like gate; retain elapsed-time measurements only as a secondary, statistical confirmation of user-visible compile latency. Do not use Cachegrind for the full test suite by default: it would be extremely slow and mixes compiler work with test-host and generated-program execution.
