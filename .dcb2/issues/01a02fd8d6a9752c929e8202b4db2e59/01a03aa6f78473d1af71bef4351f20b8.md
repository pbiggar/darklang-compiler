Then elapsed time, `perf`, and Cachegrind must not be the gate. They all observe execution and therefore cannot provide a strict deterministic contract. Cachegrind is much more repeatable than timing, but a .NET process still has runtime/JIT and process-level behaviour that should not be assumed bit-for-bit invariant without proving it.

The deterministic solution is an **explicit compiler work metric**: instrument Dark Compiler to count defined units of work while compiling a fixed Dark corpus, then compare those integer counters exactly.

Examples of useful deterministic counters:

- parser tokens/nodes processed;
- type-check operations and instantiated generic functions;
- ANF, MIR, and LIR functions/instructions created;
- optimizer iterations and rewrite attempts;
- SSA variables/CFG edges;
- register-allocation vertices, interference edges, and worklist operations;
- emitted instruction and output-byte counts.

The metric should be collected inside `CompilerLibrary`, separately for each pass and summed only from explicitly documented counters. It would compile Dark programs only—never run the produced binary—and emit a stable JSON result suitable for an exact baseline/regression comparison.

This does not claim that, for example, one interference edge costs the same as one parser token. It gives a deterministic measure of the algorithmic work that the compiler performs and pinpoints which pass increased it. That is the appropriate primary gate for this issue.

Cachegrind can later be used as an optional validation tool to check whether a lower deterministic work count also reduces real executed instructions, but it should not define the pass/fail result.
