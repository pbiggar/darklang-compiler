The repository already has the foundations for this: compiler pass timing (`./dark -vv`) and a test-timing report/JSON export (`./run-tests --ai --timings-json=/tmp/dark-tests.json`). The missing piece is a repeatable statistical harness for a fixed, representative compile workload.

Recommended approach:

1. Use `hyperfine` as the standard compile-time comparison tool. It is already installed (v1.18.0), supports warmups, repeated samples, and JSON export. Benchmark the already-built `./dark` against a selected set of representative sources—ideally the routine benchmark inputs—and write outputs under `/tmp`. Run at least 20 warm samples; report median, mean, standard deviation, and the raw JSON artifact. Keep “cold build/compile” measurements separate from warm compiler measurements.

2. Use the existing timings to localize regressions before profiling. `./dark -vv <program> -o /tmp/out` emits per-pass time, including parse, type checking, AST→ANF, SSA, optimization, register allocation, code generation, and emit. The test executable already records per-E2E compile/runtime time and aggregate pass time; `--all-test-timings` is human-readable and `--timings-json=PATH` is suitable for comparison tooling.

3. Measure test execution separately from building it. `./run-tests` always builds first, using serial MSBuild and disabled build servers, so its wall-clock time conflates F# compilation with test execution. After one explicit build, benchmark `bin/Tests/Debug/net10.0/Tests --ai` with `hyperfine`; use the JSON timing output to identify the slow test/pass. The current runner is serial and shares prebuilt stdlib/preamble contexts, so per-test compile values deliberately do not represent a fully cold compiler invocation.

4. For a suspected hot path, use `dotnet-trace` (EventPipe CPU sampling) on the compiler or test process. This is the best next diagnostic for managed F# code: it attributes samples to methods and also exposes GC/JIT/loading behavior. `dotnet-counters` is useful for a quick GC/allocation-rate check; `dotnet-gcdump` is for retention diagnosis, not normal timing—it forces a full GC and perturbs the measurement. [.NET diagnostic tools overview](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/tools-overview), [EventPipe overview](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe)

5. Treat F#/.NET build performance as a separate metric. F# supports `--times` for compiler-phase timing, and MSBuild binary logs (`-bl`) show project/task-level build work. A binlog adds measurable overhead, so use it to diagnose a regression, not as the benchmark itself. [F# compiler options](https://learn.microsoft.com/en-us/dotnet/fsharp/language-reference/compiler-options), [MSBuild binary logs](https://learn.microsoft.com/en-us/visualstudio/msbuild/obtaining-build-logs-with-msbuild?view=vs-2022)

Linux `perf` is not currently viable in this workspace: it is absent and `perf_event_paranoid` is `4`, which blocks unprivileged access. The environment is Linux ARM64 with .NET 10, so a privileged host/container could instead use the new `dotnet-trace collect-linux` facility for unified managed events, kernel events, and native call stacks; it requires root/CAP_PERFMON, kernel 6.4+, and is still preview. [dotnet-trace collect-linux](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace?WT.mc_id=dotnet-00000-cephilli)

I would make `hyperfine` + the existing per-pass JSON the default decision gate, then reach for `dotnet-trace` only when a statistically real regression needs attribution. No files were changed.
