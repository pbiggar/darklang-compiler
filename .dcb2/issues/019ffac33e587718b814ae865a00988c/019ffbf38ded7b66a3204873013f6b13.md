# Design brief

## Problem

At compiler 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, compiled programs lack the HTTP family available in interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, preventing behavioral parity for clients, event streams, routing, and servers.

## Goals

- Match the interpreter’s public buffered and streaming HTTP behavior, including observable success and error semantics.
- Provide incremental server-sent-event handling, request routing, configuration, and server execution.
- Record exact revisions and source or same-source probe evidence for every comparison, explicitly labeling extensions and intentional divergences.

## Proposed solution

Deliver one coherent HTTP runtime family with shared public data and error semantics, transport-backed buffered and streaming clients, incremental event-stream parsing, pure routing, and bounded server execution. Treat interpreter behavior at the pinned revision as authoritative; preserve differences within their related areas and expose compiler-only behavior only when explicitly classified and documented.

## Success criteria

- Scoped same-source programs exhibit equivalent observable results under the pinned compiler and interpreter revisions.
- Streaming remains incremental, event parsing remains correct across input boundaries, and routing and body-limit behavior match the baseline.
- Client and server failures map to the expected public error forms without uncategorized runtime failures.
- Every retained parity claim identifies exact revisions and current evidence; all differences are classified as gaps, extensions, or intentional divergences.

## Open questions

- Which native transport and TLS strategy can preserve the interpreter’s observable error behavior across supported platforms?
- What lifecycle, cancellation, and shutdown behavior should apply where the interpreter’s public behavior is unspecified?
- Should capabilities beyond the parity surface be deferred or exposed as explicitly marked compiler-only extensions?
