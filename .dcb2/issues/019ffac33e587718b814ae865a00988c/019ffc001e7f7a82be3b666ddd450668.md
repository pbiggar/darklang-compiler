# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, compiled programs lack the HTTP runtime family exposed by interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, preventing parity for clients, event streams, routing, and servers.

## Goals

- Match the pinned interpreter’s observable buffered, streaming, SSE, routing, configuration, and server behavior.
- Copy the interpreter modules directly wherever compatible, minimizing duplicated design and semantic drift.
- Document every retained difference as a parity gap, compiler-only extension, or intentional divergence.

## Proposed solution

Port the interpreter’s public HTTP modules as faithfully as possible, preserving their types and pure behavior, and supply the compiler runtime integration needed for client transport, streaming, and server execution. Treat the pinned interpreter revision as authoritative for observable behavior while keeping necessary native-platform differences explicit and contained within the same HTTP family.

## Success criteria

- Same-source HTTP programs produce equivalent observable results under the recorded compiler and interpreter revisions.
- Streaming and event parsing remain incremental across input boundaries, while routing and body limits follow the baseline.
- Client and server failures consistently use the expected public error forms without uncategorized runtime failures.
- Any behavior beyond or differing from the baseline is explicitly classified and documented.

## Open questions

- Which native transport and TLS strategy best preserves the interpreter’s observable behavior across supported platforms?
- What lifecycle, cancellation, and shutdown semantics should apply where the baseline leaves behavior unspecified?
- Should capabilities beyond the parity surface be deferred or exposed as documented compiler-only extensions?
