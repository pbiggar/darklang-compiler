# Implementation plan

Single contained implementation. Behavioral comparisons were revalidated at compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 against darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d; integration locations were inspected at compiler HEAD e8366cd8ef8290652e7507353e6c9dd11d93785c. Remove generalized bare-comma tuples, comma-spelled tuple types, and .N access; retain match-specific bare tuple grammar and AOT static typing. Compiler-only record patterns remain outside this tuple scope.

## Work item 01a0020f6beb7af4a4e52e6825757f4b

Title: Establish the tuple parity regression contract

Category: behavior

Evidence: DCB1 8a402797 broadly described tuples as mature, while compiler tuple and pattern E2E files expose narrower coverage and unsupported nesting. Interpreter 04f tests in backend/testfiles/execution/language/collections/dtuple.dark, language/basic/elet.dark, and language/flow-control/ematch.dark provide executable baselines.

Outcome:

Add focused same-source cases for unit, grouping, singleton rejection, heterogeneous and nested construction, tuple types, access through parity APIs, let/lambda destructuring, recursive match patterns, exact-arity failure, equality, rendering, runtime values, and left-to-right evaluation.

## Work item 01a0020f6beb741bbeca1d48d7051ed1

Title: Make invalid tuple arities unrepresentable

Category: type

Evidence: Compiler b2 AST.fs represents TTuple, PTuple, and TupleLiteral with unrestricted lists; current LPTuple already uses first/second/rest. Interpreter 04f ProgramTypes.fs and RuntimeTypes.fs use first, second, and rest for TTuple, ETuple, MPTuple, LPTuple, KTTuple, DTuple, and CreateTuple.

Outcome:

Introduce a reusable first/second/rest tuple shape and use it for tuple types, expression literals, match patterns, let patterns, and ANF tuple allocation; provide pure mapping, folding, length, and positional traversal helpers while retaining unit as separate primitive cases.

## Work item 01a0020f6beb758694a720b98450e8ba

Title: Align tuple, grouping, and unit grammar

Category: behavior

Evidence: Compiler b2 1_Parser.fs correctly groups expressions but turns parenthesized match patterns into PTuple lists, accepts comma tuple types, and 1_InterpreterParser.fs:2669 generalizes bare tuples to top level. Interpreter 04f LibParser/Parser.fs parses grouped patterns and types separately, requires a second tuple element, uses A * B types, and special-cases bare tuples under match.

Outcome:

Make both parser paths distinguish (), (expression), and tuples of two or more elements; reject trailing-comma singleton forms; parse and print tuple types with ordered star-separated elements; restrict bare comma tuples to the interpreter-supported match scrutinee and pattern contexts.

## Work item 01a0020f6beb7a76b62fcde978ebdb5d

Title: Separate source access from internal projection

Category: type

Evidence: Compiler b2 AST.fs exposes TupleAccess(expr,index), both parsers accept .integer postfixes, and TypeChecking/AST_to_ANF synthesize the same node internally. Interpreter 04f has no tuple-access expression node or .N grammar; its lowering projects registers from typed first/second/rest shapes.

Outcome:

Remove TupleAccess from source syntax and the source AST. Replace compiler-generated projections used by destructuring, equality, rendering, closures, dictionaries, and enum payloads with an internal operation whose position is validated against known layout metadata.

## Work item 01a0020f6beb742bb2f6a0d9d2dccf04

Title: Provide interpreter-compatible tuple access APIs

Category: function

Evidence: Interpreter 04f packages/darklang/stdlib/tuple2.dark and tuple3.dark define the public tuple operations entirely through construction and destructuring. Compiler stdlib Tuple2.dark and Tuple3.dark have corresponding APIs but currently use comma tuple types.

Outcome:

Match the interpreter Tuple2 and Tuple3 create, first, second, third, swap, and mapping functions using tuple construction and destructuring, while arbitrary-arity access remains expressible through patterns.

## Work item 01a0020f6beb752db91daab3f8d41b3c

Title: Migrate maintained tuple-bearing sources

Category: other

Evidence: At HEAD, a focused scan finds 162 .N source accesses across 16 Dark/E2E/benchmark files, including Dict.dark, native ownership tests, four benchmark inputs, tuples.e2e, and tuple-construction-from-access.e2e. docs/current-language-features.md still advertises zero-based tuple access.

Outcome:

## Work item 01a0020f6beb723198a81440cb9a7998

Title: Type tuples positionally through all substitutions

Category: behavior

Evidence: Compiler b2 1.5_TypeChecking.fs constructs TTuple from inferred element lists and checks expected list length, while many substitution and traversal paths independently manipulate those lists. Interpreter 04f ProgramTypesToRuntimeTypes.fs recursively converts first, second, and rest without losing position or arity.

Outcome:

Infer and check each ordered element against its corresponding expected type, require exact construction arity, and preserve heterogeneous nested shapes through aliases, generics, unification, monomorphization, renderer generation, and reference-count shape analysis.

## Work item 01a0020f6beb7680a603cb6a78761f54

Title: Preserve ordered native tuple values

Category: behavior

Evidence: Compiler ANF TupleAlloc currently holds a list; 3_ANF_to_MIR.fs allocates length*8 bytes and emits stores at index*8 in two lowering paths. Interpreter 04f ProgramTypesToRuntimeTypes.fs sequences first, second, then rest before CreateTuple, and Interpreter.fs materializes DTuple(first,second,rest).

Outcome:

Lower every element exactly once from left to right, carry its positional type through ANF, MIR, reference counting, and both backends, and allocate contiguous ordered slots with complete retain/release coverage for nested managed values.

## Work item 01a0020f6beb78aca01f0e8c1be308ab

Title: Lower tuple patterns recursively and atomically

Category: function

Evidence: Current 2_AST_to_ANF.fs contains several duplicated PTuple collectors, some using non-exact length logic and four paths returning 'Nested pattern in tuple element not yet supported'. pattern_matching.e2e:414, :420, and :461 preserve these gaps; interpreter 04f Interpreter.fs recursively matches first/second/rest and requires exact rest-list length.

Outcome:

Use shared typed tuple-shape and projection helpers for let, lambda, and match lowering. Validate exact arity before projection, recursively compose tuple subpatterns with supported tuple, list, and constructor patterns, preserve positional binding order, and make every shape or element mismatch take the normal non-match path without leaking bindings or evaluating guards and bodies.

## Work item 01a0020f6beb7994a960e3b32c2e0753

Title: Retain structural tuple equality during representation changes

Category: behavior

Evidence: Current docs/comparison-parity.md and 1.5_TypeChecking.fs:5406 record an existing typed structural implementation. Interpreter 04f Builtins.Pure/Libs/NoModule.fs compares first, second, rest length, and rest elements recursively; the work is integration preservation rather than a new comparison design.

Outcome:

Adapt the existing comparison expansion to the structural tuple shape and internal projection operation so equality requires equal arity and recursively equal ordered elements, evaluates operands once, derives inequality by negation, and continues to reject tuple ordering.

## Work item 01a0020f6beb7da29bbc0043a0e8c9b6

Title: Match tuple value rendering

Category: function

Evidence: Current 1.6_ValueRendering.fs:250 always concatenates a one-line tuple, while Runtime.fs only supplies primitive no-newline output helpers. Outcome:

Render tuple values recursively with parentheses, comma-space separators, source order, and the interpreter's short-versus-indented multiline layout; use typed internal projections and the existing primitive renderers so nested tuples inside lists and enum values share one presentation path.
