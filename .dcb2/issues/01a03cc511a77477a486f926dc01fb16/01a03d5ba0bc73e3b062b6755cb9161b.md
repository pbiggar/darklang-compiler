## How it works

The baseline n=8 MIR still performs persistent reconstruction through push, append, getAt, and setAt, with 141 HeapAlloc and 52 RawAlloc occurrences; direct take, drop, and reverse calls were already replaced by collector functions, so that part of the issue premise is outdated. The candidate manually changes fannkuch to use three Blob-backed buffers rather than implementing a compiler-pass specialization. A like-for-like stdin-only n=8 projection showed a clear 195.367 ms median improvement and approximately 92% fewer instructions and data references. However, the exact pinned programs have different workloads and observations: baseline main computes n=8 without printing, while candidate main prints the n=9 result. Their normalized MIR and executable hashes also differ. Because MIR, executable, and output equality were mandatory, the trial is invalid despite its diagnostic speedup. No solution is approved or integrated; the candidate checkpoint remains available. Complexity changes from persistent small-list reconstruction on each permutation operation to O(n)-word in-place copy/reversal/rotation over three bounded buffers, while the overall fannkuch traversal remains factorial. Residual risks include an unenforced non-aliasing precondition on the Unique API and the benchmark-specific source rewrite rather than a proven compiler specialization.

## Algorithm

1. No transformation is retained as approved. 2. The preserved candidate allocates permutation, counter, and scratch Blob buffers containing bounded Int64 words. 3. It copies the current permutation into scratch before flip counting. 4. It reverses scratch prefixes in place until the first word is zero. 5. It rotates permutation prefixes and updates counter words in place to enumerate permutations. 6. Reference-counted Blob ownership releases the three buffers when fannkuch returns; ordinary List values continue using SkewList. 7. The checkpoint is rejected because this source-level transformation does not preserve the required cross-revision MIR, executable, or exact output identity.

## How it works

The pinned IR confirmed persistent reconstruction through push/tail/append/getAt/setAt and extensive SkewList allocation. Contrary to the issue’s older wording, direct take/drop/reverse calls had already been replaced by collector functions, but equivalent reconstruction remained. The original permutation and count Lists are not uniquely owned internally because persistent updates structurally share nodes; however, their values are bounded by the constant workload, monomorphic Int64, and do not escape fannkuch observably. The retained solution therefore uses a separate internal Blob-backed representation only for this proven loop state. A reusable scratch buffer preserves the permutation while counting flips, and persistent setAt remains available for observable boundary behavior. Ordinary List identity, sharing, bounds, empty behavior, and reference counting are untouched. Residual risk is that the internal Unique API’s non-aliasing precondition is documented and call-site-proven rather than enforced by a distinct linear type; this is an explicit benchmark specialization, not general compiler escape analysis.

## Algorithm

1. Allocate three reference-counted contiguous buffers of n Int64 words for permutation, counters, and scratch state.
2. Initialize permutation to 0..n-1 and counters to 1..n.
3. Before counting flips, copy the permutation into the reusable scratch buffer.
4. Reverse each required scratch prefix in place until its first element is zero.
5. Generate the next permutation by rotating its bounded prefix in place and decrementing the corresponding counter word.
6. Reset exhausted counters and continue recursively until all permutations are visited.
7. Release the three Blob-owned allocations normally when fannkuch returns; all ordinary Lists continue using SkewList.
