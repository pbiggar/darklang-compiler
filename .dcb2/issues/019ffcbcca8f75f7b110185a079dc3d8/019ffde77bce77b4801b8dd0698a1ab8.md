# Design brief

## Problem

Documentation is extensive but fragmented: 111 visible Markdown documents (about 20,000 lines) coexist with 538 machine-managed records, without a central index or clear separation between current guidance, generated data, and history. Several status documents contradict newer material, while architecture, memory management, benchmarks, and agent workflows are duplicated or burdened by implementation journals, test inventories, and obsolete snapshots.

## Goals

- Make documentation easy to discover by audience and purpose
- Establish one trustworthy current source for each topic
- Reduce verbosity, duplication, and maintenance burden while preserving durable rationale
- Clearly separate maintained guidance from generated records and historical evidence

## Proposed solution

Adopt a small documentation taxonomy covering navigation, current conceptual guidance, operational procedures, generated reference data, and archived history. Provide one central index; designate a canonical document for each subject; consolidate overlapping architecture, memory, benchmark, and workflow material; replace hand-maintained status matrices with generated data or concise links where possible; archive or remove completed investigations and obsolete plans; trim commit logs, exhaustive test lists, and implementation-level narration; reconcile all remaining status and backlog claims with current behavior; and add lightweight ownership, freshness, and link-integrity conventions.

## Success criteria

- A newcomer can reach setup, architecture, language, testing, benchmarking, and contributor guidance from one index
- Every subject has one identifiable current source with no contradictory status claims
- Primary documentation is materially shorter, with generated and historical material clearly separated from maintained guidance
- Current-state claims match repository behavior and internal links remain valid
- Documentation has an explicit maintenance and archival policy that limits future drift

## Open questions

- Should machine-managed issue records remain versioned alongside human documentation or move to a separate store?
- How much benchmark and investigation history must remain in the working tree rather than relying on generated artifacts or version history?
- Which current-state tables should be generated automatically versus maintained manually?
