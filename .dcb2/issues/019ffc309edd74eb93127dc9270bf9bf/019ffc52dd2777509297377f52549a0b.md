# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, record behavior is not consistently aligned with darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d across syntax, typing, matching, equality, rendering, and runtime identity.

## Goals

- Match the interpreter’s public record behavior across declarations, construction, access, nested updates, patterns, generics, equality, rendering, and runtime identity.
- Match interpreter rules for nominal identity, field ordering, duplicate, missing, and unknown fields, and update evaluation order.
- Remove legacy record forms, migrate record-bearing sources, and explicitly classify any remaining compiler-only extensions or intentional divergences.

## Proposed solution

Adopt one canonical, interpreter-compatible record model throughout the compiler. Resolve each record to its declared nominal identity and generic arguments, preserve the interpreter’s distinct ordering and evaluation semantics, validate fields and patterns at the same boundaries, and carry identity through lowering and runtime values so matching, equality, and rendering agree with the baseline. Remove alternate legacy syntax and semantics as affected sources migrate.

## Success criteria

- Same-source record programs produce equivalent accepted values, diagnostics, evaluation order, pattern results, equality results, rendering, and runtime identity at the pinned revisions.
- Generic and nested records retain their declared identity and type arguments through construction, access, update, matching, and equality.
- Duplicate, missing, and unknown fields behave exactly like the interpreter in declarations, expressions, updates, and patterns.
- Legacy forms are rejected, record-bearing sources use the canonical forms, and every surviving difference is documented as an intentional divergence.
