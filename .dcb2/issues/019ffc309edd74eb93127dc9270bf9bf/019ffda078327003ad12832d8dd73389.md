# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, records only partially match darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d: legacy syntax, incomplete declaration validation, flattened identity, generic metadata, record patterns, and some rendering semantics diverge.

## Goals

- Adopt the interpreter’s public record syntax and nominal, qualified identity model.
- Match construction, access, nested update, generic typing, field validation, equality, rendering, and evaluation order.
- Remove record patterns and other compiler-only record forms, while documenting ahead-of-time validation as an intentional phase difference.

## Proposed solution

Establish one interpreter-compatible record contract across parsing, static typing, lowering, and runtime boundaries. Preserve resolved nominal identity and declared generic arguments while retaining efficient fixed-layout native storage where it is unobservable. Apply interpreter field and update semantics, reuse portable interpreter behavior where practical, align equality and rendering with resolved identity, reject unsupported record patterns, and migrate record-bearing sources to the canonical syntax.

## Success criteria

- Same-source valid record programs produce equivalent values, access and update results, evaluation order, equality, and rendering at the pinned revisions.
- Duplicate, missing, unknown, empty, and incorrectly typed fields are rejected consistently, with compile-time rejection explicitly classified where the interpreter fails at runtime.
- Nested and generic records preserve declared type identity and type-argument order through construction, update, equality, and presentation.
- Legacy record forms and record patterns are no longer accepted, and every remaining difference is documented as a compiler extension or intentional ahead-of-time divergence.
