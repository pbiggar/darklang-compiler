# Design brief

## Problem

At compiler 7e76432aa807d127e73a2f33665f1ec6998c8335 versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, integer support has incomplete fixed-width APIs, partial arbitrary-width parity, and non-operational public 128-bit support despite literal scaffolding.

## Goals

- Match every interpreter-declared integer operation, conversion, result, and failure contract.
- Provide ownership-correct arbitrary-width and signed/unsigned 128-bit representations on both native targets.
- Retain existing compatibility helpers as clearly documented compiler extensions.

## Proposed solution

Create one shared integer semantics layer: retain canonical arbitrary-width storage, establish an ownership-correct 128-bit representation with wrapping primitives, complete fixed-width and checked conversion primitives, and reuse the interpreter’s portable validation and aggregation wrappers. Centralize parsing, remainder, randomness, bounds, overflow, and runtime-error behavior while keeping compatibility aliases, extra comparison/equality helpers, bit-count/parity helpers, and unsigned signed-style helpers outside the parity surface. Preserve compile-time type enforcement as the intentional AOT divergence.

## Success criteria

- All interpreter-declared integer behavior produces matching values, result shapes, formatting, conversions, and user-visible failures at the pinned revisions.
- Overflow, zero division, modulus, shifts, parsing, random bounds, and conversion boundaries match the interpreter contract.
- The canonical signed 128-bit wrapping-addition boundary case produces the interpreter result.
- Compiler-only helpers and intentional AOT differences are explicitly classified without expanding the parity API.
