# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 versus interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, user-defined algebraic data types do not consistently share the interpreter’s syntax, name resolution, typing, construction, or runtime identity semantics.

## Goals

- Make current interpreter behavior the parity baseline for declarations and constructors.
- Support nullary, payload, recursive, generic, qualified, and colliding constructors consistently.
- Match interpreter rejection of duplicate definitions, invalid declarations, and incorrect payload arity.
- Preserve nominal constructor identity through evaluation, rendering, and equality; remove compiler-only syntax and explicitly document any intentional divergence.

## Proposed solution

Adopt one interpreter-compatible ADT model across parsing, declaration validation, constructor resolution, type checking, lowering, and runtime values. Resolve constructors using their module and declaring-type context, instantiate generic and recursive types consistently, enforce payload shape and evaluation semantics, and retain nominal identity at runtime. Migrate affected sources away from compiler-specific declarations and construction forms, then remove those extensions.

## Success criteria

- The same valid ADT programs compile and behave identically at both pinned revisions across construction, qualification, recursion, generics, rendering, and equality.
- The same invalid declarations, duplicate or ambiguous names, and payload-arity errors are rejected with equivalent semantic outcomes.
- Constructors with matching names or shapes from different types or modules remain distinct.
- Compiler-specific ADT syntax is absent from migrated sources and no longer accepted unless recorded as an intentional divergence.
