# Trial result

The preserved candidate is correct on the bounded focused workload but shows no clear Register Allocation performance win. No established-suite improvement was proven; overall multiplier: 1×.

## Evidence

## Problems

Reduce spill-frame size when separately spilled values have disjoint live ranges.

## Solution

The transformation is safe for a graph edge because the later-colored endpoint always avoids slots assigned to earlier interfering neighbors, preserving simultaneous-live separation; however, the representative existing `tak` workload produced byte-identical code and equal Register Allocation medians, so there is no retained measured benefit. The candidate also lacks the requested ARM64/x64 generated-code regressions and a dedicated spill-heavy runtime input.

## Implementation

- Candidate greedily reuses an 8-byte negative spill slot when no already-assigned interference neighbor uses it.
- Candidate derives the aligned spill frame from the deepest assigned slot.
- Candidate adds a chordal-graph interference test and documents spill-slot coloring.

### Algorithm

1. Keep physical-register assignments unchanged.
2. Enumerate spilled or invalid-color vertices in domain order.
3. For each spill, inspect assigned interference neighbors.
4. Choose the first unused negative 8-byte slot.
5. Align the deepest assigned spill offset to 16 bytes.

### Example

For three mutually non-interfering forced spills, the candidate can assign all values `-8`; for a three-way call-live clique it assigns distinct slots. The measured existing `tak` workload did not contain a changed allocation pattern: baseline and candidate executables were identical.
