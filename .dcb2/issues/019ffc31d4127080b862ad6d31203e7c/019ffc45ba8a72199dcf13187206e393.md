# Design brief

## Problem

Compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 lacks the interpreter’s HTTP runtime family, preventing compatible HTTP clients, event streams, routing, and servers; interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d is the parity baseline, with DCB1 report commit 8a402797 retained only as historical evidence.

## Goals

- Provide interpreter-compatible buffered and streaming HTTP clients, authentication, content types, and structured errors.
- Preserve observable event-stream parsing across arbitrary chunks, multiline data, blank blocks, and end-of-stream.
- Provide compatible request routing, configuration, body limits, and server lifecycle behavior.
- Record comparison revisions and explicitly classify compiler-only extensions and intentional divergences.

## Proposed solution

Deliver one coherent HTTP runtime capability: port the portable language-level behavior from the interpreter and connect it to compiler-native transport, streaming, cancellation, cleanup, and server facilities. Define ownership and lifecycle boundaries for streams and servers, enforce configured body limits, and maintain a revision-stamped parity record distinguishing shared behavior from unavoidable runtime-specific differences.

## Success criteria

- The same supported programs produce equivalent requests, responses, errors, authentication headers, and content-type behavior on the compiler and baseline interpreter.
- Streaming produces equivalent data and event sequences regardless of transport chunk boundaries, including correct final-block behavior.
- Routing selects the same handler and exposes the same method, path, and path-parameter behavior.
- Cancellation, early termination, failures, and shutdown release runtime resources predictably, while oversized bodies are rejected at the configured boundary.
- Every compatibility claim identifies the exact compiler and interpreter revisions, with extensions and intentional divergences clearly documented.

## Open questions

- Which transport, cancellation, and server-lifecycle differences are unavoidable across supported operating systems and architectures and therefore need classification as intentional divergences?
- Should compiler-native streaming or server capabilities beyond the interpreter surface be exposed now as documented extensions or kept internal until parity is complete?
