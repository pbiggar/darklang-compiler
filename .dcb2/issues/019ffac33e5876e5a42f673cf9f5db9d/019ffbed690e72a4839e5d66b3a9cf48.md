# Design brief

## Problem

At compiler C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 versus interpreter I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d, dictionary types, operations, and duplicate-key outcomes differ, so identical string-keyed programs lack behavioral parity.

## Goals

- Expose the interpreter’s complete string-keyed, single-value-parameter dictionary contract.
- Preserve value-form emptiness, Int cardinality, duplicate-rejecting ordinary insertion, and Option-based duplicate detection during list construction.
- Explicitly isolate compiler-only generic-key, enumeration, folding, and defaulted-lookup capabilities, and document any intentional divergence.
- Match all observable results, including collision handling and collection or traversal order.

## Proposed solution

Treat I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d as normative and C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 as the compiler comparison point. Provide a public compatibility contract over the existing representation, complete absent interpreter capabilities, and align existing type signatures, argument and result shapes, collision behavior, and observable ordering. Keep compiler extensions outside that parity contract. Maintain revision-pinned evidence linking every retained gap to current source and, where practical, a focused same-source probe; use report commit 8a402797 and parity documents only as historical leads.

## Success criteria

- The same source using the interpreter’s public string-keyed dictionary surface type-checks and produces equivalent results on both systems.
- Duplicate keys are rejected, reported, or overwritten only where the interpreter contract specifies, with the same winning value when overwriting occurs.
- Observable collection and traversal order matches the interpreter.
- Every claimed gap is traceable to revision-pinned source evidence and a practical same-source probe where feasible.
- Compiler extensions remain identifiable without changing baseline behavior.

## Open questions

- Should compiler-only extensions remain publicly accessible through a clearly separate non-parity surface, or be internalized?
