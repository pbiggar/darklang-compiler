`RawRelease` is an accounting-only stopgap, not a real release of storage. In this candidate, ANF encodes a special `RefCountDec` metadata marker, MIR/LIR turn it into `RawRelease`, and both ARM64 and x64 code generation ignore the pointer and only decrement the leak counter. The 80,016-byte allocation is bump-allocated because raw free-list reuse stops at 248 bytes, so the heap space remains unavailable for reuse. Leak checking therefore reports zero while allocator consumption does not decrease.

That is adequate for this extremely narrow, single-use trial, but it is not the runtime abstraction I would retain. It also makes `RawRelease` a misleading name and overloads reference-count metadata to communicate a unique-allocation lifetime event.

The alternatives compare as follows:

- **Blob:** It would reuse established ownership insertion and dynamic-buffer RC, but it is a poor semantic fit. Blobs are immutable byte values, whereas matrix construction mutates Int64 cells. Their header records byte length, while this lowering wants an element count. More importantly, current Blob decrement also balances leak accounting without reusing variable-sized storage, so converting to Blob would not solve physical reclamation.
- **General `DeAlloc`:** This is appropriate only with a real allocator contract. A raw pointer currently carries no allocation size, so a parameterless deallocation cannot choose a free-list class. A useful operation would need either `RawFreeSized(ptr, size)` or an owned allocation header containing its size. With the current arena it would mean “return to reusable storage,” not an OS `free`.
- **Internal array/buffer type:** This is the most idiomatic direction. A private `DenseInt64Buffer` or typed internal array could have an explicit layout such as `[element count][cells][ownership/size metadata]`, dedicated bounds-checked load/store operations, and a storage shape understood by ownership insertion. For proven unique, non-escaping buffers, retain operations can be omitted and final release can be size-aware; if the representation later permits aliases, ordinary RC can be added without pretending the value is a Blob or Dict.

My recommendation is therefore to treat `RawRelease` as trial scaffolding and eventually replace it with an owned, size-aware internal buffer abstraction. If a smaller allocator cleanup is desired first, generalize raw allocation/free as a matched pair carrying size information and support reusable large size classes. Merely renaming `RawRelease` to `DeAlloc` would overstate what the generated code currently does.
