# Design brief

## Problem

At C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, the compiler’s dictionary contract differs observably from interpreter I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d in key typing, duplicate handling, result forms, traversal order, and equality; DCB1@8a402797 is only historical evidence.

## Goals

- Provide full behavioral parity for the interpreter’s string-keyed public dictionary value.
- Preserve the HAMT only where its observable semantics match the interpreter.
- Clearly separate generic-key and convenience capabilities as compiler-only extensions.

## Proposed solution

Define one string-keyed public dictionary contract governed by interpreter semantics for construction, lookup, updates, combination, transformation, traversal, ordering, duplicates, and equality. Adapt or constrain the HAMT behind that boundary, add the missing public capabilities with interpreter argument and traversal behavior, and isolate compiler extensions from the parity surface. Retain prior parity findings only when reconfirmed against the recorded revisions.

## Success criteria

- Same-source comparisons at C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 and I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d produce identical shared results, duplicate outcomes, traversal order, and equality behavior.
- The public value is string-keyed, reports signed integer size, treats empty as a value, rejects duplicates on ordinary insertion, and uses an optional result for duplicate-sensitive bulk construction.
- Overwriting construction, combined filtering and mapping, and iteration match interpreter argument order and traversal behavior.
- Generic keys and additional enumeration, folding, and defaulted lookup remain explicitly separated compiler extensions.
