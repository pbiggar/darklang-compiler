# Design brief

## Problem

At compiler HEAD 768d68a5bacb31e5cf7f2202f25d038fe03ab776, the scope previously described here is already present through a sibling dictionary-parity delivery and subsequent integration fixes; darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d remains the interpreter baseline. The remaining risk is duplicate work or stale parity reporting, not a second implementation.

## Goals

- Treat the sibling delivery as the owner of dictionary type, behavior, ordering, equality, rendering, and private-storage boundaries.
- Revalidate the integrated result and retain only unowned regressions or stale parity reporting.
- Keep generic-key machinery private and classify AOT diagnostic timing as the intentional divergence.

## Proposed solution

Use the landed sibling delivery as a scope gate and dependency. Skip the public dictionary implementation already supplied there, including its shared equality and rendering integrations. Recheck the current compiler snapshot against the pinned interpreter, route any regression back to the owning work, and limit this issue to residual gaps that are both currently evidenced and outside that ownership. If no such gap remains, perform no duplicate implementation; only reconcile stale parity records through their existing owner.

## Success criteria

- Current same-source dictionary behavior matches the pinned interpreter for public types, values, duplicates, traversal, merging, and equality.
- No second implementation or competing public boundary is introduced.
- Generic-key storage remains inaccessible to user code, and the AOT-only diagnostic phase difference remains explicitly documented.
- Every residual discrepancy has one clear owner; this issue carries work only when it is not already covered elsewhere.

Deferring that scope prevents conflicting implementations while preserving a contained place for any genuinely residual gap.
