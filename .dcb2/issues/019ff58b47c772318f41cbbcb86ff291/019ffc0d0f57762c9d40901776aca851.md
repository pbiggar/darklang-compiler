# Design brief

## Problem

There is no version-locked, revalidated inventory of observable differences between the compiler and current interpreter for capabilities both support.

## Goals

- Use the current interpreter’s public behavior as the baseline for well-typed programs accepted by both implementations.
- Identify semantic, error, ordering, representation, and side-effect differences while excluding performance-only and already-owned feature gaps.
- Classify parity defects, compiler-only extensions, and intentional divergences explicitly.
- Preserve ahead-of-time type checking and exclude interpreter behaviors caused solely by lazy type checking.
- Group related differences while keeping genuinely independent outcomes separately deliverable.

## Proposed solution

Create an evidence-backed comparison ledger pinned to the exact compiler HEAD and darklang/dark revision. Revalidate prior-report and parity-document leads against current behavior, retaining only observable differences within shared support. Treat interpreter runtime behavior for statically invalid programs as an intentional architectural difference rather than a compiler parity requirement, without weakening compile-time checks or adding redundant runtime behavior. Consolidate related findings and propose one child issue for each independently observable difference or genuine design boundary.

## Success criteria

- Every comparison records both exact revisions and current supporting evidence.
- Every retained gap is observable in programs valid under both implementations and is substantiated by a focused same-source comparison where practical.
- Parity defects, compiler-only extensions, and intentional divergences are clearly separated.
- Lazy interpreter type-check behavior does not generate compiler work when compile-time checking already prevents the condition.
- Stale, unsupported, performance-only, and already-owned findings are excluded.
- Each proposed child is independently reviewable without fragmenting related behavior.
