# Design brief

## Problem

At C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 versus I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d, compiler-specific utilities are exposed without clearly distinguishing supported extensions from interpreter parity or runtime internals.

## Goals

- Use current interpreter behavior as the parity baseline and record both exact revisions
- Preserve intentional compiler-only source behavior under explicit compiler-specific contracts
- Prevent implementation-only runtime facilities from normal source resolution
- Keep related utility differences within one coherent design boundary

## Proposed solution

Re-baseline the scoped utility surface at the recorded revisions, treating the historical report and parity documents only as leads. Classify the source-facing filesystem, path, platform, randomness, and module-local encoding capabilities as documented compiler-only public extensions, without implying interpreter equivalents. Classify pointer-backed and other runtime plumbing as internal-only and exclude it from ordinary language name resolution. Capture observable contracts and intentional divergences with focused same-source evidence where practical.

## Success criteria

- Every comparison identifies C@51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 and I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d
- No compiler-only capability is presented as interpreter parity
- Each scoped capability has an explicit public-extension or internal-runtime classification
- Retained public extensions preserve their observable compiler behavior and document their compiler-specific contract
- Internal facilities cannot be resolved by normal user source
- Module ownership remains unchanged and semantic compatibility is not inferred from similarly purposed APIs
