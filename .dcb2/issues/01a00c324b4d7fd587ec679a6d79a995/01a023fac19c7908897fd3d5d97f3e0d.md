The HTML constructors are not parser-supported. `Stdlib.Html.div`, `img`, `document`, etc. are ordinary functions defined in `src/DarkCompiler/stdlib/Html.dark`; the parser has no `Html` references.

There is one HTML-specific compiler escape hatch, but it is in AST→ANF lowering, not parsing: `Stdlib.Html.voidElements`. It is registered as a compiler-visible value in `Stdlib.fs`, type-checked as `List<String>`, then lowered by constructing the literal list in `2_AST_to_ANF.fs`.

It exists because `voidElements` is a bare public module value, while the compiler’s stdlib source model materializes functions but does not generally compile top-level module constants. The HTML serializer needs it, and the E2E test also exposes it publicly. The same pattern already exists for `Stdlib.Blob.empty` and `Stdlib.List.empty`.

The parser changes introduced alongside Html/Http were generic compatibility work for qualified type aliases and interpreter-style multiline list layout; they do not recognize HTML names or syntax.

So: the HTML-specific lowering can be removed, but not while preserving `Stdlib.Html.voidElements` as a bare public value under the current module-value model. The clean options are:

- make the void-element list private behind a normal zero-argument Html function, changing/removing the public value; or
- add general source-level module-constant materialization, then define `voidElements` in `Html.dark` and remove its bespoke compiler registration/lowering.

The first is contained but changes the API. The second preserves the API and removes the HTML special case, but is a general compiler feature rather than an HTML cleanup.
