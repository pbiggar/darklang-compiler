That presumption does not hold: the pinned interpreter does **not** expose `Html.voidElements`. The repository’s generated compatibility inventory marks it compiler-only, and the interpreter-parity document records that native top-level value initialization/execution is absent in this compiler.

The prior Html/Http work therefore added `Stdlib.Html.voidElements` as a compiler extension, despite the parity document’s broader claim that `Html.s` is the only extension. It should not be preserved as interpreter compatibility.

A general module-constant feature could still be worthwhile, but it would be unrelated to interpreter parity and materially broader than removing an accidental HTML escape hatch. The contained cleanup is to remove the public compiler-only `Html.voidElements` value and keep the void-tag list internal to `Html.dark` through ordinary function code; that removes all HTML-specific compiler registration and ANF lowering without adding a new language feature.
