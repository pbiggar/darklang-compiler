# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, DateTime is aliased to Int64 and duration parsing is absent, diverging from the interpreter’s distinct DateTime and Int-based public contracts.

## Goals

- Match the interpreter’s observable DateTime type and arithmetic behavior.
- Match duration parsing results, recognized units, and exact errors.
- Explicitly classify retained compiler-only extensions and intentional divergences.

## Proposed solution

Treat the interpreter at the recorded revision as the parity baseline. Introduce a distinct DateTime value across the covered public surface, align its numeric contracts on Int, and add duration parsing with the interpreter’s accepted inputs, results, and failures. Handle these related differences as one compatibility change while documenting any deliberately retained divergence.

## Success criteria

- Same-source comparisons at the recorded revisions produce equivalent public values, types, and errors.
- DateTime is observably distinct from Int64 and the covered numeric contracts use Int.
- Duration parsing matches the interpreter for accepted units, computed results, and invalid-input errors.
- Every remaining compiler-only behavior is explicitly classified.

## Open questions

- Which compiler-only DateTime extensions, if any, are intentional and should remain?
