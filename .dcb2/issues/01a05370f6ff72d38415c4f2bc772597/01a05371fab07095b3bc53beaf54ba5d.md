**Feasibility: conditionally yes.** QEMU can provide a deterministic, meaningful *dynamic x86_64 guest-instruction-count* metric for Dark compiler work, but it cannot by itself measure native compile-time latency or prove a wall-clock win.

The existing QEMU track is not directly reusable: it runs compiled Dark benchmark executables under pinned QEMU 11.1.1 and counts their guest instructions. The compiler itself currently runs as an ARM64 .NET process in this environment; `/usr/share/dotnet/dotnet` is ARM64, and the x86_64 sysroot does not contain an x86_64 .NET runtime. The current QEMU runner also invokes the compiler outside QEMU, then measures only the resulting executable.

A compiler-specific track would need to run an x86_64 .NET runtime plus the compiler DLL under the pinned QEMU user-mode emulator, compile a fixed corpus, and count the entire compiler process. That count would include .NET startup, JIT, GC, stdlib construction, the Dark compilation pipeline, and output writing—exactly the work a cold CLI user experiences. A reduction is a credible real-work improvement on x86_64, provided it is stable across repeated identical runs.

It should be treated as an instruction-work gate, not a latency gate:

- It is deterministic in the same sense as the repository’s current QEMU/runtime and Cachegrind tracks: fixed binary, corpus, target, runtime, QEMU version, and plugin yield an exact count rather than noisy elapsed time.
- It does **not** model native CPU microarchitecture: cache behavior, branch prediction, JIT code quality on a real CPU, syscall cost, and QEMU translation overhead mean it cannot establish “compile time is faster by X%” on actual x64 hardware.
- Managed-runtime effects are material. JIT tiering/PGO, background runtime activity, and GC make it necessary to pin the .NET runtime/configuration and require several equal counts before accepting a result. Any variance should fail the measurement rather than be averaged away.
- The metric must explicitly define scope. Existing `CompileReport.CompileTime` covers user compilation after a prebuilt stdlib context; the CLI first builds that stdlib and then writes the binary. Cold end-to-end CLI and warm pipeline-only measurements answer different questions and should be separate tracks.

The repository is already well positioned for this: QEMU 11.1.1 and its instruction-count plugin are pinned in `benchmarks/infrastructure/qemu_instruction_count.sh`; the x86 quick track already version-locks QEMU, Rust, and toolchains; and the compiler exposes per-pass timing through `PassTimingRecorder` and `-vv`. Those timers are useful for diagnosis, while QEMU instructions would be the deterministic acceptance metric.

Recommendation: pursue this as feasible after provisioning a pinned x86_64 .NET runtime and designing a small fixed compiler-workload corpus. Use QEMU counts to reject regressions and substantiate large algorithmic wins; validate any claimed user-visible compile-time improvement with native x86_64 wall-clock measurements on a controlled runner. Do not repurpose the existing runtime-benchmark snapshots, since their track identity and measured program are fundamentally different.
