# Design brief

## Problem

Compiler-speed work currently relies on noisy wall-clock timings, so small real improvements cannot be distinguished reliably from host and runtime noise.

## Goals

- Provide an exact, repeatable instruction-work metric for compiling one representative Dark program.
- Measure the cold compiler CLI path users invoke, without measuring the F# compiler build.
- Make regressions fail and improvements auditable while preserving a correct compiled program.
- Retain per-pass timing only as diagnostic evidence, not as the acceptance metric.

## Proposed solution

Add an ARM64 QEMU compiler benchmark track centered on the existing `benchmarks/problems/fasta/dark/main.dark` program. `fasta` is the right initial workload: it is a non-trivial, fixed 74-line program with recursion, lists, tuples, floats, generics, and stdlib calls, and prior investigation identifies it as a material register-allocation compile-time target (about 100 ms of allocation within roughly 340 ms user compilation on native timing).

The measured command is one cold compiler invocation: the pinned ARM64 `dotnet` host runs the already-built `DarkCompiler.dll` under pinned `qemu-aarch64` with an ARM64 dynamic-instruction-count plugin, compiling `fasta` to a disposable ARM64 Linux executable. Thus the count deliberately includes .NET startup/JIT/GC, stdlib construction, all compiler passes, ELF generation, and output writing; it excludes `dotnet build`, QEMU setup, and correctness execution.

The track records an exact total guest-instruction count plus immutable attribution: compiler commit, SHA-256 of the benchmark source and expected output, compiler DLL hash, .NET runtime version/hash, QEMU version/hash, plugin hash, target, command shape, and measurement-policy version. Run the identical command three times before producing a result; all three totals must match exactly. A mismatch is a measurement failure, never an average.

After each counted compilation, validate that the output executable exists, is ARM64 ELF, and produces `fasta`’s existing expected output when executed outside the counted command. Keep a single baseline snapshot. A candidate passes if it is output-valid and its exact instruction count is less than or equal to baseline; it advances the baseline only when lower. Regressions fail without replacing the snapshot. The report shows absolute and percentage deltas and the existing `-vv` pass timings for diagnosis only.

This is an instruction-work gate, not a claim of equivalent native elapsed-time improvement. Native ARM64 timing remains confirmation evidence for changes intended to improve interactive compile latency.

## Success criteria

- A clean baseline produces three identical ARM64 QEMU guest-instruction totals while compiling `fasta`.
- The generated executable is validated against the existing `fasta` expected output.
- A lower exact count is recorded as an improvement; an equal count passes without rewriting the baseline; a higher count fails and preserves it.
- Any changed source, compiler artifact, .NET runtime, QEMU binary, plugin, target, or measurement policy invalidates comparison rather than silently reusing a baseline.
- The measurement report identifies the total delta and exposes pass timings for investigation without making timer values pass/fail criteria.
