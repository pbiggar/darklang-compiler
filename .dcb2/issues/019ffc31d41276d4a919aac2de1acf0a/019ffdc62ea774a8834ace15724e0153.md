# Design brief

## Problem

At C@971a70fa133c94efb970c6856f837044cdcf743b versus I@04fbe9dcc995c6188757d583e273cbd30a3e2d3d, floating-point behavior and public surface differ across parsing, formatting, rounding, classification, and advanced mathematics; DCB1@8a402797 was revalidated only as starting evidence.

## Goals

- Make shared numeric programs produce interpreter-equivalent values and errors.
- Provide shortest-roundtrip formatting while preserving signed zero and canonical nonfinite representations.
- Retain and explicitly document compiler-only conveniences and intentional divergences.

## Proposed solution

Deliver one compatibility slice that mirrors the interpreter’s public definitions where portable, adds typed architecture-neutral runtime operations for behavior requiring native support, centralizes IEEE special cases across backends, and replaces capped decimal generation with deterministic shortest-roundtrip conversion. Preserve the established angle helpers and documented compiler extensions.

## Success criteria

- The requested numeric surface accepts the same source and matches baseline values, option/result shapes, and runtime errors for ordinary, boundary, signed-zero, NaN, infinity, and domain cases.
- Every finite formatted value round-trips to the same bits using shortest text; signed zero and nonfinite spellings remain stable.
- Parity evidence records the exact compiler and interpreter revisions and classifies every retained extension or intentional divergence.

## Open questions

- What exact exponent and whole-number spelling should shortest-roundtrip output use where the pinned interpreter’s capped formatting is not roundtrippable?
- Should upward rounding adopt the interpreter’s arbitrary-precision result and nonfinite error contract despite the compiler’s existing fixed-width rounding extensions?
- Should hyperbolic tangent reproduce the pinned interpreter’s apparent hyperbolic-sine behavior or use mathematical tangent and record an intentional divergence?
