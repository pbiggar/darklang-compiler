You’re right. I traced it: in the current compiler, the stored descriptor identity has **no runtime consumer**.

`RecordAlloc`/`RecordClone` write it to offset 0, and `RecordGet` shifts field loads by one word. But there is no generated-code path that reads, compares, branches on, or validates that word. The only uses of `descriptor.Identity` are its construction and those stores (plus the analogous `NativeOutput` store).

The language’s nominal semantics are enforced earlier and statically:

- the type checker resolves record declarations, aliases, and type arguments;
- equality is admitted only for compatible nominal types before code generation;
- field offsets and field types come from compile-time record metadata;
- monomorphization and reference-count planning already retain concrete types;
- records and tuples cannot be interchanged by a well-typed program.

So I overstated the case in the prior answer: the **record-specific compiler metadata and ANF operations** are relevant to interpreter parity, but copying a 64-bit nominal tag into every native record allocation is not presently necessary for that parity. It is an unused runtime representation choice.

The direct nbody regression is therefore avoidable without reverting nominal record semantics: remove the physical identity word, restore fields at slot 0 and the old allocation sizes, while retaining `RecordAlloc`/`RecordGet`/`RecordClone` and all compile-time nominal metadata. That would need careful validation of all fixed-block offsets and reference-count payload sizes, but it does not appear to require a language-semantics change.
