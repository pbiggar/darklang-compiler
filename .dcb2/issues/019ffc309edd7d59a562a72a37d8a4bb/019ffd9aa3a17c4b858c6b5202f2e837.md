# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, program structure, resolution, entry selection, and completion differ from interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d.

## Goals

- Use pinned interpreter behavior as the program-level parity baseline.
- Unify values, functions, recursive references, types, modules, packages, and executable expressions under one program model.
- Preserve ahead-of-time whole-program type checking while documenting every remaining divergence.

## Proposed solution

Adopt the interpreter’s declaration and module syntax, namespace and collision rules, forward-reference behavior, and package-qualified resolution. Compose declaration-only package sources by module path, designate one script source as executable, resolve and validate the complete program before backend processing, then execute that script’s top-level expressions in order and use the final result under the interpreter’s completion contract. Remove legacy declaration forms, implicit main-function fallback, and synthesized source-level entries while migrating repository programs.

## Success criteria

- Equivalent programs resolve declarations, duplicates, forward references, and recursion consistently.
- Module and package boundaries expose the same names under the same qualification rules.
- A declaration-only script fails; executable expressions run in order with matching effects and completion, while competing executable sources fail deterministically.
- Whole-program errors are reported before backend processing without changing interpreter-visible acceptance or results.
- Parity evidence records both exact revisions and classifies all compiler-only extensions and intentional divergences.

## Open questions

- How should an AOT invocation select and record the interpreter package branch or immutable package snapshot used for resolution?
