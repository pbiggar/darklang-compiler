# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, program-level parsing, visibility, module/package resolution, and entry selection do not consistently match the public behavior of interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, including legacy forms and implicit entry fallbacks.

## Goals

- Make interpreter behavior the program-structure parity baseline.
- Apply matching declaration ordering, duplicate handling, forward-reference, recursion, module-boundary, qualification, and package-reference rules.
- Require an unambiguous executable entry and perform validation over the composed whole program.
- Explicitly classify any retained compiler-only extension or intentional divergence, with every comparison tied to the exact revisions above.

## Proposed solution

Adopt one interpreter-aligned program model covering top-level values, functions and recursive groups, types and constructors, modules, package references, and executable entry expressions. Resolve declarations using the interpreter’s ordering and visibility rules across composed source units, validate the complete program before backend processing, reject missing or competing entries, and remove legacy top-level syntax and implicit entry synthesis while migrating repository programs. Revalidate retained DCB1 and parity-document findings against the recorded revisions rather than carrying them forward as assumptions.

## Success criteria

- The compiler and interpreter accept or reject equivalent programs consistently for declaration ordering, duplicates, forward references, recursion, and qualified visibility.
- Module and package boundaries expose the same declarations under the same qualification rules.
- A program with exactly one valid entry executes it; missing or multiple entries fail deterministically during whole-program validation.
- Legacy top-level forms and implicit entry fallbacks are absent from supported repository programs.
- Parity evidence records both exact revisions and labels every remaining compiler-only behavior as an extension or intentional divergence.

## Open questions

- Which, if any, existing compiler-only source-composition conveniences should remain as explicitly documented extensions?
