# Design brief

## Problem

At compiler HEAD b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, source typing can diverge from darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d through compiler-only generic syntax, implicit type fallbacks, and differing inference, polymorphism, annotation, and error-phase behavior.

## Goals

- Make the pinned interpreter revision the source-visible parity baseline across bindings, functions, recursion, user types, constructors, annotations, and constrained uses.
- Match type-variable syntax, unification and occurs checks, repeated-variable constraints, generalization boundaries, any observable value restriction, fresh instantiation, annotation subsumption, inference failures, and error phase.
- Remove compiler-only generic syntax and implicit fallbacks; classify any retained extension or divergence explicitly.
- Keep monomorphization and specialization internal and observably equivalent to interpreter behavior.

## Proposed solution

Replace the compiler’s distinct source-level generic model with one interpreter-aligned typing contract. Revalidate DCB1 report commit 8a402797 and current parity documentation against the pinned revisions using source-traced comparisons and focused same-source probes. Build and solve constraints consistently, generalize only at interpreter-observed boundaries, instantiate polymorphic uses freshly, enforce annotations through the same relationships and occurs checks, and reject unknown types instead of defaulting them. Treat removed syntax and fallbacks as compiler-only extensions; permit backend specialization solely as an intentional, non-observable implementation divergence.

## Success criteria

- Every comparison records compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 and interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d.
- Same-source programs agree on acceptance, source-visible type relationships and results, rejection conditions, and error phase across the covered generic behaviors.
- Recursive and non-recursive generalization, repeated variables, constrained uses, annotation subsumption, and infinite-type cases behave like the interpreter.
- Compiler-only generic syntax and implicit type defaults are no longer accepted, while internal specialization creates no language-visible difference.

## Open questions

- Must diagnostic parity cover exact wording and source spans, or only failure meaning and phase?
- Should removal of existing compiler-only generic syntax be immediate or accompanied by a defined source-migration window?
