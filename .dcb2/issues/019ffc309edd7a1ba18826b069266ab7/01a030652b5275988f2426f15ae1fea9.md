## Implementation plan — with concrete examples

This plan keeps the interpreter’s public language as the baseline: compiler evidence `b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899`, interpreter evidence `04fbe9dcc995c6188757d583e273cbd30a3e2d3d`, and the implementation-base commit recorded for every new comparison. It does **not** remove interpreter-supported explicit type arguments; it removes only legacy compiler-only spellings and implicit backend fallbacks.

### 1. Build a small executable parity table first

Before changing checker logic, add a document and focused tests where each row is one same-source program with its expected parser result, type result, runtime result, and failure phase.

Examples:

- `let id<'a>(x: 'a): 'a = x; id<Int64> 42L` → accepted, returns `42L`.
- `let id = fun x -> x in (id true, id 42L)` → accepted; the two uses have independent types.
- `let same<'a>(left: 'a, right: 'a): 'a = left; same(1L, true)` → type error: one `'a` cannot be both `Int64` and `Bool`.
- `let bad<'a, 'b>(x: 'a): 'b = x` → type error even if `bad` is never called.
- `let self = fun x -> x(x) in 0L` → infinite-type error during type checking.
- `let value: Int64 = 1L` in interpreter syntax → parser error, because value annotations are not public interpreter syntax.

The table distinguishes an intentional AOT-early rejection from a parser or type-checking mismatch. For example, an empty value whose element type affects native representation may be rejected before lowering, while an interpreter might only discover the equivalent problem when it evaluates that value.

### 2. Align the public parser and signature-variable rules

Make parser behavior match the interpreter’s type-variable spelling and declaration rules. A function may declare parameters with apostrophes, and variables found in its parameter or result signature are implicitly included in that function’s type parameters. Explicit type arguments remain accepted only in the interpreter’s adjacent call form and must have exactly the declared arity.

Examples:

- Accepted: `let identity<'a>(value: 'a): 'a = value`.
- Accepted through implicit signature discovery: `let identity(value: 'a): 'a = value`.
- Accepted: `identity<Int64> 42L`.
- Rejected: `identity<Int64, Bool> 42L` when `identity` has one type parameter.
- Rejected legacy declaration syntax: `let identity<T>(value: T): T = value`.
- Rejected public value annotation: `let answer: Int64 = 42L`.

This work stays in parsing and written-type conversion; a syntax the interpreter does not have must fail before source type inference starts.

### 3. Replace string-based generic matching with structural inference state

Introduce explicit internal forms for four different concepts that are currently all represented as `TVar string`:

- source variable: the user wrote `'a`;
- inference variable: a fresh unknown created while checking an expression;
- quantified variable: the `'a` in a reusable scheme such as `forall 'a. 'a -> 'a`;
- rigid annotation variable: a skolem used while proving an implementation satisfies an annotation.

Use one pure substitution-threading unifier for every compound type.

Examples:

- Solving `'a` against `Int64` records the substitution `'a = Int64`.
- Solving `(List<'a>, 'a)` against `(List<String>, String)` succeeds.
- Solving `(List<'a>, 'a)` against `(List<String>, Int64)` reports a repeated-variable conflict.
- Solving `'a` against `List<'a>` reports an infinite type instead of creating a cyclic substitution.
- Solving `Result<Int64, String>` against `Result<Int64>` reports nominal type-argument arity mismatch.
- Solving `UserA` against `UserB` fails even if both happen to have identically shaped fields; nominal identity is preserved.

The old `matchTypes`, `consolidateBindings`, `unifyTypes`, and `reconcileTypes` paths are retired or reduced to adapters over this one solver. Diagnostics become structured internally and are rendered consistently at the type-checking boundary.

### 4. Type expressions with schemes: generalize, instantiate, recurse, and check annotations consistently

Typing environments hold schemes rather than raw mutable-looking types. A non-recursive independently polymorphic binding is generalized; each use instantiates it with fresh inference variables. Recursive groups instead receive monomorphic placeholders while their bodies are solved, then are generalized only outside the group. Function annotations are checked as whole polymorphic contracts, not as a collection of specializations observed at call sites.

Examples:

- `let id = fun x -> x in (id true, id 42L)` generalizes `id` once as `forall 'a. 'a -> 'a`; the first use gets `Bool -> Bool`, the second gets `Int64 -> Int64`.
- `let f = fun x -> x in f == f` still compares the one bound runtime closure to itself. Fresh type instantiation must not duplicate closure allocation.
- `let addOne = fun x -> x + 1L in addOne 2L` is not treated as polymorphic because the body constrains `x` to `Int64`.
- `let loop x = loop x` is checked as a recursive monomorphic definition; the checker must not accept distinct recursive calls at incompatible types.
- `let bad<'a, 'b>(x: 'a): 'b = x` fails by skolemizing `'a` and `'b` and proving that the body’s `'a` cannot satisfy rigid `'b`.
- `type Box<'a> = Box of 'a; Box(42L)` and `match Box(42L) with | Box(value) -> value` use the same instantiation and unification rules as ordinary calls.

This work explicitly records whether the interpreter exposes a value restriction. If it does, the restriction is an explicit generalization rule; it must not arise accidentally from traversal order or code generation.

### 5. Make solved type checking the only owner of source types; keep specialization internal

Type checking produces an elaborated program whose source expressions have solved types and internal instantiation facts. ANF lowering consumes that information; it does not invent source types for calls, tuple fields, record fields, list elements, or empty values.

Examples:

- After checking `identity<Int64> 42L`, lowering may produce an internal symbol such as `identity_i64`, but the source-level result remains exactly `42L`.
- `Stdlib.List.isEmpty<Int64> []` is closed and may lower normally.
- `Stdlib.List.isEmpty []` either remains valid only if its element type is provably representation-irrelevant, or fails as an explicit ambiguous-inference error before lowering. ANF must not silently choose `Int64`.
- A generic `fromList<Int64> []` specialization may lower directly to `Some(Dict {})` if that is semantically equivalent, but must not create a call to a nonexistent synthetic `Dict.empty_i64` helper.
- A recursive generic specialization discovers all closed dependencies before ANF-to-MIR. If a representation remains unsolved, compilation fails there with an inference diagnostic rather than crashing later in MIR.

The implementation preserves compiler-only monomorphization only as an invisible implementation technique. Source names, accepted programs, results, and closure identity cannot depend on specialization collection order.
