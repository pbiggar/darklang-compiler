You’re right: the current stage is inconsistent with the intended AOT divergence.

`pattern_matching.e2e:361` expects a compile-time `Non-exhaustive` error for the known `[1, 2, 3]` versus `[a, b]` case. But lines 584–589 explicitly describe analogous known list-length mismatches as runtime failures. The type checker has a narrow known-list-mismatch path (`1.5_TypeChecking.fs:4912` onward), while ANF lowering still unconditionally provides `makeNoMatchingCaseFallback` (`2_AST_to_ANF.fs:8703-8733`), producing `Non-exhaustive match: No matching case found …` at execution.

Also, `error="…"` alone does not identify the phase: the e2e harness accepts an error match regardless of whether compilation or execution emitted it. Here the surrounding comments and the ANF fallback establish that lines 584–589 are runtime cases.

So the current behavior is not a general compile-time exhaustiveness guarantee. It statically catches selected, provably impossible literal-list cases, then otherwise relies on runtime fallthrough. That conflicts with the stated intentional difference if that difference is meant to be comprehensive compile-time rejection of non-exhaustive matches. The prior scope language describing runtime non-exhaustive behavior should therefore not be treated as the intended contract.
