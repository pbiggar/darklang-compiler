# Design brief

## Problem

At compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 versus interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, match syntax, pattern coverage, binding validation, and failure reporting are not at parity.

## Goals

- Match the pinned interpreter’s complete public pattern grammar and semantics.
- Preserve single evaluation, left-to-right selection, binding scope, guarded fallthrough, and duplicate-binding rules.
- Retain documented AOT-only static typing differences without changing interpreter-observable runtime behavior.
- Keep value construction and representation with the tuple, list, record, and ADT owners.

## Proposed solution

Using DCB1 commit 8a402797 only as revalidated starting evidence, adopt an interpreter-shaped recursive pattern model supporting its literal, wildcard, variable, tuple, list/cons, constructor, nested, guarded, and alternative forms. Remove compiler-only record and ellipsis-rest patterns from the parity surface and migrate their uses. Validate every arm structurally, require consistent alternative bindings, type patterns and Boolean guards statically, and lower matches to ordered decisions that evaluate the scrutinee once, roll back failed bindings, evaluate guards only after successful patterns, and continue on false guards. Preserve non-exhaustiveness as a runtime match failure carrying the unmatched value; classify earlier static type errors as intentional AOT timing divergences.

## Success criteria

- Same-source matches over every pinned interpreter pattern form select the same branch and expose the same bindings.
- Pattern components, alternatives, arms, and guards are observed left-to-right, and only the selected body executes.
- Duplicate usable binders and inconsistent alternative bindings are diagnosed even in unreachable arms, while ignored-name behavior matches the interpreter.
- Non-Boolean guards are rejected statically as a documented compiler divergence; valid guards retain interpreter evaluation and fallthrough behavior.
- Non-exhaustive matches compile and fail observably at runtime with the unmatched value, while exhaustive matches succeed without requiring a catch-all.
- Compiler-only record and ellipsis-rest patterns are absent from the parity syntax and existing match expressions use interpreter-supported forms.
