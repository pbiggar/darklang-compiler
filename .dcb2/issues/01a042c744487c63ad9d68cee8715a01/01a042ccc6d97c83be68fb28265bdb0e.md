# Trial result

No safe multi-allocation region exists in Fasta’s hot CFG, so no ARM64 code candidate was retained.

## Evidence

## Problems

Remove repeated ARM64 heap-end materialization only where it demonstrably reduces Fasta’s hot allocation cost without register-pressure regressions.

## Solution

Fasta’s repeated allocation guards occur in `_start` while constructing literal tables once; the hot `makeRandomFasta` return block has one `HeapAlloc(16)` only. Hoisting there cannot reduce hot allocation cost, and startup-only commoning would not meet the material-gain requirement. No compiler code changed, x64 is untouched, and no commit was made.

## Implementation

- Recorded the rejected local-commoning trial in `docs/investigations/rejected-experiments.md`.
- Removed the local heap-end-commoning direction from `docs/investigations/benchmark-fasta-optimization.md`.

### Algorithm

1. Pin baseline `52282dc4a55ef88d60972be5ecf08f1aaabc68c6`.
2. Dump ARM64-assigned Fasta LIR with internal identifiers enabled.
3. Count allocation sites by function/block.
4. Require a hot region with at least two allocations and preservation of X11 over all intervening instructions and control-flow edges.
5. Reject because `makeRandomFasta_L0` contains one allocation, while `_start` contains the repeated startup-only allocations.

### Example

Before and after investigation, `makeRandomFasta_L0` is:
`X19 <- HeapAlloc(16); HeapStore(X19, 0, Reg X26); HeapStore(X19, 8, Reg X24); Ret`.
There is no following allocation in the block with which to share a materialized heap end. In contrast, `_start` contains 854 `RawAlloc` sites for one-time literal construction; reducing their static guard setup does not reduce the hot recursive allocation cost.
