# Design brief

## Problem

At compiler HEAD d61907cc7c3614035e12b97c9f445baf07d4b8b8, as at 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, the line-diff and typed value-search utilities from darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d remain absent; the compiler also lacks the interpreter’s runtime package-value catalog and dynamic value representation.

## Goals

- Match interpreter-visible diff classifications and ordering.
- Match canonical namespace, path, and custom-type identity semantics.
- Preserve AOT type safety and explicitly document compiler-only extensions and intentional divergences.
- Pin all parity evidence to exact compiler and interpreter revisions.

## Proposed solution

Copy the interpreter utility logic and public data shapes into the compiler standard library. Reuse existing collection and string behavior for diffing. For typed search, add a minimal native discovery bridge backed by canonical type and location metadata because the compiler’s monomorphized runtime representation cannot directly perform the interpreter’s dynamic package-value lookup. Keep static type enforcement and classify any restriction to the AOT-available value universe as an intentional divergence.

## Success criteria

- Equivalent text inputs produce identically ordered line classifications.
- Search results match canonical namespace prefixes, paths, and exact custom-type identities within the defined value universe.
- The utilities are available to compiled programs without unrelated behavioral changes.
- Parity evidence records compiler d61907cc7c3614035e12b97c9f445baf07d4b8b8 and darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, with every remaining difference classified.

## Open questions

- Should compiled search cover only package values embedded at link time, or must binaries query the interpreter’s full package store?
