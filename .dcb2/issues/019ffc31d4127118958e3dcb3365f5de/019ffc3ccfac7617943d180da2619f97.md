# Design brief

## Problem

At compiler revision 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, native programs lack the typed database and SQLite capabilities exposed by interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, preventing behavioral parity for persistence and SQL-backed programs.

## Goals

- Match the interpreter’s public database and SQLite behavior for typed values, persistence, queries, conversions, decoding, cardinality, nulls, and errors.
- Preserve portable abstractions and explicitly classify any compiler-only extension or intentional divergence.
- Maintain revision-pinned evidence for every retained gap using current source locations and focused same-source probes where practical.

## Proposed solution

Deliver one coherent vertical capability spanning type integration, database value representation, query semantics, persistence runtime support, and SQLite connections, parameters, values, and execution. Build the public surface from shared portable wrappers and decoders, compose errors consistently, and use the pinned interpreter behavior as the normative baseline. Retain DCB1 commit 8a402797 and existing parity documents only as leads, with conclusions revalidated against the recorded revisions.

## Success criteria

- Equivalent same-source programs produce matching observable persistence and SQLite results at the pinned revisions.
- Parameter conversion, row decoding, cardinality, null handling, and error behavior match the interpreter baseline.
- Every claimed gap has revision-pinned source evidence and, where practical, a focused behavioral probe.
- Any remaining difference is explicitly documented as a compiler extension, intentional divergence, or unresolved platform constraint.

## Open questions

- What persistence scope, isolation, and lifecycle should native binaries provide where the interpreter relies on managed platform context?
- What SQLite availability and connection-lifecycle contract must native binaries guarantee across supported platforms?
