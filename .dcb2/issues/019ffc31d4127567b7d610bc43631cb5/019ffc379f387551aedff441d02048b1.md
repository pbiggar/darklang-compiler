# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, UUID behavior does not match the public interpreter behavior at 04fbe9dcc995c6188757d583e273cbd30a3e2d3d and does not preserve UUID identity throughout execution.

## Goals

- Match canonical interpreter behavior for UUID parsing, generation, formatting, equality, and serialization.
- Return a single-case BadFormat parse error for invalid canonical input.
- Represent UUIDs as a distinct runtime value.
- Keep legacy parsing behavior explicitly separated as a compatibility extension.

## Proposed solution

Introduce one coherent UUID design pinned to the recorded revisions: use current interpreter behavior as the parity baseline, add strict canonical validation with Result-based failure, and carry a distinct UUID value through all observable operations. Preserve compiler-only compatibility behavior behind a clearly separate extension and document intentional divergences explicitly.

## Success criteria

- Canonical valid input parses to a distinct UUID value and invalid input returns BadFormat.
- Generated and parsed UUIDs have matching canonical formatting, equality, and serialization behavior.
- UUID values cannot be observed as ordinary string-backed runtime values.
- Compatibility parsing remains available only through the explicitly separated extension.
- Parity claims identify the exact compiler and interpreter revisions and are supported by revalidated current-source evidence.
