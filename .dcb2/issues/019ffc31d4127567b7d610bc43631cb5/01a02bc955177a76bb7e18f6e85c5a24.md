At current compiler HEAD `a0585c37c3957e597e3fb7e9029cd54e9554afe6`:

- `findByType` has no Uuid-specific branch. It accepts a caller-supplied type hash and queries package values as a custom type; the only UUID reference is an inaccurate comment in [ValueSearch.dark](/workspace/c4d-for-dcb/src/DarkCompiler/stdlib/ValueSearch.dark:42). A module-local `Uuid` sum type should be discoverable through this ordinary custom-type path, so Uuid should not be added to `findByType`.

- A single-case `Uuid = UUID(UInt128)` needs no Uuid-specific type-checking or equality logic. Existing sum equality expands payload comparison in [1.5_TypeChecking.fs](/workspace/c4d-for-dcb/src/DarkCompiler/passes/1.5_TypeChecking.fs:5793), and `UInt128` already has comparison support. The normal type checker handles the nominal distinction from `String`.

- The type belongs naturally in `Stdlib.Uuid`, alongside its constructor-facing parsing, generation, and formatting functions. It need not remain in the root [Types.dark](/workspace/c4d-for-dcb/src/DarkCompiler/stdlib/Types.dark:3).

- JSON does not currently provide `toJSON` / `fromJSON` hooks. [1.7_JsonPlanning.fs](/workspace/c4d-for-dcb/src/DarkCompiler/passes/1.7_JsonPlanning.fs:208) generates serializers and decoders from compiler type shapes, and its current Uuid handling is explicit at lines 328 and 728. [AltJsonBuilder.dark](/workspace/c4d-for-dcb/src/DarkCompiler/stdlib/AltJsonBuilder.dark:45) has `toJson`, but it builds a JSON object and is not a type codec hook.

So the first three points fit the ordinary-Dark representation directly. Moving UUID JSON behavior to `Uuid.toJSON` / `Uuid.fromJSON` would require a JSON codec-dispatch mechanism that does not currently exist; that is a distinct design and implementation change to the JSON system, not something available merely by defining functions in the Uuid module.
