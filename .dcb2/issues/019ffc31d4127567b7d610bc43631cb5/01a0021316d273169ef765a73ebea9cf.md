# Design brief

## Problem

At compiler HEAD 1ee3513aeded5eee6c4bac5779ee1aae9632f86b versus current darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, UUIDs remain String-backed, parsing and normalization diverge, and compiler-only legacy behavior expands the public contract.

## Goals

- Match the interpreter’s UUID parsing, generation, formatting, equality, and serialization behavior.
- Represent UUID as a distinct runtime value.
- Expose ParseError with BadFormat as its only case.
- Remove all legacy and compiler-only UUID surface behavior.

## Proposed solution

Replace the String alias with a dedicated 128-bit UUID value carried consistently through parsing, generation, equality, serialization, and deserialization. Accept and reject exactly the textual forms recognized by the pinned interpreter, return BadFormat for every parse failure, and emit canonical lowercase hyphenated text when formatting or serializing. Remove versioned compatibility APIs and additional error cases instead of preserving them as extensions.

## Success criteria

- The same UUID inputs produce matching success or BadFormat results on both recorded revisions.
- Equivalent accepted spellings normalize to equal UUID values and canonical lowercase hyphenated output.
- Generated values are distinct version-4 UUIDs rather than strings.
- Serialized UUIDs use canonical text and deserialize back to equal distinct UUID values.
- UUID values cannot be used as strings without explicit conversion.
- No compiler-only UUID parser, formatter, or error variant remains publicly exposed.
