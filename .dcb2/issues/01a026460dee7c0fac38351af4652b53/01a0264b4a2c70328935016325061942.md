Yes: the viable direction is to retire `passes/1_Parser.fs` and make the existing `passes/1_InterpreterParser.fs` the sole compiler entry parser. The compiler currently selects between both through `CompilerLibrary.SourceSyntax`; the CLI, E2E runner, syntax runner, AST printer, and corpus tests all preserve that split.

We cannot directly copy an interpreter parser from this repository: it does not vendor the interpreter implementation. The `parser.dark` files under `src/Tests/e2e/upstream/` are upstream test programs for the parser API, not its implementation. Historical parity evidence points to the interpreter’s `backend/src/LibParser/Parser.fs`, which is F#, and the compiler’s interpreter-syntax parser is a separate ~3,000-line F# reimplementation targeting this compiler’s AST.

If the upstream parser has since been rewritten in Dark, copying it still would not be a drop-in replacement: it would need a bootstrap/runtime path and an adapter from the interpreter’s parsed representation into this compiler’s AST and source-tree metadata. That is a substantially larger architecture change than removing the legacy compiler parser, and would add a circular dependency unless the parser is independently bootstrapped.

Recommendation: first collapse onto the existing interpreter-syntax parser, remove the `CompilerSyntax` public mode and compiler-only fixtures/formatting surface, then maintain parity through imported upstream syntax/E2E corpus coverage. Treat executing a Dark-authored upstream parser inside the compiler as a separate follow-on proposal, contingent on a stable parser API and bootstrap design.
