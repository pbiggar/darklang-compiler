No—not as a literal drop-in.

The current upstream parser is F#, but its public result is a range-complete `LibParser.WrittenTypes.ParsedFile` plus recoverable diagnostics, whereas this compiler requires its own `AST.Program` and `NameSyntax.ParsedSource`. The upstream execution path then lowers that tree into the interpreter’s `ProgramTypes`, not this compiler’s AST. [Upstream parser](https://github.com/darklang/dark/blob/14c4158ae7d0d2bb73964d1fe3752c6b262e7b96/backend/src/LibParser/Parser.fs) · [upstream project boundary](https://github.com/darklang/dark/blob/14c4158ae7d0d2bb73964d1fe3752c6b262e7b96/backend/src/LibParser/LibParser.fsproj)

Vendoring it would also entail its tokenizer, lexer, written-tree types, validation, Prelude, and project dependencies. Its parser state deliberately uses mutable stacks, lists, and counters, which conflicts with this repository’s functional/no-mutation rules.

A practical integration is possible, but it is a port, not a copy: vendor or reference the upstream parsing layer, then add a maintained `WrittenTypes → compiler AST/NameSyntax` adapter and decide how to translate upstream diagnostics. That adapter would be a new compiler front-end boundary and must cover all declaration, type, name-resolution, generic, and source-range semantics.

So: we can reuse upstream code as the authoritative grammar implementation only by accepting that dependency and building an adapter. If the goal is simply one parser now, deleting the legacy compiler parser and retaining `1_InterpreterParser.fs` remains the substantially smaller change.
