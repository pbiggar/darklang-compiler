Yes—substantially.

If performance is explicitly out of scope, Darklang can represent nearly all compiler-internal collections with existing types:

- association lists instead of `Map`/`Set`;
- lists instead of arrays and bitsets;
- recursive, immutable fixed-point functions instead of mutation/loops;
- `Blob`/`Bytes` plus recursive serialization instead of an efficient byte buffer.

That makes the first self-hosted compiler much simpler conceptually: port the F# algorithms as straightforward pure Dark programs, accepting that parsing, graph analysis, register allocation, and emission may be slow and allocate heavily. The current compiler is already structured around pure data transformations and explicit `Result` flow, so this is a rewrite rather than a language-design prerequisite.

The minimum remaining blockers are functional, not performance-related:

1. A self-hosted compiler must receive source/output paths or source text—there is currently no public argv interface.
2. It must write arbitrary executable bytes. `File.writeText` is insufficient; the existing `writeFromPtr` and raw-pointer facilities are internal compiler/stdlib mechanisms, not a usable public compiler API.
3. It must select a target, and macOS output still needs signing.

So the reduced initial prerequisite is a very small `CompilerHost` boundary—arguments/stdin, text input, binary Blob output, executable permission, target information, and signing. No general Array, generic map/set, or optimized byte builder is needed for bootstrap stage 1.

I would therefore revise the bootstrap plan: first expose that narrow host boundary; then port a deliberately slow list-based compiler for one Linux target; compile it with the F# seed; and use the resulting Dark compiler to compile itself. Efficient compiler data structures can be introduced later as an optimization project, once self-hosting correctness is established.
