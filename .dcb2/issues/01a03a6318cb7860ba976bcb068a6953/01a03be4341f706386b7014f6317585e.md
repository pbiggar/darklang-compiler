Yes—most of the compiler’s *semantic pipeline* can be rewritten in Darklang today, but a fully self-hosting compiler cannot yet be a straight port.

The F# compiler is about 75.7k lines. Its AST/ANF/MIR/LIR representations, parser, type checker, lowering, optimization, reference-count insertion, tree shaking, instruction selection, encoding, and executable-layout logic are predominantly pure transformations over algebraic data. That is exactly the shape Dark supports: ADTs, records, generics, recursion, closures, pattern matching, lists, strings, `Result`, arbitrary-precision `Int`, fixed-width integers, and typed effects. The project’s architecture explicitly identifies eventual Dark self-hosting as a design goal.

The important caveat is data structures and the outer driver. The current register allocator and bitset implementation rely heavily on F# arrays, loops, and local mutation; Dark currently exposes neither a general Array nor a generic map/set (its `Dict` is string-keyed). A literal port would therefore be impractically slow or awkward. Rewriting those algorithms purely with lists and string-keyed dictionaries is possible, but not a good production compiler. Add a small compiler-oriented substrate first: efficient immutable/persistent vectors or arrays, generic ordered maps/sets, byte buffers, and a total fixed-point iteration primitive or equivalent library implementation.

The other non-portable boundary is unavoidable but small: host target detection, command-line argument access, loading source files, writing arbitrary binary bytes, executable permissions, and macOS signing. The repository already has most of the native machinery below this boundary—typed file and raw-memory intrinsics, `Blob`, syscall lowering, and direct ELF/Mach-O emitters—but `RawPtr`/byte output are internal-only and there is no public argv API. Treat these as a deliberately tiny bootstrap/runtime ABI, not as compiler logic.

Recommended bootstrap:

1. Define a minimal `CompilerHost` intrinsic surface: `args`, `readText`, `writeBlob`, `setExecutable`, target selection, and macOS ad-hoc signing. Keep it explicit and target-dependent.
2. Add the missing efficient data structures and byte serialization API, validated independently while the F# compiler remains the trusted seed.
3. Port shared representations and pure front end first: lexer/parser → AST → name resolution/type checking → ANF. Use the existing F# compiler as the oracle through end-to-end and IR-dump comparisons.
4. Port MIR/LIR, optimizer, and register allocation next. This is the highest-risk performance phase; preserve the current dense-bitset algorithm rather than replacing it with list-based graph operations.
5. Port one complete vertical backend first—Linux x86_64 is the smallest deployment target here—through code generation, encoding, ELF serialization, and `writeBlob`. Then add ARM64 Linux and ARM64 Mach-O.
6. Build `darkc-stage1` from the Dark compiler sources using the existing F# compiler. Stage 1 compiles the same sources to produce `darkc-stage2`; require stage-1/stage-2 reproducibility where binary metadata permits it, plus full end-to-end-suite equivalence. Once that holds, use the Dark compiler for normal builds while retaining the F# seed as an audited bootstrap fallback.

I would call the project **self-hosting-feasible, but not self-hosting-ready**. Roughly 85–90% of the codebase by compiler logic is portable now; the remaining work is not primarily syntax translation—it is establishing performant compiler data structures and a narrow, principled host/byte-output ABI. The existing Dark stdlib is already substantial (about 29k lines of `.dark` sources), including raw-memory-backed Blob/Bytes code, which is strong evidence that the runtime can support the required lower-level substrate once it is intentionally exposed to the compiler.
