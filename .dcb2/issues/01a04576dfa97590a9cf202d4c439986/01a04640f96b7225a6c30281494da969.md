# Trial result

The pinned baseline already fused eligible comparison branches, so this trial retained only a neutral safety tightening of that existing optimization. No established-suite improvement was proven; overall multiplier: 1×.

## Evidence

## Problems

Remove redundant Boolean materialization on comparison-controlled branches.

## Solution

The existing LIR peephole already removed eligible Cset materialization. The retained change makes its flag dependency explicit: fusion is now rejected unless Cset immediately follows Cmp or FCmp, in addition to the existing CFG-wide single-use check. This preserves branch polarity and labels, retains backend condition handling on ARM64 and x64, and avoids exposing unrelated preceding flags. It is neutral for valid generated source cases already covered by the existing fusion.

## Implementation

- Required `Cmp` or `FCmp` immediately before `Cset` before fusing a Boolean branch.
- Added focused integer, float, and invalid-pattern LIR regression checks.
- Documented the eligibility invariant in `docs/classic-optimizations.md`.
- Committed the clean isolated candidate; no integration was performed.

### Algorithm

1. Match `Branch(condition, trueLabel, falseLabel)`.
2. Require the final instruction to be `Cset(condition, comparisonCondition)`.
3. Require the preceding instruction to be `Cmp` or `FCmp`, ensuring no intervening flag-clobbering instruction.
4. Require the Cset destination to have exactly one CFG-wide read and no earlier local use.
5. Remove Cset and replace Branch with `CondBranch(comparisonCondition, trueLabel, falseLabel)`.
6. Otherwise retain the materialized Boolean branch unchanged.

### Example

Before: `Cmp(v2, #4); Cset(v1, NE); Branch(v1, true, false)`. After: `Cmp(v2, #4); CondBranch(NE, true, false)`. Cset is removed while `NE` and both CFG labels are unchanged. Conversely, `Mov(v2, #1); Cset(v1, EQ); Branch(v1, true, false)` remains unchanged because no adjacent comparison proves the flags.
