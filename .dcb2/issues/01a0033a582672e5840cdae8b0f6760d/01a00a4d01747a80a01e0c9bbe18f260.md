`fannkuch` wasn’t “removed” in a bug sense; it was intentionally downgraded from canonical routine parity because full `n=9` exhausts Dark’s fixed heap.

The evidence is direct:

- The Dark benchmark file now calls `fannkuch(8)` and comments that full `n=9` can’t complete on the fixed heap. See [main.dark](/workspace/c4d-for-dcb/benchmarks/problems/fannkuch/dark/main.dark:94).
- `PARITY.json` marks `fannkuch` as `reduced` with reason: Rust can do full `n=9`, Dark cannot because the complete traversal exhausts the fixed heap. See [PARITY.json](/workspace/c4d-for-dcb/benchmarks/PARITY.json:64).
- Benchmark policy only includes `comparable` full pairs in routine; reduced ones are diagnostic-only. See [benchmarks/README.md](/workspace/c4d-for-dcb/benchmarks/README.md:69).

Why this looks like “memory not reclaimed”: Dark uses explicit ref-counting with free-list reuse and no moving GC. So it *does* reclaim/return blocks when RC drops, but there is no full garbage collector and the default workload allocates far too aggressively:

- Fannkuch’s full traversal is permutation-heavy (`n=9` is 362,880 permutations).
- In Dark it repeatedly rebuilds immutable SkewList-backed structures via `reversePrefix`, `rotateLeft`, `countFlips`, and `setAt`, which creates significant transient allocations per step. The existing investigation docs call this out as the dominant cost and attribution for fixed-heap exhaustion. See [benchmark-fannkuch-optimization](/workspace/c4d-for-dcb/docs/investigations/benchmark-fannkuch-optimization.md:3).
- Heap is bounded (512MB in ARM64/x64 codegen, with bump + free-list allocator layout). See [6_CodeGen](/workspace/c4d-for-dcb/src/DarkCompiler/passes/arm64/6_CodeGen.fs:69).

So yes—your intuition is directionally right: it’s about reclaim behavior in an allocation-heavy algorithm, but the proximate cause is allocator design + immutable list reconstruction volume hitting fixed-heap limits, not a missing collector that “never reclaims.”
