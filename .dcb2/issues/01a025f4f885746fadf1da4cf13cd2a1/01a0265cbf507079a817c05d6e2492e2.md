The suite’s dominant cost is architectural: E2E tests compile and execute a separate native binary for each expression, sequentially. The runner does reuse a prebuilt stdlib/preamble context, but `runE2ETestWithPreambleContext` still calls the full compiler and `executeCaptured` for every case. Execution writes each binary to `/tmp`, performs a durable `Flush(true)`, changes permissions, spawns it, captures output, and deletes it.

The largest concentration is `src/Tests/e2e/stdlib-internal/refcounting.e2e` (204 E2E cases), followed by `interpreter/cli_presentation.e2e` (30), `interpreter_behavior_parity.e2e` (16), `stdlib-internal/stream.e2e` (15), and `control_combinators_retry.e2e` (13). These are not inherently low-value: refcounting and interpreter-parity coverage catch real native-runtime/compiler regressions. Their granularity is the expensive part.

A timing run confirmed the process is CPU-bound and repeatedly emits native binaries; before I stopped it because this workspace already had three other full suites competing for CPU, it had written about 600 MiB. That shared-machine run cannot supply trustworthy per-test rankings, but it directly confirms repeated compilation/binary execution as the cause rather than an individual sleep or timeout. The explicit timeout test sleeps for only 5 ms, so it is not material.

Recommendations, in order:

1. Add a clean, non-contended timing baseline using the existing `--timings-json` output, and retain it as a CI artifact/trend. The runner already has the instrumentation needed.
2. Batch compatible E2E expressions from one source file into one compiled executable, with a small generated assertion harness that reports the original line/case. This preserves native end-to-end coverage while eliminating hundreds of compiler invocations. Start with `stdlib-internal/refcounting.e2e` and parity files.
3. Keep a small set of one-case-per-binary smoke tests for process, stdin, signals, exit-code, and crash behavior, where isolation itself is the behavior under test.
4. If batching is not immediately feasible, remove the durable `Flush(true)` from the test-only execution path after validating that the existing retry handles the race. It is an avoidable synchronous-storage cost for every binary; this should be measured separately because it changes execution infrastructure.
5. Consider parallel E2E compilation only after resource limits are explicit. The suite currently runs E2E serially; unrestricted parallelism would likely increase memory pressure and make CI timings noisy.

The most promising change is batching, not deleting refcounting or parity tests. It targets the repeated full compilation and process-launch cost while retaining the behavior those tests uniquely validate.
