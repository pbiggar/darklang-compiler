Disabling the *durable* flush is a credible optimization, but it should not be treated as a blind global deletion.

`Flush(true)` was introduced in commit `3afa2e915a` (2025-12-24) after “Text file busy” failures during parallel test execution. The commit’s evidence was three passing runs of a then-216-test suite. Parallel E2E execution was removed shortly afterward in `7dcc1baf33`; today E2E cases run sequentially, with only the unit suite running concurrently beside E2E.

The current code already closes the writing `FileStream` before `chmod` and `Process.Start`, and retries `Text file busy` up to three times with 10 ms delays. For an ephemeral executable, forcing the OS to persist file contents to physical storage is not required for correctness: closing the stream makes the completed file available to the subsequent `exec`; durability across power loss has no value. The `Flush(true)` comment also conflates persistence with `ETXTBSY`: on Linux, that error is normally about attempting to execute a file still open for writing, not the kernel merely delaying data persistence.

Important scope:

- The durable flush occurs in both `executeCaptured` (the E2E path) and `executeAttached` (normal `dark -r` execution), so a global removal changes production CLI behavior as well as tests.
- Several lower-level test helpers independently use `Flush(true)` and would remain unchanged. Thus this is not a complete test-speed solution.
- No repository test specifically verifies recovery from `ETXTBSY`; the existing retry is untested as a behavior.
- macOS code signing happens only after the stream closes. It has no apparent durability requirement, but Linux and macOS must both be exercised before accepting the change.

Recommended experiment: retain the scoped `use FileStream` and the retry, but replace only `Flush(true)` in the two `CompilerLibrary` execution functions with ordinary close semantics (or `Flush()` if desired for clarity). Then run repeated clean suites on Linux and macOS, recording `--timings-json` plus any `Text file busy` retry/failure occurrences. Compare the execution/write portion separately from total suite time. If reliable, limit the optimization to captured test execution first; make the interactive CLI path a separate decision.

I expect this to save synchronous I/O time—our interrupted run had already written roughly 600 MiB of generated executables—but it cannot address the larger repeated-compilation cost. It is a low-complexity complementary improvement, not a substitute for E2E batching.
