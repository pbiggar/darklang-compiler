Agreed: do not batch or alter the tests. The better fix is a compiler-session cache for already-allocated functions.

The key finding is that [`CompilerLibrary.compileUserWithPlan`](/workspace/c4d-for-dcb/src/DarkCompiler/CompilerLibrary.fs:2008) correctly reuses immutable stdlib and preamble LIR, but then passes those functions—and newly generated JSON decoder functions—through ARM64 code generation again for every executable. That is the measured **798.0s Code Generation** phase.

The viable compiler optimization is a **session-scoped function codegen cache**:

- Cache the symbolic ARM64 instruction list produced for an immutable, non-`_start` LIR function.
- Key it by the complete allocated `LIR.Function`, target, and codegen-affecting options; bypass it for coverage builds.
- Reuse cached instruction lists, then still run encoding and binary assembly per compilation. This is necessary because each test has a different entry point, string pool, and final call offsets.
- Scope the cache to an explicit compiler session, not a global or persistent cache. A test-suite invocation can thread that session through its existing sequential compiler calls; ordinary CLI compilation remains unchanged.

This directly covers both sources of redundant work:

- stable stdlib/preamble functions, which are already pre-lowered but currently re-codegenerated;
- `__dark_json_*` decoder functions, whose deterministic names and structurally identical LIR recur across JSON cases such as the 40 `Float` parses and 31 `Int64` parses.

The repository previously had this exact cache boundary: the removed implementation cached `LIR.Function → ARM64.Instr list` before encoding. Its limitation was policy, not correctness: it only admitted stdlib and preamble functions, so it missed generated JSON decoders. The replacement should be deliberately narrower than restoring all old cache systems: only an in-memory, lifetime-bounded codegen cache, only for known-reusable functions (`stdlib`, preamble, and compiler-reserved `__dark_json_*` functions). No SQLite, no global mutable cache, no parallelism.

This is preferable to replacing typed JSON plans with a generic runtime decoder. [`JsonPlanning`](/workspace/c4d-for-dcb/src/DarkCompiler/passes/1.7_JsonPlanning.fs:1) intentionally generates statically shaped decoders so records, sums, ownership, and precise path errors use normal compiler semantics. A reflective runtime decoder would need runtime type descriptors and duplicate that behavior; it trades a test-only compile-time regression for a broader runtime and semantic risk.

A second, larger compiler optimization is possible after this: promote planned JSON decoder functions into reusable symbolic-LIR artifacts in a compilation context, so repeated types skip AST→ANF, MIR, and register allocation too. It requires explicit context fingerprints for user records, sums, aliases, and specializations. The codegen cache is the safer first step because it targets the dominant measured phase while preserving identical per-program lowering and test behavior.

Expected validation should compare timing JSON before and after on the unchanged suite, verify byte-for-byte equivalent output for representative JSON cases, and ensure cache lifetime ends with the compiler session so memory cannot accumulate across runs.
