We found the 20 minutes.

A complete timing profile of the current 8,447-test suite took **1,236.8s (20m 36.8s)**. It attributes the cost overwhelmingly to typed JSON parsing tests:

| Work | Tests | Time | Share |
|---|---:|---:|---:|
| `Stdlib.Json.parse` E2E cases | 420 | **811.0s** | **65.6%** |
| All JSON E2E cases, including serialization | 579 | 823.5s | 66.6% |
| Everything else | 7,868 | 413.3s | 33.4% |

The slowest individual case is the nested `Result<Result<Option<Result<Int64, String>>, String>, String>` JSON parse at **10.19s**, almost entirely compile time. Many ordinary scalar JSON parse probes take 2–5s to compile. Runtime is not the problem: across the complete suite it is 13.5s; those slow JSON cases typically run in 2–8ms.

The phase totals confirm this is compilation, specifically code generation:

- Code Generation: **798.0s**
- AST → ANF: 120.0s
- Type Checking: 75.6s
- E2E suite-context construction: 65.4s
- ARM64 Emit: 48.7s
- Reference-count insertion: 30.2s
- MIR optimization: 29.8s
- Test runtime: 13.5s
- Stdlib build: 6.8s

`Code Generation` alone is 64.5% of wall time. The JSON parse cases drive it because `JsonPlanning.rewriteProgram` generates a monomorphic decoder graph for every target type, then each E2E assertion compiles that generated graph into a separate native executable. The deeper the target shape, the larger the generated decoder and the worse the compilation cost. JSON serialization does not have the same profile: the 420 parse cases account for essentially all JSON time.

The source corpus is [`src/Tests/e2e/upstream/stdlib/json.dark`](/workspace/c4d-for-dcb/src/Tests/e2e/upstream/stdlib/json.dark:1). Its line 1154 nested-result parse is the 10.19s outlier; even simple lines such as the `Int` parse probes near line 111 are multi-second compile operations. These tests are valuable—together they cover fixed-width and arbitrary integers, nested containers, records, dictionaries, sums, aliases, error paths, and deep type-directed decoding—but compiling 420 isolated native programs is not proportionate to that value.

The historical boundary now has a concrete culprit. The last recorded fast suite, 6,601 tests in 129.0s, predates `a2aa8b312` (**Implement AltJson and typed JSON parity**, Aug 15). That commit introduced `1.7_JsonPlanning.fs` (1,011 lines), the JSON runtime/stdlib surface, and enabled the upstream JSON corpus. The first recorded 15–26 minute runs occur after that parity series. This is a much stronger bisect result than the earlier broad parity range: typed JSON planning plus its enabled corpus is the regression boundary. A conventional wall-clock bisect remains unsuitable because worker contention varies, but the per-test compile-time classification is unambiguous.

Recommended next step: treat JSON as its own test-execution design problem. Keep a small set of isolated single-case native tests for compile errors and process boundaries, but batch compatible JSON assertions—at least scalar and same-shape error/success probes—into compiled programs with an assertion harness that retains line-level failure reporting. That preserves coverage while avoiding repeated generation and codegen of the same raw parser and decoder shape. This alone has a ceiling of roughly **11–13 minutes saved** from the current profile; further compiler work can then target code generation of the remaining complex decoder graphs.
