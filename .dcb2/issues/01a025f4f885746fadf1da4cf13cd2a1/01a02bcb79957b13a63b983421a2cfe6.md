The JSON *runtime operations* are fast; the 20-minute cost is recompiling their generated decoders. The 420 `Stdlib.Json.parse` tests consume **811.0s**, with **809.7s in compilation** and only **1.3s at runtime**.

[`JsonPlanning`](/workspace/c4d-for-dcb/src/DarkCompiler/passes/1.7_JsonPlanning.fs:1) already deduplicates decoders by concrete type within a single program. But each E2E assertion is compiled as a new program, so its planner state starts empty and regenerates—and the compiler re-lowers, allocates registers, code-generates, and encodes—the same decoder graph again. For example, the suite independently compiles `Json.parse<Float>` 40 times, `Int64` 31 times, `Int` 23 times, and numerous repeated container shapes.

The highest-value optimization is therefore **opt-in JSON E2E batching**, not making JSON parsing less expressive:

- Compile compatible JSON assertions from one source module into a single native test program.
- Have the generated harness evaluate each assertion and retain its original source line/name in failure output.
- Keep tests requiring compile failure, stdin, process exit, or intentional termination isolated.
- Let one invocation of `JsonPlanning.rewriteProgram` see all calls in the batch; its existing deterministic-name map then emits each shared decoder once.

This should eliminate the repeated compilation of primitive and shared nested decoders while preserving every JSON behavior assertion. Start with the repeated scalar parse groups, then measure whole-module batching versus smaller module/type-family batches—the full file may become large enough for compiler-pass costs to become nonlinear.

A suite-scoped cache of planner AST alone is not sufficient: the profile is dominated by **Code Generation (798.0s)**, so cached plans would still be lowered and code-generated for every executable. Likewise, simply restoring the old generic codegen cache is not a direct fix: its cacheable set covered stdlib and preamble functions, not generated user-side JSON decoder functions, and the project deliberately removed that infrastructure for complexity reasons ([`removed-optimizations.md`](/workspace/c4d-for-dcb/docs/removed-optimizations.md:1)).

A longer-term alternative is a narrowly scoped, explicit cache/linkable artifact for generated JSON decoder functions. That could help normal repeated compiler invocations too, but it needs careful keys for user-defined records, sums, aliases, compiler options, and binary relocation. It is substantially riskier than test batching and should follow only if batching leaves material time.

Recommendation: validate batching first with a representative repeated group such as `Float`/integer parsing, compare summed compile-phase timing and failure diagnostics, then expand to the compatible JSON corpus. This attacks the measured 810-second cost directly without dropping coverage or changing JSON semantics.
