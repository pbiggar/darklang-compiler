This is a real regression, not just test-count growth.

Repository-run records show:

- Aug 14: 5,930 tests in 32–43s; later 6,575–6,601 in 127–129s.
- Aug 17: 8,448–8,450 tests in 985–1,584s.
- Aug 21: 10,048 tests in 1,411.8s.

So the 5,930 → 10,048 increase is only 1.69× in test count, while recorded wall time rose roughly 33–44×. The first recorded slow suite is 8,449 tests in 1,146.9s at candidate `8412026a` (Aug 17); the transition occurred during the large parity-integration sequence between the Aug-14 samples and that commit, not in the recent loop-preheader or list-literal work.

The runner diagnostics point to repeated compilation rather than one pathological runtime test. I ran representative filters with the existing timing JSON:

- `--filter=date`: 271 tests, 45.4s. Individual E2E cases were mostly 88–143ms, of which 87–136ms was compilation; runtime was generally 2–6ms.
- `--filter=duration`: 21 tests, 27.2s. The date/duration parse cases similarly spent 81–207ms compiling and only 2–10ms running.

For the date sample, the measured cumulative compiler work was Code Generation 5.19s, Type Checking 3.83s, MIR Optimizations 3.61s, ARM64 Emit 2.17s, and AST→ANF 1.68s. It also incurred a one-off 14.03s stdlib build and 4.19s suite-context build. There is no single dominant compiler pass or slow test; the cost is distributed across every native E2E compilation.

That explains the scale: at roughly 0.1s+ per E2E compilation, thousands of imported upstream cases produce minutes of CPU time. The parity integrations added both many cases and substantially larger stdlib/preamble contexts: DateTime, List, Stream, Unicode/Regex, declarations/recursion/records, JSON, and the corresponding upstream fixtures. Large upstream files such as `string.dark`, `json.dark`, `date.dark`, `int64.dark`, and `int.dark` are part of normal discovery.

There is also an important measurement confounder. During this investigation, three other full test suites were simultaneously CPU-bound in sibling worktrees. The historical 985–1,584s reports were also produced by concurrent worker attempts. This does not explain the underlying per-test compile cost, but it can multiply the reported wall time; it makes a normal wall-clock `git bisect` unsafe as-is.

I did not mark a git-bisect boundary yet because the available fast and slow timing reports are from divergent trial worktrees rather than ancestor/descendant commits, and their host contention differs. Calling commits good/bad from those samples would produce a false result. A valid bisect needs a deterministic proxy: build each candidate in an isolated worktree, run a fixed selected corpus with `--timings-json`, and classify using summed E2E compile time (not elapsed wall time). The likely bisect range is the parity-integration series after the Aug-14 ~6,600-test samples and before the Aug-17 8,449-test result.

The next diagnostic should therefore be a clean timing run that groups the JSON by source file and reports aggregate compile time per file. That will reveal whether upstream DateTime/JSON/String/Int corpora dominate, or whether their presence made every ordinary E2E compilation slower through a larger shared stdlib context. It is the evidence needed to choose between reducing/reclassifying a corpus and fixing a compiler-wide regression.
