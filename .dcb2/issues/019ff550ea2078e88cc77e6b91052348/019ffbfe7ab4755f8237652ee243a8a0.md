# Implementation plan

Add a separate, reproducible compile-time benchmark path around CompilerLibrary.fs, using a fixed Dark source corpus, stable phase identities, a pinned NativeAOT measurement binary, deterministic instruction counts, environment-specific baselines, and non-gating wall-clock correlation data.

## Work item 019ffbfe7ab479e9ac5cc6d37519ddac

Title: Define stable compilation phase identities

Category: type

Evidence: Compiler passes are numbered under src/DarkCompiler/passes/, with architecture-specific passes under arm64/ and x64/; repository rules prohibit string sentinels.

Outcome:

Introduce an exhaustive discriminated union for every measured shared and architecture-specific compiler phase, plus stable serialized identifiers and target-specific expected phase order; keep overall compilation as a distinct measurement rather than a magic phase name.

## Work item 019ffbfe7ab4756e8691af440b9589d3

Title: Expose an isolated in-memory compilation boundary

Category: function

Evidence: src/DarkCompiler/CompilerLibrary.fs is the main compilation orchestrator, while the dark CLI also owns file and execution concerns.

Outcome:

Provide a CompilerLibrary entry point that accepts already-loaded source text and explicit compilation configuration, runs parsing through binary encoding, and returns the binary in memory so startup, source reads, output writes, and program execution remain outside every measurement.

## Work item 019ffbfe7ab47d71a1f46da5f7000615

Title: Add measurable pass boundaries

Category: function

Evidence: docs/compiler-passes.md documents the eight-pass pipeline, and individual pass files already provide natural attribution boundaries.

Outcome:

Route the isolated compilation pipeline through stable, non-inlined phase wrappers whose symbols can be attributed by the instruction-counting tool without changing pass inputs, outputs, or functional behavior; retain a wrapper covering the complete in-memory compilation.

## Work item 019ffbfe7ab47abeb8f5a2696d4d9547

Title: Create a pinned ahead-of-time benchmark executable

Category: other

Evidence: The repository builds with .NET 10 in its devcontainer, while normal compiler execution otherwise includes runtime startup effects that the design excludes.

Outcome:

Add a dedicated Release NativeAOT benchmark project with deterministic publish settings, retained measurement symbols, and a pinned .NET toolchain; make toolchain identity and benchmark-binary digest part of every result.

## Work item 019ffbfe7ab47974b84a6591be31bf07

Title: Define cold and warm workload semantics

Category: behavior

Evidence: The design requires distinct cold and warm workloads and excludes startup and source I/O.

Outcome:

Implement cold mode as one measured compilation in a fresh process after unmeasured startup and source loading, and warm mode as fixed unmeasured compilations followed by measured compilations in the same process; encode iteration counts in the result instead of relying on implicit defaults.

## Work item 019ffbfe7ab478b785356bfd2859ce22

Title: Add a versioned representative source corpus

Category: other

Evidence: src/Tests/e2e/ contains language-level workload material, and repository guidance explicitly forbids tests that compile the entire stdlib.

Outcome:

Check in small, fixed Dark programs covering parsing, type checking, generics and monomorphization, closures, pattern matching and ADTs, records and lists, control flow, register pressure, and both backend paths where supported; store sources directly rather than generating or compiling the full stdlib.

## Work item 019ffbfe7ab4765fa14a8b2ea98a963a

Title: Add an exact corpus manifest

Category: type

Evidence: The success criteria require missing, unexpected, and changed workloads to be reported deterministically.

Outcome:

Define a versioned manifest containing each workload ID, source path, content digest, applicable host and target profiles, and expected phase inventory; reject duplicate IDs, digest drift, missing files, undeclared files, and unsupported profile combinations with deterministically sorted diagnostics.

## Work item 019ffbfe7ab4790cba8aa67a00ac4b37

Title: Collect deterministic instruction counts

Category: behavior

Evidence: Existing wall-clock compiler timings are noisy, and the design explicitly selects deterministic instruction counting with startup and I/O excluded.

Outcome:

Run the pinned NativeAOT executable under a pinned deterministic dynamic instruction-counting tool with collection disabled until the isolated compilation boundary; extract inclusive counts for every stable phase wrapper and the complete compilation wrapper as unsigned integers.

## Work item 019ffbfe7ab475d096f72ed25e7bf5e0

Title: Validate phase attribution completeness

Category: behavior

Evidence: Platform.detectArch() selects arm64 or x64 backends at runtime, so valid phase inventories differ by architecture.

Outcome:

Compare each measurement against the target-specific ordered phase inventory and fail on missing, duplicate, reordered, or unexpected phases; report unattributed instructions between the overall boundary and measured phases separately so orchestration overhead cannot disappear from totals.

## Work item 019ffbfe7ab473fa952ab461f598508c

Title: Define the machine-readable result schema

Category: type

Evidence: The design requires machine-readable results keyed by measurement environment and repeatable output inventories.

Outcome:

Emit versioned canonical JSON containing corpus version, workload and mode, stable phase ID, phase and overall instruction counts, iteration semantics, binary digest, tool versions, and measurement-environment key; sort all collections and exclude timestamps and volatile paths from deterministic content.

## Work item 019ffbfe7ab4767e9a4d14aad8ef704d

Title: Key measurements by explicit environment profiles

Category: type

Evidence: The compiler supports macOS Mach-O and Linux ELF with runtime architecture selection, while the documented benchmark environment is the Docker devcontainer.

Outcome:

Define checked-in profiles covering host OS and architecture, target architecture, compiler configuration, .NET and AOT versions, instruction-counter version and options, and corpus version; begin with the Linux x64 host-to-x64 target supported by the devcontainer and reject unrecognized profiles rather than selecting a fallback baseline.

## Work item 019ffbfe7ab47a819590a25a510a2c5a

Title: Create dedicated compile-time baselines

Category: other

Evidence: benchmarks/run_benchmarks.sh and RESULTS.md currently represent generated-program performance, while the design requires independent compile-time baselines.

Outcome:

Store instruction-count baselines separately from generated-program benchmark baselines, indexed by environment, corpus version, workload, cold or warm mode, phase, and total; require an explicit command-line operation to regenerate canonical baseline data.

## Work item 019ffbfe7ab47276b48ae31ed6549b19

Title: Implement deterministic baseline comparison

Category: function

Evidence: The success criteria require stable attributable deltas and deterministic reporting of changed inventories.

Outcome:

Compare every current count to its exact baseline entry, fail regressions according to explicit checked-in per-profile policies, accept and report improvements, and fail before comparison when environment, corpus, workload, or phase inventories differ; emit absolute and percentage deltas per workload and phase plus aggregate totals.

## Work item 019ffbfe7ab473d8b170b17b71a06ca8

Title: Add controlled wall-clock measurement mode

Category: behavior

Evidence: The design requires controlled wall-clock medians to test whether count changes predict elapsed-time changes.

Outcome:

Provide a separate non-instrumented timing mode using the same isolated boundary, fixed warmups and samples, monotonic timing, explicit CPU-affinity options, and median plus dispersion statistics; retain raw samples and environment metadata while keeping wall-clock noise out of deterministic instruction-count gates.

## Work item 019ffbfe7ab47a938b4df603f55f73f7

Title: Report count-to-time correlation

Category: function

Evidence: A success criterion is demonstrating whether instruction-count improvements correlate with lower wall-clock compile time.

Outcome:

Compare current and baseline instruction and median-time deltas across matching workloads, calculate a documented correlation statistic and directional agreement, and clearly report insufficient or mismatched samples rather than fabricating a value.

## Work item 019ffbfe7ab47260a121d2de752009d7

Title: Keep secondary metrics extensible but noncanonical

Category: type

Evidence: The design leaves secondary metrics for equal-instruction cases open, and repository conventions prohibit unknown-value defaults.

Outcome:

Represent optional allocation or simulated-cache measurements as versioned optional metric records keyed by environment, without inventing values or using them as regression gates until a profile explicitly enables a defined collector.

## Work item 019ffbfe7ab473159c9f7b993a14b47b

Outcome:

Add a compile-time benchmark script with flags for profile, cold or warm mode, instruction collection, wall-clock collection, verification, output path, and baseline regeneration; use no environment-variable configuration and do not execute generated binaries.
