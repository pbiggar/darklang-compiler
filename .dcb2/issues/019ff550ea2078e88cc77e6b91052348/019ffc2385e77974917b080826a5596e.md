# Design brief

## Problem

Wall-clock compiler benchmarks are distorted by host contention, runtime startup, and input/output, making pass-level performance changes hard to attribute reliably.

## Goals

- Measure compile-only cost with a deterministic instruction-count metric immune to noisy neighbours
- Report both total compilation cost and cost per compiler pass
- Compare candidate and baseline revisions using identical inputs, runtime, toolchain, and configuration
- Retain machine-readable measurements for reproducibility and diagnosis

## Proposed solution

Introduce a canonical benchmark mode over a fixed representative corpus using a pinned deterministic instruction-count environment. Prefer Valgrind/Callgrind if it can run the .NET compiler reliably; otherwise use an equivalent emulator or process-scoped counter proven insensitive to host contention. Keep runtime preparation, corpus loading, and output handling outside the measured region, while measuring compilation as a whole and partitioning the same count at pass boundaries. Compare repeated candidate and baseline runs using the instruction count as the canonical metric; wall-clock data may remain diagnostic but must not determine regressions.

## Success criteria

- Repeated runs of an unchanged revision produce identical counts or remain within a deliberately tight documented tolerance, including under competing host load
- A deliberate compiler slowdown or improvement is detected consistently against a baseline
- The reported pass-level changes account for and localize changes in total compilation cost
- Candidate and baseline results are produced from the same corpus and pinned execution configuration
- Raw total and per-pass counts are available in a stable machine-readable form

## Open questions

- Can Valgrind/Callgrind execute the pinned .NET runtime reliably and provide stable counts, and which deterministic mechanism should replace it if not?
- Which target architecture and representative programs define the canonical corpus?
