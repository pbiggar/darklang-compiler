# Design brief

## Problem

Wall-clock compiler timings are too noisy to distinguish small performance changes reliably.

## Goals

- Identify and select a deterministic compiler-performance metric
- Produce reproducible baseline-to-candidate comparisons
- Reliably detect differences of 1% or greater
- Use compilation of the current runtime benchmark corpus as the representative workload

## Proposed solution

Begin by evaluating the viable noise-independent measurement options: Valgrind Cachegrind or Callgrind against managed .NET and NativeAOT builds, emulator-based instruction counting, and process-scoped retired-instruction counters. Compare them for .NET compatibility, repeatability under competing host load, corpus coverage, and sensitivity to 1% changes. Pin the simplest mechanism that satisfies those criteria in a fixed Linux environment, compile the identical runtime benchmark corpus with baseline and candidate builds, sum the measured work into one candidate-to-baseline ratio, and classify changes of at least 1% as faster or slower; wall-clock timing remains informational.

## Success criteria

- The available mechanisms are compared and one is selected using demonstrated repeatability, .NET compatibility, and immunity to competing load
- Repeated measurements of an unchanged revision produce an effectively identical ratio and the same classification
- Injected compile-work changes of 1% or greater are reliably detected in the expected direction
- Every comparison reports one corpus-level ratio and labels the candidate faster, slower, or unchanged

## Open questions

- Can the managed .NET compiler be counted repeatably, or must the canonical measurement use NativeAOT?
- Should the deterministic metric cover the entire compilation command or only compiler-owned work?
- What tolerance, if any, is acceptable if the best viable mechanism does not produce exactly identical counts?
