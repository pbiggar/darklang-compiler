# Design brief

## Problem

At compiler HEAD 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3, native compilation lacks the broad operating-system-facing CLI behavior exposed by darklang/dark revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, preventing same-source parity.

## Goals

- Match the interpreter’s public observable behavior across environment, filesystem, POSIX, shell configuration, installation, and daemon capabilities.
- Maintain revision-specific, source-backed evidence for every gap, using focused same-source probes where practical.
- Explicitly distinguish parity requirements, compiler-only extensions, platform limitations, and intentional divergences.
- Exclude performance differences unless they affect observable behavior.

## Proposed solution

Establish a revision-pinned compatibility matrix, revalidating rather than inheriting findings from report commit 8a402797. Add a coherent platform capability layer for essential native operating-system operations, then expose the broader behavior through shared library abstractions aligned with the interpreter’s semantics, including results, side effects, cleanup, path handling, and platform-specific behavior. Keep closely related differences within this single compatibility effort and document every exception with source and behavioral evidence.

## Success criteria

- Scoped same-source programs produce equivalent results, errors, side effects, and resource-lifecycle behavior on supported targets.
- Every scoped capability has current source evidence and behavioral evidence where practical, tied to the exact compared revisions.
- Compiler-specific extensions and intentional or unavoidable divergences are explicitly classified and documented.
- Existing supported compiler behavior remains compatible outside documented divergences.

## Open questions

- Should PowerShell-facing compatibility cover its behavior on the existing macOS and Linux targets only, or establish semantics for a future native Windows target?
- When an operating-system capability is unavailable on a target, should incompatibility be detected during compilation or reported as a typed runtime result?
- What stability and cancellation guarantees should apply to long-running observation and daemon operations beyond behavior currently exposed by the interpreter?
