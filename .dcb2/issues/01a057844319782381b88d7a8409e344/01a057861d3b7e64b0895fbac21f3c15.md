The compiler has the naming model needed for this, but not the package-loading boundary.

- `NameResolution` already models package and builtin identities separately, and preserves exact qualified names.
- Today the compiler exposes only four explicitly registered builtin identities (`unwrap`, `testRuntimeError`, and `testNan` plus its v0 spelling). Other compiler primitives are either `Stdlib.*` intrinsics or private `__*` functions available only while compiling the bundled stdlib.
- The bundled stdlib is a fixed list of local `.dark` files. The checked-in name-resolution contract explicitly says the compiler does **not** load content-addressed packages; its existing package catalog is only an immutable AOT snapshot for `ValueSearch`, not callable package code.
- The interpreter repo’s package tree includes `darklang/stdlib`, `internal`, language tools, CLI, and other packages, so direct compilation needs to resolve package dependencies and builtin calls together rather than merely add aliases. [Interpreter package tree](https://github.com/darklang/dark/tree/main/packages/darklang)

Recommendation: treat this as a package-import feature with a builtin manifest, not a broad renaming of `Internal` or `__` helpers. Introduce a pinned interpreter-package source inventory that declares package identities and dependencies, and a separate typed builtin manifest whose entries have canonical `Builtin.<name>_v<version>` identities, source signatures, and an explicit native lowering (or an explicit unsupported error). Feed both inventories into the existing name-resolution and type-checking environments, then compile the reachable package closure alongside user code.

This keeps private `__*` implementation helpers private, preserves interpreter-style builtin versioning, and makes unsupported interpreter builtins visible at the source boundary instead of accidentally treating them as compiler internals. The first implementation should target the smallest package closure containing a known builtin call, with end-to-end tests for versioned resolution, package-to-builtin calls, package dependency reachability, and an unsupported builtin diagnostic.
