The space is broader than exposing `__*` under `Builtin.*`. There are four separate boundaries to plan:

1. **Builtin identity and versioning.** `NameResolution` has `BuiltinFunction`/`BuiltinValue` identities, but the compiler registers only `unwrap`, `testRuntimeError`, and `testNan` (with one explicit `_v0` alias). Most current `Builtin.*` entries are instead ordinary `ModuleFunction` compiler extensions. A manifest must be authoritative for name, version, function/value kind, type parameters, parameter types, return type, and lowering class.

2. **Execution lowering.** A callable name alone is insufficient: `AST_to_ANF` has explicit lowering only for `print`, `printLine`, `stdinReadLine`, `unwrap`, `testRuntimeError`, `testNan`, and package-catalog specialization. Every additional interpreter builtin needs either a pure Dark replacement, an ANF/runtime primitive and both backend implementations, or an intentional AOT-unsupported diagnostic.

3. **Package ingestion and linking.** The compiler loads a fixed local stdlib file list. It has no source-package resolver, dependency closure, source/hash pin, package type environment, or callable package linker. Its existing package catalog supports `ValueSearch` snapshots only; it cannot make interpreter package functions callable.

4. **Visibility and collisions.** Compiler-only `__*` functions are deliberately hidden from programs compiled against the stdlib. Promoting them wholesale would expose raw pointers, refcounting, allocation, and representation details. In addition, `Builtin.print`, `Builtin.printLine`, and `Builtin.stdinReadLine` presently exist as module intrinsics; registering true builtins with the same spelling requires one canonical inventory, not duplicate candidates that happen to resolve by provenance order.

`Builtin.jsonParse`, `Builtin.Test.runtimeError`, and `Builtin.TInt64` also appear textually in the upstream fixtures, but the observed instances are parser/tokenizer input, comments, or a `LanguageTools` enum constructor—not evidence that those runtime builtins must be implemented.

## Package-level problems beyond builtin calls

- The compiler’s source-unit API can compose parsed units, but does not assign interpreter package identities, resolve package dependencies, or preserve an interpreter package hash/revision boundary.
- Packages bring types, constructors, generic definitions, values, functions, and possibly package-to-package dependencies. The current preamble mechanism is useful infrastructure but is not a package manager: imported declarations are treated as a flat inherited environment.
- Package code may rely on interpreter-only language tools, metadata, effects, or runtime services. The plan needs a compatibility classification per dependency: **native**, **implemented in Dark**, **AOT snapshot**, **test-only**, or **unsupported**.
- Current v0 alias generation applies to ordinary registered functions. Builtins need exact interpreter-version semantics instead: no inferred aliases, no accidental fallback to another version, and source diagnostics that name the requested version.
- The implementation must preserve the current rule that user code cannot name compiler representation helpers such as raw-memory `__*` operations, even if a public builtin happens to be implemented using one.

## Recommended planning sequence

First create a pinned interpreter builtin-and-package inventory, rather than choosing individual mappings ad hoc. For every builtin referenced by the selected package closure, record its exact signature/version, category, interpreter implementation location, candidate compiler implementation, target status, and test status. Then choose an initial package closure and enumerate its transitive dependencies. Only after that should the implementation plan decide which entries are native lowerings, Dark wrappers, AOT snapshots, or explicitly unsupported.

The first design decision to settle is the product boundary: whether “call interpreter packages directly” means **a pinned vendored package set compiled into the binary**, **caller-supplied package sources**, or **content-addressed package resolution**. The existing compiler supports none of these as packages today; choosing one determines the loader, reproducibility model, diagnostics, and caching strategy.
