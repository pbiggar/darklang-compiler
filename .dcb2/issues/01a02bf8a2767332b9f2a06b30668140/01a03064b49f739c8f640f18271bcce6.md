# Design brief

## Problem

Compiler-only APIs currently include values and operations whose behavior is supplied during compilation or by native intrinsics, producing source-visible behavior not present in the target runtime language.

## Goals

- Make the compiler and target runtime differ only in permitted diagnostic timing and non-observable implementation strategy.
- Allow constant folding only when it preserves the semantics of an existing target-language operation.
- Remove source-reachable compiler-only APIs that have no parity target.

## Proposed solution

Audit every registered `CompilerExtension` and documented extension. Replace each surviving API-level compile-time fold with its equivalent target-language implementation and retain only ordinary semantics-preserving optimization. Remove registrations, lowering paths, public declarations, and tests for extensions with no equivalent target operation. Keep compiler-private intrinsics inaccessible to source programs.

## Success criteria

- `Stdlib.Path.tempDir()` no longer requires a compiler-specific constant-folding case and retains its existing `"/tmp"` behavior through the target-language definition.
- No source-reachable public compiler extension remains unless it has a documented parity counterpart with identical observable behavior.
- Compilation-context facts are not exposed through retained public APIs.
- Type checking and exhaustiveness checking remain compile-time diagnostics as the intentional phase difference.

## Conversation response

Agreed. Constant folding is acceptable only as an implementation optimization of a surviving, semantically equivalent runtime-language operation—not as a reason to retain a compiler-only API.

Current evidence finds one explicit API-level fold: `Stdlib.Path.tempDir()`. It already has an equivalent Dark implementation returning `"/tmp"` in `stdlib/Path.dark`; the compiler-specific `tryConstantFoldIntrinsic` case can therefore disappear while ordinary compiler optimization may still fold the resulting literal call. No observable API or result remains compiler-specific.

For every other extension candidate, the rule is:

- If an interpreter/parity operation exists, implement or retain that operation with matching runtime semantics; normal constant propagation/folding may optimize it when its inputs make that valid.
- If no equivalent target operation exists, remove the public name and its compiler registration/lowering. Do not preserve it merely because native code can provide the value or effect.
- Keep private lowering primitives only where they are unreachable from user source and necessary to implement retained parity APIs.

This excludes compile-host-dependent substitutions such as target OS, target architecture, filesystem state, environment values, clocks, or random values. Folding those into a binary changes the program’s observable result based on compilation context, not merely the timing of computation.
