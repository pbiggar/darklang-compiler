# Design brief

## Problem

At compiler HEAD d3a336e8d6f38cf165709537f6d07f2e5ea73a32 the JSON family is absent, while interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d exposes distinct structural and type-directed contracts.

## Goals

- Provide the complete scoped AltJson structural contract.
- Provide type-directed Json serialization, parsing, structured errors, and paths.
- Match current interpreter behavior while explicitly classifying compiler-only extensions and intentional divergences.

## Proposed solution

Introduce one lossless JSON core preserving numeric text, object order, and duplicate fields. Project it into AltJson’s structural model and convenience operations, then derive Json encoders and decoders from resolved compile-time types. Preserve the interpreter’s observable formatting, supported-type rules, error cases, and path rendering; reject compiler-only value categories unless they receive an explicit extension contract.

## Success criteria

- Scoped same-source programs behave like interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d for valid and malformed JSON.
- Structural parsing, formatting, access, construction, ordering, duplicates, omissions, escaping, and numeric behavior match the baseline.
- Supported typed values round-trip, including records and enums, with matching structured failures and nested paths.
- Every parity comparison records both exact revisions, and every extension or intentional divergence is explicit.

## Open questions

- How should interpreter content-addressed package and type identities carried by typed errors map onto the compiler’s nominal type identities?
