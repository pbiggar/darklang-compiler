# Implementation plan

Single contained compiler change. Every comparison below is pinned to compiler b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899 (C) and darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d (I); DCB1 8a402797 was used only as a lead. Interpreter-visible grammar and evaluation are authoritative, while unavoidable AOT type-checking differences remain explicit documented divergences.

## Work item 01a001edbfd2753a973ff779393a636a

Title: Establish the executable operator contract

Category: behavior

Evidence: I backend/src/LibParser/Parser.fs:58-75,757-815,1445-1526,1857-1899,2078-2133 and execution tests language/apply/einfix.dark plus language/flow-control/epipe.dark define the current behavior; C vendored einfix.dark is reduced and its epipe.dark is adapted with legacy aliases.

Outcome:

Create a compact parity matrix and same-source corpus covering accepted tokens, precedence, associativity, grouping, unary negation, operator values, sections, partial application, pipelines, evaluation order, arity, and failure timing.

## Work item 01a001edbfd27f8ab73f3d3a1f592bb8

Title: Align both compiler parser frontends

Category: function

Evidence: C passes/1_Parser.fs:1481-1698 and passes/1_InterpreterParser.fs:1785-2002 assign ^ to XOR, omit @, add bitwise tiers, make comparisons non-chainable, and bind unary operators recursively; I Parser.fs:1445-1526 and 1857-1899 defines the differing table and parses -f x as -(f x).

Outcome:

Give CompilerSyntax and InterpreterSyntax one public operator table: add list append @, make ^ exponentiation, use interpreter precedence, make @ and ^ right-associative, keep other binary families left-associative including comparison parsing, and restrict prefix syntax to unary minus with interpreter application binding.

## Work item 01a001edbfd27075b361fc435c05d3ea

Title: Reject legacy source operator tokens

Category: behavior

Evidence: C passes/1_Parser.fs:45-164 and passes/1_InterpreterParser.fs:26-160 accept these tokens; I Parser.fs:2078-2092 explicitly diagnoses them as reserved or unsupported. C AST.fs:55-86 currently exposes matching source-level bitwise and unary cases.

Outcome:

Remove public parsing of <<, >>, &, |||, compiler XOR ^, ~~~, and !, producing the same reserved/unsupported-token behavior as the interpreter without removing backend bitwise primitives used by named functions.

## Work item 01a001edbfd27621879188fc57a8e0d6

Title: Represent pipelines as typed syntax

Category: type

Evidence: C parsers rewrite |> immediately into Call, TypeApp, or Apply at passes/1_Parser.fs:1491-1517 and passes/1_InterpreterParser.fs:1795-1824, including a permissive Apply fallback. I WrittenTypes and ProgramTypes model PipeExpr variants, and Parser.fs:757-815 rejects unsupported segments.

Outcome:

Introduce explicit pipeline and pipeline-segment cases that retain the left expression, allowed segment kind, supplied arguments, and type arguments until type checking/desugaring; arbitrary expressions cannot masquerade as valid pipeline stages.

## Work item 01a001edbfd27ad5808f3081d0f57e0a

Title: Implement operator values and sections

Category: behavior

Evidence: C passes/1_Parser.fs:1925-1963 recognizes only && and || and constructs a unary lambda after consuming a following operand; passes/1_InterpreterParser.fs:2299-2360 does the same for a wider legacy set. I Parser.fs:757-773 and 2105-2133 separately model pipeline infix stages and two-argument operator functions.

Outcome:

Make every public parenthesized infix operator, including @ and ^, a standalone two-argument callable with normal partial application; preserve the pipeline-specific x |> (op) y form as op x y instead of consuming y while parsing (op).

## Work item 01a001edbfd2769885a44665cf22fd93

Title: Preserve pipeline name resolution and argument placement

Category: function

Evidence: I WrittenTypesToProgramTypes.fs:684-693,775-891 resolves structured segments and ProgramTypesToRuntimeTypes.fs:823-851 prepends the value; I epipe.dark covers List.push, local variables, lambdas, generic calls, constructors, and (-). C parser-time AST rewriting cannot preserve all of that context.

Outcome:

Lower valid named, generic, variable, lambda, enum-constructor, and infix pipeline stages by evaluating the pipeline value once and prepending it to existing arguments while retaining local shadowing and explicit type arguments.

## Work item 01a001edbfd27853bc1e2e766fba6d89

Title: Correct partial-application capture semantics

Category: behavior

Evidence: C passes/1.5_TypeChecking.fs:2432-2479,2547-2589,2670 onward and 4370 onward synthesize lambdas containing supplied argument expressions, which can delay or repeat effects and failures. I Interpreter.fs:1004-1036,1191-1224,1528-1657 stores evaluated argsSoFar and completes or rejects application at the corresponding arity boundary.

Outcome:

Evaluate supplied arguments once, left-to-right, when a partial application is formed; capture their resulting values and preserve interpreter behavior for underapplication, exact application, overapplication, non-callable values, and errors across named, generic, module, lambda, operator, and pipeline calls.

## Work item 01a001edbfd27ca0a877103b615e6ab6

Title: Match primitive operator invocation

Category: behavior

Evidence: I ProgramTypesToRuntimeTypes.fs:170-183,853-899 and Builtins.Pure/Libs/NoModule.fs:253-597 define dispatch and failures. C passes/2_AST_to_ANF.fs:2864-2907,3336-3392,4044-4197 maps ^ inconsistently—fixed-width XOR but arbitrary Int power—and 4_MIR_to_LIR.fs:382 rejects float modulo while 1734-1844 adds a compiler-specific negative-divisor error path; Runtime.fs supplies native runtime helpers but no unifying public operator dispatch.

Outcome:

Lower +, -, *, /, %, ^, ++, &&, ||, unary minus, and @ to type-directed AOT implementations matching interpreter operand order, supported types, overflow behavior, division/modulus rules, exponentiation rules, arity, and error timing; keep general comparability meaning outside this change.

## Work item 01a001edbfd279439f18130b95ef67cb

Title: Migrate affected Dark sources

Category: other

Evidence: At C, stdlib Bool.dark uses !; integer modules implement bitwise APIs with &, |||, ^, <<, >>, and ~~~; Base64.dark, Crypto.dark, String.dark, Uuid.dark, __HAMT.dark, and numeric modules consume those tokens. These sources must not be reinterpreted when ^ changes meaning or fail when legacy tokens disappear.

Outcome:

Replace compiler-only bitwise, shift, complement, boolean-not, and XOR expressions throughout stdlib, runtime-facing Dark code, tests, examples, and benchmarks with canonical named functions or private typed intrinsics; leave ^ only for exponentiation and use @ for list append where semantically equivalent.

## Work item 01a001edbfd27ea7ac3d92dd9519beac

Title: Retire legacy rewrites and operator aliases

Category: other

Evidence: C passes/2_AST_to_ANF.fs:2891-2907 still targets Stdlib.Int.mod_v0, while Stdlib.fs:207-235 broadly strips _v0 and supplies implicit Stdlib prefixes. C passes/3_ANF_to_MIR.fs and passes/4_MIR_to_LIR.fs contain valid internal bitwise instruction lowering independent of public token acceptance.

Outcome:

Remove obsolete parser pipe rewrites, source-AST legacy operator cases, synthetic section typing, operator-specific _v0 references, and permissive aliases reached by operator lowering; retain internal MIR/LIR bitwise operations only as implementation details for canonical named APIs and document that boundary.
