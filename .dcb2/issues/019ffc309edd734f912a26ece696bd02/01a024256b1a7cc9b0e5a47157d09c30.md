# Implementation plan

One expression-grammar boundary remains: current compiler parser/lowering retains operator behavior that differs from interpreter revision 04fbe9dcc995c6188757d583e273cbd30a3e2d3d.

## Work item 01a024256b1a7d9ba74bf3725f2b7e79

Title: Align operator expressions and pipelines with the interpreter contract

Category: behavior

Evidence: Interpreter `backend/src/LibParser/GRAMMAR.md` and `Parser.fs` at 04fbe9d define `|>`/`||`/`&&`/comparison/`@`/additive/multiplicative/`^`, with right-associative `@` and `^`, two-argument sections, validated pipe segments, and reserved unsupported bitwise tokens. Compiler `src/DarkCompiler/passes/1_Parser.fs` currently accepts bitwise operators, parses `^` as left-associative `BitXor`, implements only `&&`/`||` one-argument sections, and rewrites arbitrary pipe RHS calls. `2_AST_to_ANF.fs` currently routes `BitXor` through `Stdlib.Int.power` while also retaining legacy bitwise primitive paths; `src/Tests/e2e/stdlib/tuple2.e2e` documents unsupported partial pipe calls.

Outcome:

Add source-backed parity probes and e2e coverage that record compiler and interpreter revisions; replace the parser’s legacy operator ladder with the interpreter precedence/associativity contract; support two-argument sections for every retained infix operator and pipe-infix sections with the piped value as left operand; restrict pipe RHS forms to interpreter-valid segments; preserve left-to-right argument evaluation, partial-application arity, and failure timing through ANF; lower `^` as right-associative power and `@` as right-associative `Stdlib.List.append`; remove expression-level legacy `<<`, `>>`, `&`, `|||`, `~~~`, and `!` behavior and associated aliases/primitive paths; retain comparison meaning outside this change’s comparability boundary; update operator-facing docs and migrate affected e2e/stdlib expressions.
