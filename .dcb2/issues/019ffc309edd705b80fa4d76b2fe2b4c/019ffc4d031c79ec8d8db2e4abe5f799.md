# Design brief

## Problem

At compiler HEAD b2e1f3d1e4ce0338d4c4662db9a1326f2e2cb899, recursive declarations do not consistently match the public syntax and observable binding semantics of darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, leaving legacy syntax and ambiguity around recursive values, mutual groups, scope, typing, and cycles.

## Goals

- Match the pinned interpreter’s recursive declaration syntax and observable behavior for recursive functions, recursive values, mutual groups, annotations, shadowing, invalid cycles, and references across group boundaries.
- Carry recursive availability and group membership explicitly through resolution, typing, and lowering without spelling conventions or sentinels.
- Treat the interpreter as the parity baseline while explicitly classifying compiler-only extensions and intentional divergences.
- Remove legacy recursive syntax after migrating affected compiler-owned sources.

## Proposed solution

Introduce one explicit recursive-group representation spanning parsing, name resolution, type checking, and lowering. Establish all group binders in the group scope before resolving members, preserve lexical shadowing and group boundaries, type the group using monomorphic recursive assumptions with annotation checking and baseline-compatible generalization, and enforce the interpreter’s rules for recursive values and invalid cycles. Validate every retained finding from DCB1 report commit 8a402797 against the pinned revisions using focused same-source evidence, and document any remaining observable divergence, including completion differences caused by stack or tail-call behavior.

## Success criteria

- At the pinned revisions, the same recursive source is accepted or rejected consistently and accepted programs have matching observable results across both implementations.
- Mutual references work only within the availability and group boundaries exposed by the interpreter, with matching shadowing and annotation behavior.
- Unsupported polymorphic recursion and invalid value cycles fail consistently with the interpreter, while valid recursive values and functions behave consistently.
- Recursive identity and membership remain explicit throughout the compiler pipeline, with no magic names, string sentinels, or inferred grouping conventions.
- Legacy recursive syntax is no longer accepted after affected sources use the interpreter-compatible form.
- Any compiler-only extension or observable runtime divergence is identified explicitly rather than being treated as parity.

## Open questions

- When tail-call lowering lets the compiler complete a valid program that exhausts the interpreter’s stack, should completion remain a documented intentional divergence or should observable failure parity be required?
