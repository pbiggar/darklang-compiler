# Design brief

## Problem

At compiler HEAD 4f5112a49370b5a5c7dd8cfe213b625947c98d68 versus darklang/dark 04fbe9dcc995c6188757d583e273cbd30a3e2d3d, native programs lack the interpreter’s canonical environment, filesystem, POSIX, shell-installation, and daemon behavior; existing compiler facilities have incompatible names and contracts.

## Goals

- Achieve same-source observable parity on supported native targets.
- Preserve interpreter-compatible values, errors, ordering, cleanup, and side effects.
- Reuse portable Dark workflows while implementing operating-system effects natively.
- Classify compiler extensions and unavoidable AOT or platform divergences explicitly.
- Maintain revision-pinned source and focused behavioral evidence.

## Proposed solution

Introduce one canonical platform-capability layer for environment mutation, filesystem and descriptor operations, metadata, locking, ownership, signals, observation, compression, and downloads. Port the interpreter’s portable path, directory, file, shell-configuration, installation, and daemon workflows onto that layer, integrating with the canonical binary-data and process boundaries. Preserve exact public contracts and resource lifecycles, while retaining existing compiler-specific facilities only as documented extensions and recording every AOT or target-specific divergence.

## Success criteria

- Scoped same-source programs produce equivalent values, structured errors, constants, filesystem effects, and cleanup behavior.
- Path handling, temporary resources, atomic updates, locking, links, permissions, ownership, traversal, and observation match the baseline contract.
- Shell configuration, installation, removal, and daemon state transitions produce baseline-compatible outcomes on supported targets.
- Native downloads and decompression match the interpreter-visible success, failure, and output behavior without external tool dependencies.
- Every retained difference is tied to the exact compared revisions and classified as parity, compiler extension, or intentional divergence.

## Open questions

- How should expression-based daemon launching behave in an ahead-of-time executable without adding runtime evaluation?
- Should interpreter capability-denial behavior be reproduced in standalone binaries or documented as a host-model divergence?
- Should PowerShell behavior be limited to the current macOS/Linux targets or define contracts for a future Windows target?
