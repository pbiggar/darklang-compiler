# Design brief

## Problem

The compiler’s CLI runtime exposes only a partial, differently shaped system interface, so interpreter programs cannot rely on consistent environment, filesystem, POSIX, shell-installation, and daemon behavior when compiled.

## Goals

- Make the current interpreter’s observable behavior the canonical compatibility contract.
- Provide the complete requested CLI system surface through shared workflows backed by native operating-system capabilities.
- Preserve compiler-only extensions and document every intentional divergence explicitly.
- Make comparisons reproducible by pinning compiler 51093e0a8e31fe45a9aa79a317fbefd6b74fbcc3 and interpreter 04fbe9dcc995c6188757d583e273cbd30a3e2d3d.

## Proposed solution

Treat this as one compatibility program: derive a revision-pinned behavioral contract from the interpreter, covering results, errors, constants, side effects, resource lifetimes, concurrency, and platform behavior; add a native capability layer for operating-system operations; port the interpreter’s high-level workflows onto it; and retain existing compiler extensions only as clearly classified additions. Revalidate inherited findings with current source evidence and focused same-source parity probes, while excluding non-observable performance differences.

## Success criteria

- Programs using the requested public CLI surface compile and exhibit interpreter-equivalent observable behavior on supported platforms.
- Focused same-source comparisons agree on successful results, state changes, error values, and lifecycle behavior at the recorded revisions.
- Shell setup, installation, and daemon workflows behave consistently across supported shells and operating systems.
- Every remaining mismatch is recorded as an intentional divergence, a compiler-only extension, or an explicitly unsupported platform capability.

## Open questions

- Which operating-system and architecture combinations define the initial required support matrix?
- Where host capabilities genuinely differ, should compatibility prefer interpreter-shaped unsupported errors or platform-specific behavior?
